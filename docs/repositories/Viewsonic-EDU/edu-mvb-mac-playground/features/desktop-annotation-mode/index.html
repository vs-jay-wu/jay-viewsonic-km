Desktop Mode（桌面標註模式）on macOS POC · VB-2247

狸貓版 mac edu-mvb-mac-playground · POC 2026-09-10 · 提出者 Jay · 需求單 VB-2247（2026-09-16 開立，掛在 VB-1897 Mac Native 底下）· 原型在本機 worktree ~/.mvb-worktrees/poc-desktop-mode（未 commit）
📘 總覽 ✅ 人工驗證清單

結論：可行，而且比 Windows 那側簡單

全部功能都在 App Sandbox 內做得到，不需要新增任何 entitlement； 現行 myViewBoard.entitlements 原封不動就能跑。 唯一需要使用者授權的是「螢幕錄製」，而那只在擷取畫面時用到——單純標註不需要任何權限。

已經做出可執行原型並實測：三個顯示器同時鋪滿標註層、可以畫、擷取的圖裡 標註有入鏡、工具列沒入鏡。

1. 舊版（Sparrow）是怎麼做的

Windows 出貨線的桌面標註模式是 Sparrow.DesktopMode —— 一個獨立的 WPF 程序，跟主程式之間隔著 Named Pipe 與一個 helper 程序。

來源內容
edu-sparrow-app
docs/sparrow-feature-map.md:67		 「Sparrow.DesktopMode / WPF / .NET FW / 桌面標註模式（透明全螢幕標註層）」
同上 :499 「Desktop 模式同對話跨三程序（UWP ⇄ Bridge ⇄ DesktopMode），AppService + Named Pipes，Bridge 中繼。」
同上 :539 「Sparrow.Bridge 是 Win32 helper 程序，讓沙箱化 UWP AppContainer 做 UWP 做不到的事」
這個三程序架構是 UWP AppContainer 的限制逼出來的，不是功能需求。 macOS 沒有這個限制：標註層就是本 app 的另一個 NSWindow， 共用同一份 app 狀態，整層 IPC 直接消失—— 跟 spec 0222 把 ClassSwift 的跨程序視窗機制原生化時，得到的是同一個結論。

連帶消失的東西：ClassSwiftActions / DesktopModeIpcActionNames 那組 action enum 與兩側 event-processor switch、syncState 鏡射、 Bridge pipe 的 5 秒 connect timeout、以及「DesktopMode 不可重新引入 heartbeat tracker」這類 為了多程序而生的規矩。

ClassSwift 那塊排除的理由：mac 的 CS 已經是 in-proc（spec 0222）， Sparrow 那套 CS 整合有一半是 IPC 中繼的產物。要不要在桌面模式裡開 CS 是**獨立的產品問題**， 不該綁在「桌面標註可不可行」這個問題上。

3. macOS 的四個關鍵決策

3.1 視窗層級：.screenSaver

畫在所有一般視窗、Dock 與選單列之上。這不是新賭注—— repo 內既有的螢幕擷取區域選取遮罩 (ScreenCaptureService) 用的就是同一個層級， 已經在出貨線上驗過。工具列再高一層（+1），選取遮罩 +2。

3.2 點擊穿透：per-tool 切換

ignoresMouseEvents 跟著工具走：畫筆時吃事件，游標工具時整層放行。 這是「標註不必霸佔整台電腦」的關鍵，也是唯一一個 Sparrow 沒有的互動語意。

3.3 誰入鏡：sharingType

視窗設定為什麼
標註層.readOnly擷取畫面時要把標註一起拍進去
工具列.nonechrome 不該出現在教材截圖裡
選取遮罩（矩形／自由）.none遮罩的暗底與框線不該入鏡

副作用（實作時踩過）：sharingType = .none 的視窗用任何截圖工具都拍不到， 所以「工具列到底有沒有畫出來」沒辦法用截圖驗證，只能靠 CGWindowList 查它的 frame。 原型留了一個 MVB_POC_TOOLBAR_CAPTURABLE=1 的自測開關把它暫時放回鏡頭裡。

3.4 座標系：筆跡存全域座標

每一筆的點都存 global AppKit 螢幕座標，不是視窗本地座標。 這讓「顯示器重新排列」「解析度改變」「跨螢幕連續畫一筆」都不需要特別處理， 也讓橡皮擦的命中測試與各層的局部重繪可以共用同一組數字。

4. 實測數據

4.1 三個顯示器同時鋪滿

CGWindowList 在原型執行中的實測（本機三螢幕：5K + 5K + Retina）：

name=mvb.desktopmode.chrome layer=1001 onscreen=true  bounds=455x46
name=                       layer=1000 onscreen=true  bounds=2560x1440   ← 顯示器 1
name=                       layer=1000 onscreen=true  bounds=2560x1440   ← 顯示器 2
name=                       layer=1000 onscreen=true  bounds=1800x1169   ← 顯示器 3

4.2 擷取鏈（自動化自測）

原型內建一個自測：自動畫一條標記筆正弦曲線＋一條螢光筆橫線，然後擷取整個螢幕並寫檔。 產出的圖同時證明了三件事：

  • ✅ 標註有入鏡（紅色曲線、黃色半透明橫線都在）
  • ✅ 工具列沒入鏡（當時它就在畫面上）
  • ✅ 拍得到其他 app 的真實畫面 → SCScreenshotManager 在 App Sandbox 內可用，不需要新 entitlement

4.3 進入模式的耗時

使用者第一次試用時回報「進入要 2~5 秒、游標轉圈，看起來像當機」。 加上分段計時與主執行緒停頓偵測後，量到的是：

階段耗時做了什麼
hideMainWindows33 ms把白板主視窗 orderOut
overlay[0..2]3~5 ms 各三個全螢幕標註層
toolbarInit20~31 msSwiftUI 工具列建構 + 首次 layout
activate0.5~8 msNSApp.activate
TOTAL73~86 ms
mainThreadFree83~109 ms主執行緒重新空閒
停頓偵測0進入後 12 秒內沒有任何 >150 ms 的主執行緒停頓
那 2~5 秒不是桌面模式的進入路徑造成的。 在「app 剛啟動 1.5 秒」與「完全就緒 30 秒後」兩種狀態各量過，數字一致。 可能的來源是 Debug build 自己的啟動成本（Sentry + olfparser dylib + MQTT 連線） 或當下的 Space 切換。再遇到時用 MVB_POC_HITCH=<檔案> 啟動就能把停頓抓下來。

4.4 繪製效能

量測期間順手改掉的兩件事（原型初版沒有）：

  • 標註層改 layer-backed（wantsLayer + .onSetNeedsDisplay）—— 一個 5K 全螢幕層走 CPU backing store 約 59 MB，三個就是 177 MB，改由 GPU 合成。
  • 局部重繪——畫線只失效「這一小段」的矩形、只重繪筆跡經過的那個顯示器； 橡皮擦游標圈也只失效圈的範圍。原本是每次滑鼠移動都重畫三個 5K 全層。

5.1 別的 App 全螢幕時，標註層蓋不上去（實測結論）

老師把簡報／影片開成 native 全螢幕（綠燈那種，自己一個 Space）時，那個螢幕無法標註。 這是 macOS 的行為，不是我們的 bug，也沒有公開 API 可以繞過。

證據等級：實測。三螢幕環境，主顯示器上跑著一個 native 全螢幕的 app：

觀察結果
三層 overlay 都有建立 overlay display=3 frame={{0,0},{2560,1440}} visible=true（三層都 visible=true）
實際收到筆畫的是哪一層 只有 display=1 與 display=2 有 mouseDown；display=3 一次都沒有
display 3 那層在系統眼中的狀態 CGWindowList：layer=1000 onscreen=false（另外兩層 onscreen=true）
同一螢幕上蓋著什麼 Orca layer=0 frame=(0,0,2560,1440) — 一個佔滿該螢幕的 native 全螢幕視窗
把 window level 拉到 CGShieldingWindowLevel()（2147483628，screen-capture shield 用的層級） 沒有用：該層仍是 onscreen=false。層級不是問題

.fullScreenAuxiliary 只讓視窗跟自己 app 的全螢幕視窗共存； 別的 app 的全螢幕 Space，第三方視窗加不進去。我們自己的白板進全螢幕則沒問題 （標註層照樣蓋得上去）——差別就在「誰擁有那個 Space」。

對產品的意義（要讓 PM 知道）：

  • 老師要在簡報上標註，簡報請用最大化視窗而不是全螢幕。
  • Windows 版沒有這個限制（Sparrow 的標註層直接擁有桌面），所以這是跨平台的行為差異，不是 mac 版沒做完。
  • 市面上的 macOS 標註工具同樣受這條限制，不是我們的實作選擇造成的。

還沒做的對照實驗：把那個 app 退出全螢幕（保持同一個螢幕、同一個位置）， 再試同一層能不能畫。能畫 → 結論確立；仍不能畫 → 另有原因，要重查。

5.2 偶發的「進入很久」（未重現）

使用者回報進入桌面模式偶爾會卡住、游標轉圈，但無法穩定重現； 而每一次量測（分段計時 + 主執行緒停頓偵測）都顯示進入路徑只花 73~86 ms、12 秒內零停頓（§4.3）。 兩邊都是事實，目前無法對上。

下次遇到時請用 MVB_POC_HITCH=<檔案> 啟動，它會把進入後 12 秒內 >150 ms 的主執行緒停頓寫出來；若那時檔案仍是「no stall」，就表示卡的不是主執行緒 （方向轉去看 window server / Space 切換 / Debug build 的啟動成本）。

5.5 實作時踩到的 macOS 陷阱

都是實際發生過、而且症狀會誤導人的：

症狀真正的原因做法
某個螢幕畫不了（其他螢幕正常） 一個顯示器一層 overlay，但只有一層是 key window。AppKit 預設把「點非 key window 的第一下」吃掉當作 activate，不送進 view view 覆寫 acceptsFirstMouse(for:) 回 true
拖工具列會抖、越拖越飄 用 SwiftUI DragGesture 的 translation 搬 NSWindow：那個座標系跟著視窗一起移動，每幀都在對上一幀剛移動過的基準重新量測 改用 AppKit window.performDrag(with:)（拖標題列那條路），它會在放開時才返回，正好接吸附
浮動工具列有黑色直角外框 視窗陰影是照 window 的矩形畫的，內容是圓角的透明面板 → 陰影露在圓角外 hasShadow = false，陰影交給內容自己畫（floatingSurface()）
進入模式後整個螢幕全黑、退不出全螢幕 對一個處於 native 全螢幕的視窗呼叫 orderOut：它的 Space 還活著但空無一物，綠燈也沒了 全螢幕視窗絕不 orderOut；讓標註層蓋上去即可
popover／面板浮在標註層上 popover 是自己的 window，主視窗 orderOut 帶不走它 走各面板自己的 dismiss 路徑（狀態才會同步），殘留的再 orderOut，且只掃 panel/popover
自測 hook 重複執行、模式被重入 SwiftUI 的 onAppear 對同一個 view 會觸發不只一次 用一次性旗標把 hook 鎖住
環境變數傳不進去；直接跑 binary 連視窗都開不出來 open 啟動的 app 由 launchd 派生，不繼承 shell 環境；而沙箱 app 直接從終端執行會起不了視窗 一律 open -n --env KEY=VALUE …
診斷檔寫不出來，而且沒有任何錯誤 沙箱只能寫自己的容器；寫 /tmp 被擋掉且 try? 吞掉錯誤 寫 ~/Library/Containers/ViewSonic.myViewBoard/Data/ 底下
截圖裡永遠看不到工具列，無法確認它有沒有畫出來 我們刻意把工具列設成 sharingType = .none（不入鏡），螢幕擷取工具也就拍不到 留一個開關（MVB_POC_TOOLBAR_CAPTURABLE=1）能暫時放回鏡頭；或改用 CGWindowList 查它的 frame

6. 正式做的話怎麼切

原型是丟棄式的，正式做建議這樣切（每片都能獨立驗）：

  1. 骨架：進入／離開、單螢幕標註層、標記筆、回白板。這片就能回答「手感對不對」。
  2. 工具組：螢光筆／雷射筆／橡皮擦／清除／Undo-Redo + 每支筆的 brush 狀態。
  3. 工具列：VSDS 化（原型用的是 SF Symbols 佔位）、拖曳吸附、tooltip、i18n。
  4. 穿透與多螢幕：游標工具、每螢幕一層、顯示器熱插拔。
  5. 擷取：三式 + 落到白板；權限被拒的引導文案。
  6. 渲染：換掉 NSBezierPath 逐筆重畫，改 CAShapeLayer／Metal（原型的局部重繪只是止血）。

需求單已開：VB-2247（掛在 VB-1897 Mac Native 底下）， 內含範圍、需要 PM 決策的三件事與驗收條件。 上面這六片的實作票也開在 VB 並連回 VB-2247 ——2026-09-16 起新單一律開 VB，不再開 MT-。

自測用的環境變數

正常使用不要設。open --env 是唯一能把環境變數傳進去的方式—— 直接執行 binary 會讓沙箱 app 起不了視窗（實作時踩過）。

open -n --env MVB_POC_DESKTOP_MODE=1 \
        --env MVB_POC_TIMING=~/Library/Containers/ViewSonic.myViewBoard/Data/t.txt \
        ~/.mvb-dd/poc-desktop-mode/Build/Products/Debug/myViewBoard.app
變數作用
MVB_POC_DESKTOP_MODE=1啟動後自動進入桌面模式
MVB_POC_DESKTOP_DELAY=<秒>自動進入的延遲（預設 1.5；設大一點才量得到「app 完全就緒」的狀態）
MVB_POC_TOOLBAR_CAPTURABLE=1讓工具列可被螢幕擷取（否則截圖永遠拍不到它）
MVB_POC_SELFTEST=<路徑>自動畫兩筆 + 擷取全螢幕並寫檔
MVB_POC_TIMING=<路徑>寫出進入模式的分段耗時
MVB_POC_HITCH=<路徑>進入後監測 12 秒，把 >150 ms 的主執行緒停頓寫出來

寫檔路徑必須在 app 的沙箱容器內：~/Library/Containers/ViewSonic.myViewBoard/Data/。 寫到 /tmp 會被沙箱擋掉而且不會有錯誤訊息（實作時踩過）。
