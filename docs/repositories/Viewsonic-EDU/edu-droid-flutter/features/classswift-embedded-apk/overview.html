2. 背景與目標

融合／內嵌之前的行為（master 現況）：MVB 啟動後從 OTA server 下載 ClassSwift apk：讀 version.json → 下載約 15 MB → 安裝。 第一次開機、網路慢或斷網時 ClassSwift 遲遲裝不起來，使用者點 Quiz Tool 就得等下載完成。

#208 的目標：ClassSwift apk 由 CI 在 build 時內嵌進 MVB assets。MVB 裝好的當下就帶著對應版本的 ClassSwift，啟動後比對版號、背景靜默安裝，全程不需網路。
融合方向已更進一步：CS 以 library 形式編進 MVB，同一 APK、同一 process，連「安裝」這一步都消失（見 findings.html）。

但注意 E9：完全離線的教室（production、無 region 快取）時，region gate 拿不到 toggle 就永遠不開， CS 仍然裝不起來。原本 OTA 版也一樣，不算回歸，但「離線可用」這個賣點實際上被 region gate 擋住。
融合方向下不適用：CS 隨 MVB 一起安裝，region gate 只影響 toggle 是否顯示、不再阻擋可用性。

3.3 Release target 對應 — #208 方案

融合方向下不適用 —— CS 沒有獨立 package name（= MVB 自己）；環境對應改為 build 時依 release target 推導 CS environment，見 findings.html R9。

ReleaseTarget 執行期由版號推導（build number 奇數 = stage、偶數且 minor 奇數 = beta、其餘 production / rollback），CI 埋入的 apk 必須一致（B9 守衛：不符即 Failed(packageMismatch 38)）：

MVB release targetClassSwift flavorpackage name
stageStagcom.viewsonic.classswift.service.stag
betaRccom.viewsonic.classswift.service.rc
production / rollbackProdcom.viewsonic.classswift.service

dev（…service.dev）沒有對應的 ragdoll-cat release flavor，不在內嵌範圍。本地開發用 make fetch-classswift；沒跑過的本地 build 回報 Unavailable、跳過安裝，不會 crash。

4. 決議 D1–D9 #208 脈絡

融合方向下的狀態：D5 仍成立；D1 精神被繼承（不留 OTA fallback，見 findings §6.1）；D2 / D3 / D4 / D6 / D7 / D8 不適用（無安裝流程、無 pin、無 bump workflow）；D9 體積模型改變需重新量測。
#議題決議理由
D1內嵌 apk 與 OTA 下載的關係完全取代，不保留 OTA fallback保留 fallback 等於整套下載程式碼都要留著
D2安裝時機與 UX啟動後背景靜默安裝；dialog 只在使用者於完成前點 CS 時出現不在使用者沒操作時彈系統安裝畫面
D3apk 來源classswift_pin.json 鎖 tag，CI 下載並驗 sha256；apk 不進 repo可重現、換版可 review、避免 repo 膨脹
D4版本 bump 交付方式commit / pr 兩種模式，排程預設 commit日常自動跟版用 commit；風險版本用 pr
D5Beta Program只下載 beta 版 MVB，不再另抓 beta CSbeta MVB 自己就帶著 beta CS
D6與 MDM（MVB_QuizTool）派送並存移除 MDM 派送 → ragdoll-cat#1089兩個版本來源會互相覆蓋
D7解出的 apk 清理時機安裝成功後立即刪；失敗保留供 retry避免 ~15 MB 長期佔用
D8region gate 尚未開啟掛監聽，gate 打開後自動補觸發一次全新裝置首次開機 gate 需等 API
D9CS 的 --split-per-abi接受現況：每個 ABI APK 各含完整 15 MB省體積方案 (a) 要把 MVB build 拆成多次；若日後體積成問題，(a) 效果最好

5. Review 修正摘要 #208 脈絡

以下 bug 全屬 #208 的內嵌安裝機制；融合方向下相關程式路徑不存在，保留作為「若回頭走內嵌方案」的檢查清單。

票面 comment 列 B1–B7，PR 內 review 文件為完整版 B1–B17（另有使用者流程 F1–F10、邊界 E1–E20、競態 R1–R13），全文見 repo-docs clone。接手時特別值得知道的幾條：

#問題若沒修到的後果
B1APK versionName 是 1.6.3-stag 而非 tag 的 1.6.3，原生端嚴格字串比對所有 stage / rc 版被拒裝
B3背景安裝直接 await startSilentInstallApk（實測可能不回傳）coordinator 永遠停在 InProgress、dialog 一直轉圈
B4+B8NotNeeded/Completed 是終端狀態；dialog 又直接套用過時狀態CS 事後被移除時要重開 MVB 才能重裝；B8 是 B4 修正自身的漏洞
B9內嵌 apk 的 packageName 從未與 MVB 期待的 package 比對CI 埋錯 flavor 時每次啟動都解壓 15 MB 並安裝一個永遠 bind 不到的 package
B10+B13retry() 沿用 filePath 不驗檔案存在、不重驗是否仍需安裝無限失敗迴圈 / 對著裝好的 app 看系統安裝畫面
B11bump workflow 沒檢查 .sha256 是否存在缺 checksum 的 release 通過自動 bump，讓所有 MVB build 失敗
B17gating 擋下時不 emit 狀態使用者主動開的 dialog 永遠轉圈且沒有 retry 按鈕
刻意設計、不修改：IFP52_2 連背景 silent install 也排除 —— 非 owner 的 IFP52_2 會在每次開機被 startSilentInstallApk 卡住系統 90 秒；代價是 owner 的 IFP52_2 拿不到「開機就裝好」（F5）。

7. 驗證狀態 — PR #208（Stephen 已完成）

融合方向（PR #210）的驗證記錄見 findings.html §5 / §6.3.2–6.3.7。以下針對 #208 的內嵌 APK 機制，融合方向下不再適用。
  • 全 repo 2789 個測試通過（ClassSwift 相關 76 個）；flutter analyze 改動範圍內無 warning
  • 實際 Gradle build 驗證：ifp / edla 含 15 MB asset，store / open 不含（E6）
  • noCompress 生效：打包後僅多 178 bytes，為 stored 而非 deflate
  • 簽章相容性（E7）：OTA bucket 上的 apk 就是同一個 release asset 改名上傳，覆蓋安裝不會 INSTALL_FAILED_UPDATE_INCOMPATIBLE
  • CI 下載 + sha256 驗證流程實跑通過；所有 workflow YAML 與 shell 語法檢查通過
