ClassSwift 融合進 myViewBoard — 階段報告

0. 一頁摘要

✅ 技術可行性已完全驗證，本地 build 與真機測試通過。 ClassSwift 不再是需要另外安裝的 app —— 它直接編進 myViewBoard，成為同一個 APK 的一部分。 老師點 Quiz Tool 就能用，沒有下載、沒有安裝、沒有「要不要安裝」的詢問、沒有版本不同步。
⚠️ 尚未具備上線條件：CI（自動化建置）尚未改造，目前只能本地 build。 另有 3 項需要產品面決策（見 §5）。
⚠️ 最需要注意的一項：融合後 ClassSwift 不能再單獨更新 —— 任何 ClassSwift 的修正都必須跟著 myViewBoard 一起發版。 而 myViewBoard 目前沒有「最低版本」檢查機制，無法要求舊裝置升級（見 §5.2）。
問題回答
能上線了嗎？不能。CI 未改造（趕上線期間暫緩），需另抓時程
使用者會感覺到什麼？Quiz Tool 秒開、不再有安裝畫面。但升級後首次使用需重新登入一次（見 §2）
APK 會變多大？+11 MB（+3.3%）：340 MB → 351 MB。
對照：現行方案是額外下載安裝約 15 MB 的獨立 app，裝置整體其實更省
需要上層決策嗎？是，4 項：Firebase 數據歸屬、失去 ClassSwift 獨立熱修能力、是否永久放棄獨立交付、兩 repo 合併時序
原本 Stephen 的方案怎麼辦？PR #208（內嵌 APK）轉為備案保留，不作廢（見 §7）

1. 這是什麼改變

現在（線上版本）融合後
ClassSwift 的身分獨立的 app，要另外安裝myViewBoard 的一部分，同一個 APK
怎麼到使用者手上myViewBoard 啟動後連網下載約 15 MB → 安裝不需要 —— 裝 myViewBoard 就有了
版本同步兩個 app 各自的版本，可能不相容永遠同版（同一個 artifact）
使用者是否需要做決定部分情境會跳出系統安裝畫面要求確認完全不需要

技術上的做法：ClassSwift 的原始碼以「函式庫」形式編進 myViewBoard，兩個專案的程式碼仍分別留在各自的 repo、各自開發，只是最後打包成一個 APK。

1.1 APK 體積

版本APK 大小說明
目前線上（edla, release）340 MB不含 ClassSwift，使用者另外下載約 15 MB 安裝
融合版（edla, release）351 MB已含完整 ClassSwift
差異+11 MB（+3.3%）比獨立安裝的 15 MB 更小 —— 兩者共用的函式庫不再重複打包

量測條件：同一台機器、同版號（3.11.0+30110002）、edla flavor、release build。 Play 商店版（store / open）不含 ClassSwift，體積不變。

2. 對使用者的影響

正面：

  • Quiz Tool 點下去即用，無等待、無安裝畫面、無網路需求（就本機而言）
  • 不會再出現「ClassSwift 版本過舊 / 不相容」這類問題
  • 非 owner 帳號、特定機型（IFP52_2）過去會卡在安裝失敗，這些情境消失

⚠️ 需要寫進 release note 的一項：

升級到融合版後，ClassSwift 的首次使用需要重新登入一次。 原因：融合後 ClassSwift 的資料存放位置改變（從獨立 app 的空間移到 myViewBoard 內）， 舊資料不會自動搬移。這是一次性的，之後正常。

4. ⚠️ 還沒做的（上線前必辦）

項目影響備註
CI（自動化建置）改造 目前只能本地 build，CI 上跑不起來 —— 所有 Android 的自動建置流程都會失敗 因趕上線暫緩。需要讓建置機器能同時取得兩個 repo 的程式碼，工作量與時程需另估
正式版（release）真機測試 目前 release 版只驗證「能打包成功」，沒有實際裝到機器上跑過 正式版會做程式碼壓縮最佳化，行為可能與測試版不同，需實機驗證
投屏功能迴歸測試 融合過程動到投屏用的連線元件（非 ClassSwift 功能，是被波及） 已用程式碼層級比對確認邏輯等價，但需 QA 實際測投屏斷線 / 重連
依賴函式庫的全面盤查 兩個 app 合併後共用同一套函式庫版本，可能有隱性衝突 已知並修復一例（Amplitude）。release 打包已通過，代表無編譯期問題，但執行期仍需系統性檢查

5. 🔴 需要決策 / 知會

5.1 Firebase 數據歸屬（需產品 / 數據面決策）

融合後，ClassSwift 的當機記錄（Crashlytics）與 Firebase Analytics 事件會進入 myViewBoard 的 Firebase 專案，而不是 ClassSwift 原本的專案。
  • 後果：ClassSwift 團隊在自己的 Firebase 後台看不到融合版的當機資料
  • 技術限制：一個 app 只能有一個主要的 Firebase 專案，這是平台限制、無法兩邊都送
  • 需要決定：接受合併（ClassSwift 團隊改看 myViewBoard 的後台），或投入額外工作做分流
  • ✅ Amplitude 不在此列 —— 兩邊本來就共用同一個 Amplitude 專案，且已做技術隔離，數據不受影響

5.2 🔺 失去 ClassSwift 的獨立熱修能力 —— 是否要補「最低版本」機制（需產品 + 後端共同決策）

這是融合最實質的代價，建議優先討論。
現在融合後
ClassSwift 出問題要修 ClassSwift 自己有更新機制 —— myViewBoard 啟動時會檢查並自動更新到最新版，不需要發 myViewBoard 必須發一版完整的 myViewBoard，走完整的發版流程與時程
後端做了不相容的改動 推新的 ClassSwift，裝置下次啟動就跟上 裝置停在舊版就是舊版，沒有補救手段

實際查證結果：

  • myViewBoard 目前完全沒有「最低版本」或「強制更新」機制 —— 沒有任何方式可以告訴舊版裝置「你必須升級」
  • 兩邊現有的機制都只是「更新到最新版」，不是「低於某版就擋下來」，性質不同
  • 融合版中 ClassSwift 的自我更新機制已被關閉（否則它會去下載獨立版並覆蓋自己）
  • → 結論：融合移除了唯一的快速修正路徑，而目前沒有東西接手

需要決定（建議三選一）：

選項成本適用情境
A. 接受現況，不做 無 若 ClassSwift 功能已穩定、後端承諾長期相容舊版
B. 在 myViewBoard 加最低版本檢查（由後端下發，過舊時提示或阻擋） 中，且需後端配合 推薦 —— 這是產品長期都會需要的能力，不只為了本案
C. 保留 ClassSwift 的獨立更新作為緊急後路 高 不建議 —— 等於同時維護兩套機制，融合的好處被抵消
需要後端團隊知道的：融合後，ClassSwift 後端若要做不相容的改動， 必須維持對舊版的相容更久，因為未升級的裝置無法再被單獨修正。 這是跨團隊的影響，建議在決策時一併告知。

補充：裝置端（EDLA）的 myViewBoard 實際更新速度與涵蓋率，會直接決定這個風險的大小 —— 建議向負責發版的同仁確認「一版 myViewBoard 推到大多數裝置需要多久」，再據以判斷要選 A 還是 B。

5.3 ClassSwift 是否永久放棄「獨立交付」（不可逆，需書面確認）

  • 目前口頭確認：ClassSwift 只有 myViewBoard 一個使用者，過去曾考慮讓 Finch 也能接，現已無此需求
  • 建議取得書面確認 —— 融合上線後 ClassSwift 就不再有獨立的發版流程，日後若有其他產品想接，成本很高
相關的第二件事：既有裝置上殘留的獨立版 ClassSwift 要不要清掉？ 已技術查證不清也不會出問題（它沒有圖示、不會被啟動，等同閒置）。 建議不清 —— 留著等於保有「萬一要退回非融合版」的現成退路，代價是永久佔用約 15 MB。 但這該是明確決定；目前僅有口頭表示「standalone 用戶不管」而無書面紀錄，建議補進票裡。

5.4 兩個 repo 的合併時序（需 RD 主管 / release 協調）

  • 本案同時牽涉兩個 repo：myViewBoard（主要改動）與 ClassSwift（小幅必要改動）
  • ClassSwift 端的改動很小且不影響其獨立版行為，但兩邊必須一起合併，否則 myViewBoard 會建置失敗
  • 需要與 ClassSwift 團隊協調 review 與合併時程

5.5 原方案（PR #208）的定位 —— 需對內說明

  • Stephen 先前完成的「內嵌 APK」方案已相當完整，若採用融合方向，該方案的機制不再需要
  • 建議保留為備案（若融合方向在組織面受阻，它是現成的次佳解），並在對內溝通時說明清楚，避免造成「工作白做」的誤解

6. QA 需要知道的

  • 首次啟動需重新登入（見 §2）—— 這是預期行為，不是 bug
  • 投屏功能要迴歸：正常投屏、中途斷網是否出現失敗提示（而非一直轉圈）、恢復後能否自動重連
  • 正式版（release）需重點測試：目前只驗證測試版，正式版的程式碼壓縮可能造成差異
  • 不需要再測「ClassSwift 安裝流程」：該流程已不存在
  • 裝置上會殘留舊的獨立版 ClassSwift：已查證不會與融合版衝突（它沒有圖示、不會被啟動）， 殘留是預期的，不是安裝失敗。若看到兩個 ClassSwift 相關套件，屬正常
  • 測試環境對應：測試版（stage）連測試站、beta 版連 RC 站、正式版連正式站 —— 已自動對應，但值得抽驗

7. 風險與退路

風險評估
技術可行性低 已完整驗證，含最複雜的「結束課堂」流程（曾是最大技術障礙，已解決並通過四種情境的真機測試）
時程中 主要卡在 CI 改造，工作量明確但需要時間；其餘為驗證與決策
組織面中 兩個團隊的 repo 需協調合併與後續開發節奏
退路有 若融合方向受阻，PR #208（內嵌 APK）可直接接手；技術上也可改為「ClassSwift 在自己的程序執行」的折衷版本，保留單一 APK 的好處
結論建議：技術面已證明可行且成本低於預期，建議先取得 §5 的三項決策， 再安排 CI 改造與 QA 完整迴歸的時程。在此之前，可先用本地建置的版本讓 QA 提前測試功能面。
