1. 目標

  1. 老師想用 Quiz Tool 時就能馬上用 —— 點下去零等待
  2. 使用者不經歷下載、更新、檢查、安裝等流程 —— 不可避免的話盡量縮短、盡量隱形
  3. 減少使用者的抉擇 —— 不要跳「要不要安裝」讓使用者有機會點「不要」；理想是背景自動處理
  4. 前提：ClassSwift（Quiz Tool）一定要處於最新版 —— 最好的狀態是「在背景永遠維持最新版」 已移除 2026-07-31 不要求最新版（永久）；最小版本限制目前沒有（暫時現狀，未來可能設計）；相容性由後端處理

3. 主要差距

Gap 1 — 版本新鮮度與 MVB 耦合 已解除（2026-07-31 前提移除）

✅ 不再是差距：「一定要最新版」前提移除後，CS 跟著 MVB release 節奏更新即可接受， 版本相容由後端負責 —— 等同直接採納下方方向 (ii)，且不需要新鮮度 SLA。 以下分析保留作為記錄（若日後前提翻回來，這段還是成立）。

D1 決議「完全取代、不保留 OTA fallback」之後，裝置上的 CS 只會在 MVB 自己更新時跟著換：

flowchart LR
  CSREL["CS 出新版
(ragdoll-cat release)"] --> BUMP["classswift-bump
更新 pin（每日）"]
  BUMP --> WAIT1["等 MVB 下一次
release build"]
  WAIT1 --> WAIT2["等裝置 OTA
更新 MVB"]
  WAIT2 --> INSTALL["重啟後才裝上新 CS"]
新 CS 到裝置的唯一路徑 —— 每一段都是等待
  • 舊 OTA 流程反而是「每次啟動就檢查、抓得到最新版」—— 內嵌方案用新鮮度換首次可用性
  • 若 CS 出了 hotfix 而 MVB 沒有 release 排程，沒有任何管道把新 CS 推上裝置（MDM 派送也在 D6 被移除）
  • E14：同一個 tag 重新發佈也推不動（pin 沒變不重抓、版號相同不更新）

當時列過的方向（記錄用）：(i) 內嵌保底 + 背景 OTA 混合式（推翻 D1）、 (ii) 接受「最新 = 跟著 MVB release 的最新」、(iii) CS hotfix 時主動觸發 MVB release。 2026-07-31 前提移除後等同採納 (ii)，且不需要逼近任何新鮮度目標。

Gap 2 — 殘留的使用者抉擇路徑

路徑情境使用者看到什麼
F4非 owner 帳號，系統拒絕 silent install點 Quiz Tool → 退回 PackageInstaller → 要按「安裝」
F5IFP52_2（機型排除背景 silent install，避免卡系統 90 秒）背景必失敗 → 同 F4，每次更新都要人工按
F6使用者在系統安裝畫面按取消Error 34 + retry —— 正是「他點了不要」的情境

要消滅這三條，關鍵在 silent install 的權限面：owner / device owner 權限怎麼配置、 IFP52_2 的系統問題能否從 firmware 端解。這不是 Flutter 端能單獨解掉的。

Gap 3 — Region gate 擋住「馬上用」（E9）

完全離線的教室（production、無 region 快取）時 gate 永遠不開，CS 裝不起來，點 Quiz Tool 完全不可用。 內嵌方案的「離線可用」賣點實際上被 region gate 抵銷。舊流程也一樣（不算回歸），但以北極星目標來看是個缺口。

Gap 4 — 開機後的競態窗口

背景安裝完成前點 Quiz Tool 仍會看到 loading（F3）。內嵌方案已把窗口從「下載 15 MB」縮成「本地解壓 + 安裝」（秒級）， 剩餘窗口可能只能靠提早觸發時機（目前掛在 onITAdminSettingsUpdated）再壓縮。

4. 長期選項發想（未定案，記錄用）

把 ClassSwift 整個融合進 MVBF（單一 APK）

Jay 2026-07-31 發想。ragdoll-cat（ClassSwift_Service.apk）是純 Android 原生 Kotlin app（Views XML + Retrofit + SocketIO）， MVB 是 Flutter app —— Flutter 的 android module 本來就能承載原生 code，技術上不是「Flutter 混 native 行不行」的問題，而是「吞下一整個 app」的工程與組織問題。

面向評估
對北極星目標 完勝 唯一能把「安裝 / 更新 / 版本同步」這整類問題連根拔掉的方向：F4/F5/F6 三條使用者抉擇路徑消失、silent install 權限問題消失、CS↔MVB 版本相容矩陣消失（單一 artifact 永遠同步）、#205 的跨 app token 傳遞變成 in-process 呼叫
技術難度 POC 後下修為中等 大工程但可行 —— 2026-07-31 POC 實證：wrapper module + sourceSets 指向手法讓 CS 零改動編進 MVB，manifest / 資源 / codegen 全數過關，整包 assemble 成功。真正的工程主體是 MVB 端 CS 整合層改為 in-process（見 findings.html R2）
執行期風險 失去程序隔離 現在 CS crash 不影響 MVB；合併後單一程序記憶體水位變高（IFP 是低 RAM 裝置）。中間解：CS 元件跑獨立 :process —— 保住單一 APK 交付，又保留部分隔離
組織面 最硬的部分 ragdoll-cat 是 CS 團隊的 repo、獨立 release 節奏；合併等於兩team 的 CI / review / release train 綁在一起（Conway's law）。且需先確認 ClassSwift_Service.apk 是否只有 MVB 一個消費者（若還有 standalone / 其他產品用途，合併等於分岔或砍掉它）→ Q11
ROI 時點 「後端處理相容」拍板後，現狀（內嵌 APK）的痛已大幅降低 —— 合併的相對效益變小。適合當長期方向存查，等內嵌方案上線後看剩餘痛點再評估

5. 對後續研究的意義

  • 評估任何手段時，用剩下的 3 個 gap 檢核：首次可用性、零抉擇、離線（新鮮度已因前提移除而出局）
  • Gap 1 是方向性問題，需要先對齊「最新版」定義與 SLA —— 已解除（2026-07-31）；後端如何處理版本相容成為新的追蹤點（Q9：哪個後端？相容到多舊？）， 以及最小版本機制的未來設計（Q10：「無最小版本限制」只是暫時，一直沒有的話後端相容範圍會無限增長）
  • 剩餘重點是 Gap 2（零抉擇）：偏權限 / firmware 面，可能要拉裝置端的人
  • 相關調查問題已列入 investigation.md（Q2、Q7–Q10；Q3 / Q5 / Q6 已因決策關閉）
