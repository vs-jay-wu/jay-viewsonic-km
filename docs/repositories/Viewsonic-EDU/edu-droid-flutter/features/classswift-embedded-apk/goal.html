1. 目標

  1. 老師想用 Quiz Tool 時就能馬上用 —— 點下去零等待
  2. 使用者不經歷下載、更新、檢查、安裝等流程 —— 不可避免的話盡量縮短、盡量隱形
  3. 減少使用者的抉擇 —— 不要跳「要不要安裝」讓使用者有機會點「不要」；理想是背景自動處理
  4. 前提：ClassSwift（Quiz Tool）一定要處於最新版 —— 最好的狀態是「在背景永遠維持最新版」 已移除 2026-07-31 不要求最新版（永久）；最小版本限制目前沒有（暫時現狀，未來可能設計）；相容性由後端處理

3. 主要差距

Gap 1 — 版本新鮮度與 MVB 耦合 已解除（2026-07-31 前提移除）

✅ 不再是差距：「一定要最新版」前提移除後，CS 跟著 MVB release 節奏更新即可接受， 版本相容由後端負責 —— 等同直接採納下方方向 (ii)，且不需要新鮮度 SLA。 以下分析保留作為記錄（若日後前提翻回來，這段還是成立）。

D1 決議「完全取代、不保留 OTA fallback」之後，裝置上的 CS 只會在 MVB 自己更新時跟著換：

flowchart LR
  CSREL["CS 出新版
(ragdoll-cat release)"] --> BUMP["classswift-bump
更新 pin（每日）"]
  BUMP --> WAIT1["等 MVB 下一次
release build"]
  WAIT1 --> WAIT2["等裝置 OTA
更新 MVB"]
  WAIT2 --> INSTALL["重啟後才裝上新 CS"]
新 CS 到裝置的唯一路徑 —— 每一段都是等待
  • 舊 OTA 流程反而是「每次啟動就檢查、抓得到最新版」—— 內嵌方案用新鮮度換首次可用性
  • 若 CS 出了 hotfix 而 MVB 沒有 release 排程，沒有任何管道把新 CS 推上裝置（MDM 派送也在 D6 被移除）
  • E14：同一個 tag 重新發佈也推不動（pin 沒變不重抓、版號相同不更新）

當時列過的方向（記錄用）：(i) 內嵌保底 + 背景 OTA 混合式（推翻 D1）、 (ii) 接受「最新 = 跟著 MVB release 的最新」、(iii) CS hotfix 時主動觸發 MVB release。 2026-07-31 前提移除後等同採納 (ii)，且不需要逼近任何新鮮度目標。

Gap 2 — 殘留的使用者抉擇路徑 融合後消失（2026-08-04）

融合方向下不再存在 —— F4/F5/F6 都源自安裝流程，融合後沒有安裝流程，三條路徑一併消失。以下保留為 PR #208 過渡期記錄。

MVB 自身的安裝問題（2026-08-04 更新）：MVB 自己更新仍需要安裝能力， 此部分聽說已定案由 Manager 處理（口頭，未書面確認）——「使用者要按安裝」的殘餘面 因此收斂到單一位置：beta_dialog_bloc 的 Beta Program 安裝 （目前借用 ClassSwiftInstaller.install(silentInstall: true)，非 Owner 帳號會失敗、 退回系統安裝畫面）。從「CS 每次更新都可能要人工按」變成「只有加入 Beta Program 時可能要按」， 是可接受的限制。
路徑情境使用者看到什麼
F4非 owner 帳號，系統拒絕 silent install點 Quiz Tool → 退回 PackageInstaller → 要按「安裝」
F5IFP52_2（機型排除背景 silent install，避免卡系統 90 秒）背景必失敗 → 同 F4，每次更新都要人工按
F6使用者在系統安裝畫面按取消Error 34 + retry —— 正是「他點了不要」的情境

（#208 過渡期適用）要消滅這三條，關鍵在 silent install 的權限面：owner / device owner 權限怎麼配置、 IFP52_2 的系統問題能否從 firmware 端解。這不是 Flutter 端能單獨解掉的。 融合方案繞過整個權限面（無 VSSystemManager.installApp 依賴）；investigation 的 Q7 / Q12 已標註融合方向下不適用。

Gap 3 — Region gate 擋住「馬上用」（E9）融合後性質改變

完全離線的教室（production、無 region 快取）時 gate 永遠不開。#208 下的症狀是「CS 裝不起來」；融合後 CS 已內建、不需安裝，但 MVB 的 region gate（RegionGateService.isEnabled(quizTool)）仍決定 CS toggle 是否顯示 —— 問題從「裝不起來」變成「看不到入口」，離線缺口本身仍在（Q2）。舊流程也一樣（不算回歸），但以北極星目標來看是個缺口。

Gap 4 — 開機後的競態窗口 融合後消失（2026-08-04）

融合方向下窗口歸零 —— 沒有背景安裝，就沒有「裝完前點下去」的窗口；F3 與 onITAdminSettingsUpdated 觸發點壓縮都不再適用（Q8 已標註）。以下為 #208 過渡期記錄。

背景安裝完成前點 Quiz Tool 仍會看到 loading（F3）。內嵌方案已把窗口從「下載 15 MB」縮成「本地解壓 + 安裝」（秒級）， 剩餘窗口可能只能靠提早觸發時機（目前掛在 onITAdminSettingsUpdated）再壓縮。

4. 融合方案：把 ClassSwift 整個融合進 MVBF（單一 APK）已實作 · PR #210（2026-08-04）

Jay 2026-07-31 提出，2026-08-03/04 完成實作與真機驗證，PR #210 已開 （mvbf Jay/VSFT-9785-classswift-fusion + ragdoll-cat jay/feature/VSFT-9785-app-exit-seam）。 完整實測見 findings.html §6.3.1–6.3.7。 ragdoll-cat（ClassSwift_Service.apk）是純 Android 原生 Kotlin app（Views XML + Retrofit + SocketIO）， MVB 是 Flutter app —— Flutter 的 android module 本來就能承載原生 code， 工程面已由 PR #210 證明可做（wrapper module + quit seam + Koin 重建），剩下的主要是組織面。

面向評估
對北極星目標 ✅ 完勝（已驗證） 已實測達成：把「安裝 / 更新 / 版本同步」這整類問題連根拔掉 —— F4/F5/F6 三條使用者抉擇路徑消失、silent install 權限問題消失、CS↔MVB 版本相容矩陣消失（單一 artifact 永遠同步）；#205 的跨 app token 傳遞可進一步改為 in-process 呼叫（#205 已先合入 master，融合分支基於其上）
技術難度 ✅ 已實作並真機驗證（2026-08-03） 2026-07-31 POC 證明可編（wrapper module + sourceSets），2026-08-03 完成實作：quit seam（ragdoll-cat 僅 4 檔）、quit 時整鍋重建 Koin 容器、Amplitude carry-over；guest / 記名 / 帳號切換 / 派題中斷四類情境真機全過（findings.html §6.3.1–6.3.7）。原估的「40 個呼叫點」成本被證明高估。剩餘工程主體：R2 正式重寫、R5 flavor 隔離、R10 依賴排查、R14 CI 改造
執行期風險 失去程序隔離 現在 CS crash 不影響 MVB；合併後單一程序記憶體水位變高（IFP 是低 RAM 裝置）。獨立 :process 已降為備援 —— quit 語意問題已由 quit seam + Koin 重建解決（findings.html §6.3.4 決策記錄），是否走 :process 純屬架構取捨。記憶體：8 輪 quit 循環 TOTAL PSS 持平、無洩漏（§6.3.5），長時間高負載與 release 包水位未量（R8）

ROI 時點 2026-08-04 更新：已不等 #208 上線 —— 融合在 2026-08-03 完成實作與真機驗證、PR #210 已開，實作成本遠低於原估（ragdoll-cat 僅 4 檔 seam）。#208 內嵌方案定位轉為過渡 / 備援；ROI 判斷點從「效益是否夠大」移到「組織面（Q11 + repo 策略）是否放行」。

5. 對後續研究的意義

  • 融合方向（PR #210）下只剩 1 個 gap：離線（Gap 3，性質已從「裝不起來」變成「region gate 不開就看不到 toggle」）—— 首次可用性、零抉擇皆已由融合達成，新鮮度已因前提移除出局。若要評估 #208 過渡方案，才回頭用 3 個 gap 檢核
  • Gap 1 是方向性問題，需要先對齊「最新版」定義與 SLA —— 已解除（2026-07-31）；後端如何處理版本相容成為新的追蹤點（Q9：哪個後端？相容到多舊？）， 以及最小版本機制的未來設計（Q10：「無最小版本限制」只是暫時，一直沒有的話後端相容範圍會無限增長）
  • 剩餘重點改為 Gap 3（離線 region gate，Q2）與組織面 Q11；Gap 2 的權限 / firmware 路線（Q7 / Q12）僅在 #208 過渡期適用，融合方向下不需拉裝置端的人
  • 相關調查問題見 investigation.html：融合方向下仍有效 —— Q2、Q9 / Q10、Q11（融合定案前必答）；僅 #208 過渡期適用 —— Q7 / Q8 / Q12；已因決策關閉 —— Q3 / Q5 / Q6
  • 融合的完整實測記錄見 findings.html §6.3.1–6.3.7 與 §6.5（repo 策略：git submodule）
