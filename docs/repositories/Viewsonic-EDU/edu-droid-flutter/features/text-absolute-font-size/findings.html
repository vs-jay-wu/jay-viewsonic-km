1. 結論 TL;DR

兩個缺陷疊加，都與「canvas zoom 烤進 annotation matrix」的機制有關：

D1 存檔端 — 資料損毀
text_annotation.dart:1089 · TextAnnotation.toJson
toJson 用預設整數化的 normalizedClone() 把 annotation matrix 的 scale 烤進字級： getNextLargerNumber(json_size × matrix_scale) → round → floor 到偶數 → clamp 到 [10,130]。 超過 130 的 scaled 值被 clamp 是最大災難（159.45 → 130，直接損失 18.5%）。
D2 開檔端 — 幽靈 zoom
olf_reader.dart:320
把 page matrix 的 scale（＝存檔時的 canvas zoom）還原給 infiniteCanvasScale， 卻不烤回任何 annotation matrix（pageSetMatrix 只被讀 scale，從未 apply）。 開檔後畫面實際以 100% 渲染、zoom 標籤卻顯示 122.66%。 WIP 的 bridge 相信這個標籤去除法 → 數字漂移。

3. 驗證方法（全程未改程式碼）

  1. adb run-as 拉出 app cache 的 OLF → 解包 content.json 檢查實際存值。
  2. VM Service 對執行中 debug app 求值（vm_eval.dart，scratchpad 可重用）：
    • olfRatio=2.0、fileToScreenScale=1.0、 infiniteCanvasScale=1.2265710829939889、dpr=2.0
    • 畫布 annotation 實際 jsonList size 與 matrix scale（開檔後 = 整數 + m0=1.0）

  3. 靜態追碼：pinch zoom 把 scale 烤進所有 annotation matrix （infinite_canvas.dart 的 _concatenatingTransformByElement）。

4. 關鍵定性

  • 存檔後檔案裡的 font-size 是「烤過 zoom 的視覺尺寸」（display × zoom）， page matrix 另存 zoom。今天的 loader 不重烤 → 視覺大小大致不變（58 vs 58.88 px）， 但「使用者當初挑的數字」已經永久遺失（48 變 58）。
  • D1 在 WIP 之前就存在（getNextLargerNumber 的 clamp/floor 一直都在 toJson 裡），但舊 toolbar 直接顯示 quill 原值，掩蓋了問題；WIP 的 bridge 讓它可見。
  • WIP 在編輯器開啟端改用 normalizedClone(convertToIntegerFontSize: false) 保留精度， 但存檔端 toJson 仍走整數化預設 —— 這正是先前單元測試 gap 分析點名的 「OLF 序列化」風險成真。

結論 1：mvbW 已經把 zoom 與 resize 分乾淨了，mvbf 才是異類

行為mvbW 落到哪證據

  • (a) matrix 會縮字形 —— 讀檔保留的 matrix 直接成為 RenderTransform （TextEdit.cs:757），XAML 的 RenderTransform 會縮整個 visual tree。
  • (b) 換行寬度在 content space —— TextEdit.cs:725 的 local Width 是 RenderTransform 之前 的值（讀檔時 x/y 有 ÷zoom，width 沒有），斷行算完才整個被 matrix 縮放。

TextEditService.cs:33：FONT_SIZE_PIXEL_POINT_RATIO = (16*20)/15， 註解寫明 Pixel : Point = 20 : 15；字級清單為 FontSizeHelper.GetFontSizes(10, 130, 2) 的 pt 域； 吸附是 FontSizeList.OrderBy(x => Math.Abs(x - inFontSize)).First() （TextEditControlViewModel.cs:1093，硬取最近，無上下限保護）。

安全上限是確定值：mvbW 天花板 130 pt = 173.33 px（檔案域）。 以目前 mvbf 存檔乘 devicePixelRatio 的寫法，dpr=2 的機器上 display 超過 86.67 存出去就進入 mvbW 的破壞區 —— 而且這條線隨裝置 dpr 浮動。 改成固定 ×4/3 後檔案域 = mvbW px 域，兩邊天花板才會對齊在 130。

結論 4：對 mvbf 修法的影響（收回「全部走 matrix」的提案）

「所有放大都走 matrix、stored 永遠 10~130」這個提案要收回。 (a) 保證它畫得出來，但 mvbW 的 resize 會廢掉：font=130 + matrix=2 的文字在 mvbW 拉大 1.2 倍時， 算式為 130×1.2=156 → 吸附回 130、matrix 不動 → 拉了等於沒拉。 不毀資料，但行為壞掉。
收斂方向：mvbf 照抄 mvbW 的分工，不要發明第三種模型。
  • canvas zoom → 只動 matrix，永遠不進 stored（＝本票 VSFT-6964 的原始 bug）
  • lasso resize → 改 font size（與 mvbW 一致，也與 PPT 直覺一致）
  • 編輯器那層用 TextScaler 取代烤值 —— 解的是「編輯器不在 canvas transform 底下」，與跨平台模型無關
好處：不動檔案格式、不需重正規化、不需要 model 版本標記，上面 padding 加法常數的坑也自動閃掉。
⚠️ 上面這條「lasso resize → 改 font size」已於 2026-08-14 推翻（查了 mvbf 端才發現 mvbf 的 resize 本來就走 matrix， 改成動 font size 是重寫整條路）。最終定案見 §9。 本節其餘結論（(a)(b) 成立、單位域驗算、破壞觸發條件）仍然有效。

獨立於本票的既有 bug：存檔乘 devicePixelRatio 導致同一份文件在不同機器存出的數字不同 （安全上限也跟著浮動）。改固定 ×4/3 需要格式版本標記來區分新舊檔，屬另一張單的範圍。

9. mvbf 端查證與方向定案（2026-08-14）

結論 1：mvbf 的 resize 走 matrix —— 與 mvbW 完全相反

transformable.dart:29-50 的 scaleByPivot / scaleXYByPivot 直接對 annotation 的 transform 做 ..scale(...)，字級一個字都沒動。

mvbWmvbf
canvas zoommatrixmatrix
lasso resizefont size（matrix 不動）matrix（font size 不動）
「烤」的時機無（各管各的）normalizedClone —— 開編輯器 / 存檔時把 matrix 灌進 font size

toolbar 之所以在 lasso 2x 後顯示 40，是因為 normalizedClone （text_annotation.dart:252-363）把 matrix scale 乘進每個 span 的 size， 再把 matrix scale 設回 1（m.scale(1.0/scale, 1.0/scale)）。呼叫點共 6 處：

  • text_editor.dart:153（開編輯器）· text_annotation.dart:1084（toJson）
  • adorning_text_options.dart:108 · element_helper.dart:276 / 372
  • popquiz_view_v2.dart:168 · sticky_note_text.dart:149
定案：mvbf 的 resize 模型本來就是對的，不要改。 要拔的是 normalizedClone 這根釘子（把 matrix 烤進 size 的動作）， 不是 resize 本身。text 若改成動 font size，會與 shape / image（都走 matrix）行為分岔。
順帶更正：getNextLargerNumber 上方註解寫「字體大小最小10最大480」是錯的， 實際 MAX_SIZE = 130（text_annotation.dart:134）。

結論 3：不動 mvbW 也能達成目標 —— 存檔正規化

槓桿：「視覺大小 = font-size × matrix scale」這條算式兩平台一致（§8 已證）， 所以同一個視覺結果有無限多組 (font, matrix) 拆法 —— 我們可以自由挑一組落在 mvbW 安全區內的。

做法：存檔時把 font-size 正規化到 ≤ mvbW 天花板（130 pt = 173.33 px），超出的倍率丟進 matrix。

視覺 260px 的字檔案內容mvbW 讀到結果
今天font=260, matrix=1195 pt一被輸入 / resize 就毀
正規化後font=173, matrix=1.5130 pt永遠在合法清單內

為什麼不需要動 mvbW、也不需要格式版本標記：

  • 語意沒變：沒有新欄位、沒改單位，只是換一組等價的 (font, matrix)。 任何 reader（mvbW / 舊版 mvbf / PPTX parser）用同一條算式還原成同樣視覺 → 舊 reader 天然正確。 這正是它比「改單位域 ×4/3」優越之處（後者一定要版本標記）。
  • 斷行不受影響：mvbW 的 wrap 寬度 = Width − padding = 檔案 width （TextEdit.cs:725 加上去、排版時再扣掉），與 matrix 無關。 只有外框 padding 與 -2/+8 常數會跟著 k 倍放大 → 純外框位移，不重排文字。
  • 繞開破壞行為：mvbW 的吸附發生在 pt 域，而我們保證餵給它的 pt 永遠在 10~130 射程內。
代價嚴重度說明
mvbW 對 >130pt 的字 resize 會「拉了沒反應」 可接受 它算 130×1.2=156 → 吸附回 130、matrix 不動 → 無效操作但非破壞性，優於今天的靜默改小；一般大小的文字完全照舊
舊版 mvbf 開新檔並進編輯器會縮一半 無解，需權衡 被它自己的 normalizedClone 烤回 260 再 clamp 成 130。純檢視不會。兩個 knob 只能滿足一邊 —— 選對 mvbW 安全，因為舊版 mvbf 會隨版本更新自然消失，mvbW 的碼我們動不了

關鍵取捨：編輯器同時活在兩個域

編輯框寬度留在「視覺域」，字級走「stored 域」—— 這是刻意的，不是疏漏。
  • TextScaler 只放大 glyph，不會放大寬度約束。
  • 所以字被放大 k 倍時，編輯框也必須是 k 倍寬，斷行點才會跟畫布上一致 —— 即 normalizedClone(bakeMatrixScale: true) 給的 width × scale。
  • commit 時再 _textFieldWidth / _editorScale 除回 stored 域寫進 annotation。
這也是為什麼 _initNormalizedTextAnno（視覺域，供 geometry）與 _initStoredTextAnno（stored 域，供 Quill 與 diff 比較）兩份並存。 比較「有沒有改過」時務必用 stored 域那份，否則域不同會永遠判定為 changed。

11. 三題查證（2026-08-14）

結論 1：master 不會有小數 —— 小數是 WIP 引進的

git show master 確認：toJson（:1075）與開編輯器 （text_editor.dart:139）都用整數化的 normalizedClone()（預設 convertToIntegerFontSize: true）。

所以 master 的字級永遠是 10~130 的偶數整數，lasso 拉出小數倍率也一樣 —— 但這正是本票的 bug：每次「烤」都 round → floor 到偶數 → clamp， lasso 1.37 倍時 20×1.37=27.4 被 floor 成 26（字真的縮小 5%），超過 130 直接 clamp。

master 是用「每次烤都掉精度」換到乾淨的偶數格線。 我們要的是保留那條格線、但不要破壞性 —— 即「偶數吸附 + 差額進 matrix」。

結論 2：Q1 不但不撞 D2，反而修好它（先前判斷已推翻）

  • olf_reader.dart:316-320：pageSetMatrix 只被讀 scale 塞給 infiniteCanvasScale，從未套用到任何 element。
  • infiniteCanvasScale 不是渲染 transform，只是狀態/標籤 —— 真正的縮放是 infinite_canvas.dart:294-298 用 scaleByPivot 把 deltaScale 烤進 element matrix。

結論 3：sticky note 是「matrix 救不回來」的反例

方向位置行為
存stickynote_annotation.dart:223font-size = getTextAnnotationFontSize() × ratio

sticky note 的字級是純量，內層 text annotation 的 matrix scale 存檔時會被無聲丟掉。
  • 無回歸 第 1、2 項不影響 sticky note —— 它走自己的序列化路徑，不經過 TextAnnotation.toJson。此行為 master 就有。
  • 但 它證明「倍率放 matrix 一定救得回來」不是全域成立。
  • 目前安全是碰巧：內層 text 被 sticky_note_text.dart:159 從 pageData.annotations 移除，pinch zoom 不會烤進它的 matrix，內層 matrix 實質恆為 identity。需要一條測試把這個前提釘住。

結論 4：resize 後重開顯示不會變（乘積守恆）

display 是每次重算、不是存起來的： display = getNextLargerNumber(stored × elementScale ÷ zoom)。 以 lasso 1.37 倍（zoom=1、stored=20）為例：

時機storedelementScale乘積toolbar
剛 lasso 完201.3727.426
關掉再開（同 session）201.3727.426
存檔重開（現行）27.4127.426
存檔重開（偶數吸附後）261.0538…27.426
只要乘積被保住，顯示就穩定 —— 四種拆法給同一個數字。 這正是「差額必須進 matrix」而不能直接截斷的原因：截斷會改變乘積。 master 就是截斷（27.4 floor 成 26 且 matrix 歸 1 → 字真的縮小 5%）。 浮點誤差也不咬人：getNextLargerNumber 先 round() 再取最大偶數。
既有怪癖（master 也有，且更嚴重）：toolbar 顯示 26、實際視覺 27.4。 此時去 dropdown 點一下「26」，stored 被重寫成 26/1.37 = 18.98，視覺真的縮成 26 —— 「選了你本來就看到的數字，字卻變小」。這是 floor-to-even 顯示的固有副作用，非本次引入； 要根治得讓 display 不 floor（spec 決策，未動）。
