## Description

1. 在縮放等級 X 下建立一個包含一些文字（字體大小 = 20）的文字框。

**已查明的事實（mvbf ↔ mvbW/sparrow 原始碼調查）**

1. **mvbW 字級清單 10~130（偶數）**：toolbar 顯示會把任何值吸附到清單（>130 顯示 130）；套用字級、adorning 等比縮放會**破壞性**改寫超出清單的值；已含 >130 字級的文字框放大操作直接被判 invalid。
2. **兩平台檔案單位域不一致**：mvbW 把 OLF font-size 當 px（UI pt = px×0.75）；mvbf 存檔乘 devicePixelRatio（裝置相關）。疊加後 mvbW 顯示的數字 = mvbf 的 1.5 倍（130 兩邊都顯示 130 其實是被 mvbW clamp 的巧合）。
3. **mvbW 存檔必掉精度**：`Math.Round` 取整 → RTF 半點量化（值只能是 2/3 px 的倍數）。
4. **Shape stroke 已示範跨平台正解**：檔案值 = content space、讀寫 1:1、不烤 zoom、縮放全部交給渲染 transform。mvbW 的 textarea 存檔其實已遵守一半（x/y/matrix 乘 zoom、font-size 刻意不乘）；mvbf 的 text 是唯一把 zoom 烤進數值的（`toJson` 的 `normalizedClone`），這是歷史 ADO 39024 的決定，需重新檢視。

---

**未來要處理 / 討論的方向**

1. **resize 若影響 font size**：在 130 上限下就不能一直放大（或取消上限）。現有 bug：放大 text 物件（視覺超過 130）後進入編輯模式會被 clamp。
2. **resize 若不影響 font size**：font size 20 的字與 font size 60 縮小後的字視覺相同、數字卻不同 —— 使用者觀感詭異。→ 需要 spec 決策：display value 在 resize 下的語意，以及顯示超過 130 時 toolbar 顯示什麼。
3. **mvbf 實作：canvas zoom 與 resize 這兩個行為要分開**，不該都去改 font size。調查已確認：畫布上文字本來就靠 matrix 縮放渲染（zoom 不動字級），字級被改的時機是「進出編輯器」時 `normalizedClone` 把 matrix 烤進字級並寫回。
4. **提案方向**（對齊 stroke 模式）：stored font size 永遠 10~130、zoom/resize 只動 matrix、顯示時由 matrix + canvas scale 計算。編輯器可用低成本作法：開啟時照舊烤 scale（視覺不變）、**關閉時反烤還原**，把「烤」從永久破壞變成編輯期間的無損暫借，不需要動 Quill 渲染（Phase A）。
5. **跨平台配套**：(a) mvbf 存檔單位改固定常數（×4/3 對齊 mvbW px 語意），取代裝置相關的 devicePixelRatio；(b) mvbW 端的破壞性 clamp / `Math.Round` 需 Windows 團隊配合修（修改點行號清單已整理）。
6. **注意**：在 mvbW 修正前，用 mvbW 編輯含大字級（>130 換算值）的 mvbf 檔案會永久毀損字級（顯示吸附 → 套用即改寫）；QA 迴歸先避開此情境。
