3. 原分析（已被第 2 節決策取代，保留脈絡）

以下為修正前的方向盤點，已由上方決策取代，僅保留作為推導脈絡。

先決問題：mvbW / mvbX 渲染 OLF 時會不會 apply pageset matrix 的 scale？ （我們存的檔案 page matrix 有 1.2266 —— 其他平台開啟時畫面會放大 1.2266 倍嗎？）

假設當時推導的修法後果
會 apply 存檔不把 zoom 烤進字級（保留 display 域數值 + page matrix 記 zoom），開檔把 page scale 烤回 annotation matrix（D2 選項 A） Round-trip 完美（48→48），跨平台視覺也一致
不會（其他平台只看 font-size 數字） 存檔烤 zoom 是視覺相容的必要之惡 → 開檔後 infiniteCanvasScale 歸 1（D2 選項 B） toolbar 會顯示烤過的值（48@122.66% 重開顯示 58）—— 視覺一致但數字仍變，需 PM/QA 確認可接受度
無論選哪邊，D1 的整數化都該處理：toJson 的 normalizedClone 應改為 convertToIntegerFontSize: false（或至少把 clamp 拿掉），否則 WIP 的 float 精度在存檔時照樣被毀 （例：zoom 175% 建的 20 → quill 35.0 → 存檔變 34）。

4. 為什麼被取代

它讓 mvbf 自己 round-trip 對了，代價是把破壞風險推給 mvbW。 2026-08-13 查了 sparrow 原始碼後才確認：mvbW 的字級清單是 pt 域、上限 130， GetNearestFontSize 硬取最近值且無上下限保護 —— 本修法存出的「可無限大」的值（例：display 130 @ zoom 400% = 520）， 只要在 mvbW 被輸入或 resize 就會被吸附改寫，永久損毀。 完整查證見 findings §8。

另外兩點在後續查證中也被推翻或修正：

  • 「D2 不需修」依賴的是「存檔烤 zoom × 開檔還原 zoom 標籤剛好互相抵消」—— 這種正確性是脆的，任一端被動到就會無聲壞掉。見 findings §9。
  • 把 scale 烤進 Quill 字級這件事本身（normalizedClone）才是病根； 現行修法改用 TextScaler 從根拔掉，而不是在它之上補精度。
