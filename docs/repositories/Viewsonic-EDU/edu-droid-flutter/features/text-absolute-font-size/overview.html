3. 問題一句話

使用者看到的 font size 會隨 canvas zoom 改變（在不同縮放等級下建立同樣 fontSize=20 的文字， 顯示出來的數字卻不同），而且存檔重開後數字會漂移（130→106、48→46）。

病根：字級其實有三個不同的域，而 mvbf 把它們壓成同一個值 —— normalizedClone 會把 annotation matrix 的 scale（含 canvas zoom） 烤進字級並寫回，這是不可逆的資訊破壞。

5. 現行模型（三個域）

域語意誰能寫
storedannotation / 檔案裡的正典值只有使用者主動挑字級時
renderstored × element matrix（含 canvas zoom）渲染層算出來，不回寫
displaytoolbar 顯示 = stored × elementScale ÷ canvasZoomUI 算出來，不回寫
  • canvas zoom → 只動 matrix，永不進 stored
  • lasso resize → 只動 matrix（mvbf 本來就是這樣，正確，不動）
  • 編輯器 → 用 MediaQuery(textScaler:) 呈現放大，不再把 scale 烤進字級
  • clamp（10~130） → 只發生在顯示域；stored 可超過 130，但存檔時不得超過 173.33（mvbW 的 130pt），超出的倍率由 matrix 承載
跨平台的槓桿：「視覺 = font-size × matrix scale」這條算式 mvbf / mvbW 兩邊一致， 所以同一個視覺有無限多組拆法，我們挑一組落在 mvbW 合法射程內的 —— 不需要動 mvbW、不需要格式版本標記、舊 reader 天然正確。 查證見 findings §8。

9. 待決事項

#問題狀態
Q1 存檔仍在烤 canvas zoom。toJson 把 matrixScale（含 zoom）烤進字級， 所以正規化上限會很常被觸發 —— zoom 400% 時任何 >43.3 的字都會走到。 視覺與 round-trip 正確，但不夠乾淨：終局應是存檔完全不烤 zoom（font 寫 stored、zoom 全留 matrix，與 mvbW 一致）。 該做但未做 地雷：toJson 的 data['width'] 用 getBounds()（轉換後），不烤 scale 會與 matrix 重複計算 → 屬 x/y/width 的域改動，需與 mvbW 對開檔案驗證。
原本以為會撞 D2，查證後相反 —— infiniteCanvasScale 只是標籤、不是渲染 transform，Q1 反而讓檔案自洽並修好 D2 的幽靈 zoom。見 findings §11
Q2 XML / textarea 存檔路徑（genParagraph 的 xmlBuilder）沒套正規化，只有 content.json（toJson）有。該路徑產出的檔會給 mvbW 讀嗎？ 待確認
Q3 舊版 mvbf 開新檔並進編輯器會被它自己的 normalizedClone 縮一半（純檢視不會）。可接受嗎？ 已權衡 選對 mvbW 安全 —— 舊版 mvbf 會隨更新消失，mvbW 的碼動不了
Q5 sticky note 會吃掉 matrix：內層 text 的 matrix scale 存檔時被無聲丟掉（stickynote_annotation.dart:223/316）。目前安全是「碰巧」（內層 matrix 恆為 identity），需測試釘住。 要加 invariant 測試
Q4 normalizedClone 其餘 5 個呼叫點（adorning / element_helper ×2 / pop quiz / sticky note）是否也該檢視？ 本次未動
