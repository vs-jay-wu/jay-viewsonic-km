為什麼這個數字有標誌意義：71894 那張單的標題就是「PPT 匯入時間過長」，內文寫「達兩分二十秒左右」—— 當年 140 秒就被開單抗議。現在是 439 秒，是那條線的 3.1 倍。

但不是每個檔都這樣。另一輪在 IFP34 上跑 olfparser 官方樣本集（54 檔，透過 olf-jni 測試 APK，不經 mvbf UI）： 54/54 成功、零 crash、中位數 30 ms、峰值 RSS 175 MB；VSFT-9993 那份 12.9 MB 繪本是 4.5 秒。 差別在有幾頁需要烘版面——不烘的檔案很快，烘的檔案成本爆炸。

另外一個要修的：mvbf 原本那條路有 convertOLF timeout after 60s 看門狗， 但 POC 分支在建立看門狗之前就回傳，所以新路徑目前是無限等。

效能可以調到哪裡：四個旋鈕

前一節的 439 秒是 olfparser 的預設設定。接著逐項改上游程式碼、 每改一項就在 IFP34 上重量一次 57539，結果是累積 99×——而且每一步都是既有程式碼的參數或路徑， 沒有新演算法。

⚠️ 前四列是在 app 內夾 log 量的；最後一列（去重）改用交叉編譯的 CLI 直接在 IFP34 上跑，因為裝置在期間被更新成 versionCode 40000000 的 system app，原本的 POC APK 已不在、UI 座標也失準。兩種方法在同一組態下的落差是 6.3 秒（app）vs 6.18 秒（CLI），約 2%，所以併在同一張表裡。

1 · 超取樣（LAYOUT_BAKE_SUPERSAMPLE，預設 2 → 改 1）

放大兩倍＝4 倍像素量，但實測是 11.5 倍的差距，遠超理論值——放大後的畫布很可能超出快取， 記憶體頻寬在弱裝置上成為瓶頸。物件數與預設完全相同（933），輸出還小 8%，只有烘圖解析度不同。

2 · 關閉版面烘烤

olfparser 自己就有非點陣的 inject_layout_shapes 路徑， orchestrator/mod.rs 的註解直接寫它存在的理由是 「uses the non-raster injection path to avoid paying the bake cost」（discovery 模式在用）。 實驗只是讓正式轉檔也走那條既有路徑。

3 · images/、fonts/ 改用 STORED

兩邊寫 OLF 的方式本來就不同：舊 parser 整包 store，olfparser 整包 deflate。 而 OLF 內容多是已壓縮的影像格式，再 deflate 一次幾乎壓不動卻要付整份 CPU。

⚠️ 不能全部改 store：images 佔比在 18 個檔案間是 0%～99%， 59377 反而是 content.json 38 MB / 總 46.9 MB（圖片只佔 20%），那種檔案很吃壓縮。 所以實作是混合——images/、fonts/ 用 STORED，其餘照舊。

4 · 影像去重（已實作並實測）

實測發現輸出裡大量重複：

57539影像數獨特重複率
原始 pptx1861860%
舊 1.8.024419122%
新（烘烤）38816458%

無烘烤版寫了 869 張圖但只有 167 張不一樣，其中有 4 張各被寫了 78 次—— 那是 93 頁共用的同一套版面裝飾，每頁重新寫一次。 注意獨特影像數反而比原檔少（186→167），所以這不是「做得比較多」，是重複勞動。

原因：PPTX 已經去重了，olfparser 把那個身分丟掉

OOXML 在封裝層本來就只存一份圖：<a:blip r:embed="rId3"> 經過該 part 的 .rels 解析後指向 /ppt/media/image2.emf，被幾個地方用就掛幾條 relationship。 pptx-parser 的 Shape::image() 已經做了這個解析， 但只拿它來切副檔名，Image struct 連 name 欄位都沒有：

let rid = blip.get(&ns::r("embed"))?;        // "rId3"
let image_part = self.part.related(rid)?;    // 解析成真正的 part
let name = image_part.name();                // "/ppt/media/image2.emf"
Some(Image {
    blob: image_part.blob(),
    ext: name.rsplit('.').next()...          // ← 只留副檔名，name 就丟了
})

MediaHandler::add_image 於是每次都無條件 image_counter += 1 產生新路徑。 它裡面那個 blob_cache 不是去重機制，key 是剛生成的唯一路徑，永遠不會命中。 同一個 crate 裡其實有 md5 去重（background.rs 的 _store_bg_image、 layout_bake.rs 的 layoutbg），只是沒套到一般 picture 上。

做法：不是「去重」，是產生前先查表

正確的 key 不是輸出 bytes 的 hash，而是 (解析後的 part 名稱, srcRect 裁切, flipH/V, 是否 90/270 預旋轉, prstGeom@prst, effectLst 子樹, custGeom 子樹) —— 全部來自 XML 屬性，一個 bytes 都不用碰。 命中就回傳既有的 source 路徑；OLF 本來就允許多個元素指同一個檔。

兩個實作上會咬人的地方：

  • rId 本身不是全域唯一的，作用域是擁有它的那個 part 的 .rels ——slideLayout40 的 rId3 和 slideLayout38 的 rId3 是兩條不同的關係。 必須用解析後的 target part 名稱。
  • 空的 <a:effectLst/> 在 OOXML 極常見且是 no-op。第一版用「有沒有這個元素」 當排除條件，869 只降到 527；改成比對 read_effect_list() 的內容才降到 174。

正確性驗證

對 18 檔的輸出做逐一比對：把 content.json 裡每個資源引用解析成實際的 source 檔案，比對 md5 + mime-type + width/height + matrix。 18 檔全部、共 2,395 個資源引用完全一致（57539 自己就有 869 個）。 content.json 其餘欄位的差異只有 generate_id() 產生的隨機 UUID ——同一支未改動的 binary 跑兩次也會有同樣的差異（對照組實測 9,721 個欄位）。 olfparser 既有測試 993 個全過。

成本：hash 的顧慮不成立

先前擔心「多一道去重檢查會不會更慢」。實測 IFP34 上 md5 掃過 57539 全部 23 MB 影像是 172 ms （其中 92 ms 是讀檔，純計算約 80 ms），對照 6.18 秒是 1.3%。 而實際做法連這 80 ms 都不用付——key 只用 XML 屬性，重複的那 702 份 從頭到尾不存在：不會被複製到記憶體、不會被寫檔、不會被壓縮。

剩下的 1.77 倍

Mac 取樣顯示扣掉壓縮後，主要是 PNG 解碼／編碼、檔案 I/O，以及 Google Fonts 網路請求 （__recvfrom；這條只在 Mac 發生，IFP 實測不會抓）。這部分才是「olfparser 做得比較多」—— 向量化 AutoShape、圖片效果、內嵌字型。要再往下壓就是功能取捨，不是效能 bug。

風險排序

旋鈕 1 與 3 不改變 OLF 的結構（ss=1 物件數與預設完全相同；STORED 只改封裝方式）， 風險最低，值得優先跟上游提。旋鈕 2 會改變 OLF 組成，風險較高。

具體可以要求上游的：把 LAYOUT_BAKE_SUPERSAMPLE 從編譯期常數改成可設定 （或依裝置／頁數自動降階），並對已壓縮的 entry 改用 STORED。對他們是小改動，對 IFP 是數十倍。

EMF 轉檔失敗後仍以 .png 送出

查效能時順帶發現，尚未驗證使用者可見影響，先記著避免發散。

57539 裡 ppt/media/image2.emf（母片上的裝飾元素，被 3 個 slideLayout ＋ 7 個 slideMaster 引用）在 OLF 輸出中的檔名是 image0002.png，但檔頭是 01000000 6c000000 —— 那是 EMR_HEADER，也就是 bytes 還是 EMF。

這是刻意對齊 Python 版的行為，pptx-convert/src/media.rs 的 convert_picture 有註解寫明：

// WMF/EMF/TIFF → PNG. Python forces ext=".png" UNCONDITIONALLY after
// `_convert_to_png` — even when the decode fails and the ORIGINAL
// bytes pass through (the source/mime-type still say .png/image/png).

Rust 沒有 WMF/EMF 解碼器（crate 開頭的模組註解也寫了），所以這條路一定失敗。 推測後果是 mvbf 解不開該檔、那個母片裝飾在每一頁都不顯示，但我沒有實際 render 驗證。

要查的話從這裡開始：把 57539 匯入後看母片裝飾有沒有出現；若確認缺圖，這是 olfparser 的獨立議題（與去重、烘烤無關），Jira MT 專案目前沒有對應的票。
