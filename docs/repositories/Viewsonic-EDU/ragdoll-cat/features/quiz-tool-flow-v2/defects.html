0. 怎麼讀這份

每則記三件事：症狀（使用者看到什麼）、為什麼沒被擋下來、 修法的形狀。不記誰寫的 —— 這條分支上多數缺陷是 「A 改流程、B 的模組在底下失效、C 在 review 抓到」，責任歸屬對後來的人沒有用。

「為什麼沒被擋下來」是重點。 每一則都通過了編譯、通過了當時的測試、 通過了至少一次 review 才留下來。

D1   pre-start 沒有班級時謊報「請檢查網路」

症狀畫面同時說「No students yet，去開一次性班級」與「Please check your internet connection」。實機 ping 8.8.8.8 與 API host 都 0% 丟包。
根因旗標算的是「真網路 AND socket 已連線」，而 socket 是進課堂才連的。沒有 lesson 時它必然為 false。
為什麼沒被擋這個狀態在改版前不可達 —— 舊流程要先有班級才走得到作答窗。slice 8 讓 capture 直達 pre-start、`S2-12` 又明訂沒有教室也要能到，它才第一次出現。
修法加入「有沒有 lesson」作為第三個判斷項。

D2   沒有班級時「真的斷網」反而不提示

症狀guest 的背景啟用鏈因斷網失敗 → 停在沒有 lessonId 的狀態 → 老師拿到零個網路提示。pre-start 空狀態兩顆按鈕仍可點，失敗只發泛用 toast。
根因D1 的修法寫成 hasLesson && !(net && sock)，沒有 lesson 時整條短路，把 net 也一起丟掉了。
為什麼沒被擋D1 的四條測試在新式子下全部照樣綠 —— 它們的 network 預設是 true，沒有任何一條走「沒有 lesson ＋ 斷網」。
修法!net || (hasLesson && !sock) —— 把 net 提到 hasLesson 之外，成為獨立的警告理由。
形狀：一個修法把「必然發生的偽陽性」換成了「只在真的出事時發生的偽陰性」。 淨值仍是正的，但不必付這個代價 —— 兩個條件本來就該獨立。

D3   End class 之後拿不到取得班級的兩顆按鈕

症狀登入 → 開截圖題 → 加入課程 → End class → 再開截圖題，右欄顯示 WAITING_FOR_STUDENTS 而不是兩顆按鈕。整個 session 都回不來。
根因 isTeacherInClass 有兩個輸入，只有一個是 flow：除了 lessonId， 它還讀 CSWindowManager 裡 JOIN_CLASS 視窗是否存在。而 teardown 的順序是 endLesson()（清 lessonId，唯一的一次發射）→ 之後才 removeAllWindowsExcept。那次發射看到「lessonId 已空但視窗還在」→ 正確地答「在課堂中」； 視窗真的消失時已經沒有第二次發射。
為什麼沒被擋 既有測試把 isTeacherInClass 注入成 String::isNotEmpty —— 正好 stub 掉那個帶著隱性依賴的判斷式。
修法 把視窗變動變成顯式的建構式參數（預設接 OnCSWindowChangedListener 的 callbackFlow），與教室狀態一起 merge。

判斷式本身從頭到尾都是對的 —— isPending()（每次呼叫重新求值）全程回 true。 壞的是沒有人再問它一次。

D4   pre-start 按 ✕ 關不掉視窗、跳錯誤 toast

症狀連著網路時 pre-start 的視窗無法關閉；斷網反而關得掉（那條分支走本地關窗、不打 API）。
根因 showCloseConfirmDialog() 只分「結果頁」與「其他」，PRE_START 掉進「其他」 被當成進行中的測驗 → 打 PUT /api/v3/quizzes/{quiz_id} 去關一個從未建立的題目 （pre-start 不上傳不建題，quizId 是空字串）→ 後端不認 → 錯誤 toast，而視窗還在。 文案也講「Unfinished responses will be lost」，但 pre-start 一個 response 都沒有。
為什麼沒被擋 那是 if/else 而不是 when。QuizState 新增第七個值時，編譯器沒有對任何人施壓。
修法在既有邏輯前加短路，六個題型共用同一個 helper；另加一支反射掃描的接線測試，確保沒有題型漏掉。

D5   capture session 洩漏、投影指示器不熄

症狀 出完題、視窗都關了，狀態列還掛著投放圖示；ScreenCaptureSession、 media-projection 型 FGS 與 MediaProjection 的 native buffer（約 100MB）撐到 service 銷毀。
根因 釋放規則 CaptureSessionReleasePolicy.editQuizTags 認的是編輯窗 tag， 而 capture 現在落在 pre-start 作答窗。shouldRelease 因此永遠回 false。
為什麼沒被擋 這個判定沒有安全的失效模式。 CaptureSessionForegroundPolicy.decide(isSuccessful = true) 回 KEEP， 理由正是「稍後會有人釋放」；而成功路徑上唯一的釋放來源就是 shouldRelease。 tag 一旦對不上，不是降級而是擱淺，且完全無聲。 該檔案自 VSFT-9013 起一行沒改 —— 它壞掉不是因為被改，是因為前提被抽掉。
修法 改用既有的 WindowTag.getMvbQuizStartWindowTagList()（它的 KDoc 本來就寫著這是截圖路徑的集合）， 讓路由與釋放規則綁在同一個來源。
適用範圍未驗證。只在 !useVSApi && isMyViewBoardBound && sdkInt ≥ 34 三者同時成立時發生。走 VSApi 的 ViewSonic 機器不使用 MediaProjection，Android 13 以下走一次性流程（截完自己 stop）。 IFP 出貨機若走 VSApi 就碰不到這個問題。

D6   註解描述的路徑已經不存在

症狀 KDoc 寫「這裡只剩繪圖題編輯窗解得出東西，因為繪圖題的草稿是在它的編輯窗裡編寫的」—— 在寫下的當天是對的，slice 9 落地後理由就不成立了（草稿 model 改由 openInPreStart 自己建）。
為什麼沒被擋沒有任何工具檢查註解與程式的一致性。它甚至不會過期得很明顯 —— 讀起來仍然像現況。
修法 發現當天就改（同一支 PR 補 commit）。結論沒變、理由變了，而 「讀起來像現況、實際上已經錯的理由」比沒有理由更糟 —— 下一個人會把它當成活的不變式往上接東西。
修正時的第一版寫成「繪圖題一度是例外……後來改成……」。 那是 changelog 不是註解：會立刻過期，而且沒人會回來更新。歷史屬於 commit 與 Jira， 註解只描述現在的性質。

7. 測試自身的缺陷

這條分支上「測試看起來綠、其實沒在測東西」出現了五種不同形狀，值得各記一筆。

T1   斷言剛好撞上初始值

_shouldWarnOffline 的初始值就是 false，而 collector 跑在 Dispatchers.IO 上。建構完立刻讀 .value 讀到的是初始值， 不是算出來的結果 —— 期望 false 的斷言在 collector 還沒跑到時就通過。

實測：用那種寫法把判斷式退回沒有修正的版本，0 條紅。 解法是走一次真實轉換（進班且 socket 斷 → 等到警告 → 離開課堂 → 等到不警告）， 那個 false 才是算出來的。

T2   stub 掉了真正要測的依賴

PendingSelectClassStateTest 注入 isTeacherInClass = String::isNotEmpty， 而 D3 的整個問題就出在真實的 isTeacherInClass 還會讀視窗狀態。 把帶著隱性依賴的判斷式換成單純的字串檢查，等於把要測的東西移除了。

T3   測一個到不了的元件

MvbOptionPanelBehaviorTest 的 11 條測試直接 inflate view、不經編輯窗， 所以在 host layout 被刪之後仍然全綠。 「看起來是覆蓋、實際上釘的是到不了的元件」比沒有測試更誤導 —— 它讓覆蓋率報告說謊。 同一個問題也出現在策略文件上（mvb-quiz-edit-option-panel.md 把已刪主體的測試標成 [x]）。

T4   collector 被第一個例外帶走

AmplitudeEventBuilder 透過 KoinJavaComponent.inject 取依賴； 測試沒啟動 Koin 時它在 collect 內丟例外，連帶殺掉整條 coroutine。 症狀極誤導：第一次發射成功，所以只驗一次的測試全綠， 只有需要第二次發射的案例才逾時。

生產環境有 Koin 所以不會因這個原因丟，但形狀相同：那個 send() 若因任何原因丟出， 該視窗的離線提示就終身失效。已知、未修。

T5   fixture 餵矛盾的狀態

四個測試把 QuizStartWindowModel stub 成 QUIZ_RESULTS， 卻給 QuizManager 一個預設的 QuizzingUiState()（＝QUIZZING）， 而視窗讀的是後者。一度被誤判為產品回歸，實際上是 fixture 自己不一致。

8. 可以帶走的判準

情境做法
某個判斷同時依賴 flow 與非 flow 的輸入 把非 flow 那半也接成訊號，否則就是把某個時間點的快照當成持續狀態。 故障形狀固定：狀態卡住，沒有錯誤。
新增列舉值 找出所有 if/else 形式的分派 —— when 會逼你處理，if/else 不會。
tag / 常數集合 從真正的來源推導，不要手抄。手抄的清單對「來源改變」毫無反應， 而那正是最常見的迴歸。
斷言一個「什麼都沒發生」的狀態 先讓它經過一次真實轉換，證明 collector 活著，再翻回期望值。 直接斷言靜止值常常剛好等於初始值。
寫測試時想 stub 掉一個複雜的依賴 先問：那個複雜性本身是不是要測的東西？（見 T2）
刪除死碼 連它的測試一起刪。留下的測試若「刪掉 host 仍然全綠」，它釘的就是到不了的東西。
修完一個模組後 問「有沒有別的模組假設了我剛剛改掉的那件事」—— 這條分支上多數缺陷來自這裡，而不是來自寫錯。
驗證測試有效性 做變異測試：把修法退回缺陷的樣子，看紅幾條。0 條紅代表那條測試沒有在測東西。
