0. 一句話

ScreenshotActivity 開在自己的 task，而 ARC 把那個 task 的 container layer 當成不透明的全畫面遮擋者（即使 WindowManager 標它 translucent=true）， 於是 myViewBoard 的 layer 被判定完全遮擋、VisibleRegion 歸零、不參與合成 —— 擷取到的畫面裡就沒有白板。第二次時該 task 沒進合成，所以正常。

為什麼只有這台

擷取路線由 PersistentCaptureSessionPolicy.shouldUse() 分流：IFP 走 VSApi、 Android 14+ 走 persistent session、其餘走 legacy per-capture MediaProjection。 這台是 SDK 33 又沒有 VSApi，是唯一會走 legacy 的機型 —— 而 legacy 是唯一每次都要彈 ChromeOS 授權對話框的路線。

2. 被推翻的假說（8 個）

全部都實際測過才排除。記下來是為了不必重走。

假說怎麼被推翻的
ImageReader 的 buffer 深度不足（maxImages=1）診斷顯示 drained=1，佇列本來就只有一張
acquireNextImage() 拿到最舊的那張同上，只有一張可取，與 acquireLatestImage() 等價
pipeline 還沒 settle，等久一點就好每 500ms 取一次連取 6 次跨 2.5 秒，全部沒有 myViewBoard
授權對話框造成 config change，Flutter 沒重繪遮罩開著時手動 wm density / wm size，白板正常重繪
ARC 的 ArcScreenCaptureSession 壞掉先建一個丟棄用的 VirtualDisplay 吃掉它、讓正式的走 GPU fallback，畫面照樣空白
VIRTUAL_DISPLAY_FLAG_AUTO_MIRROR 用錯換成 mVB 端的 OWN_CONTENT_ONLY | PUBLIC，畫面照樣空白
myViewBoard 的視窗有 FLAG_SECURE原始碼完全沒設定
mirror layer 的 VisibleRegion=0 是病灶正常那次量到它也是 0 — 這個欄位沒有鑑別力

3. 找到成因的那一步

轉捩點是在同一輪流程裡把第一次與第二次的完整 dumpsys SurfaceFlinger 都抓下來逐項比對。合成層清單的唯一實質差異：

第一次（空白）                      第二次（正常）
  ARC Snapshot 88#72                 ARC Snapshot 88#72
  Task=140#5953                      Task=140#5953
  MainActivity#5971   vis=0          MainActivity#5971   vis=1
  Task=141#5983  ← 多這個               (不在合成清單裡)
    isOpaque=true
    geomLayerBounds=[-38400, -21600, 38400, 21600]

兩份 dump 裡 MainActivity 是同一個 layer， activeBuffer（3840x2160:2816, RGBA_8888）與 flags 完全相同， 差別只有 VisibleRegion。畫面內容一直都在，只是沒被合成。

而 Task=141 在 dumpsys window 裡明明是 translucent=true — WindowManager 與 SurfaceFlinger 對同一個 task 的判斷不一致， 這就是 ARC 特有的地方。

4. 修法與觸發條件

遮罩掛好後把 Activity 的 task 退到背景（moveTaskToBack(true)）。遮罩與題型面板是 TYPE_APPLICATION_OVERLAY，不屬於該 task，所以照常浮在最上層可互動； Activity 也還活著，繼續持有 MediaProjection 與 ImageReader。

if (!myViewBoardConnectionStateProvider.isBound()) return   // 獨立 app 沒有 MVB 可以讓位
if (!packageManager.hasSystemFeature("org.chromium.arc")) return
moveTaskToBack(true)

用能力偵測而不是機型清單。實測：VPC-Chromebox 有 org.chromium.arc， IFP51 / IFP63 都沒有。

連帶要移除 manifest 的 android:noHistory="true" —— 它的語意是「離開前景就銷毀」，與 moveTaskToBack 直接衝突（實測一呼叫就 onDestroy → sendResult(CANCELED)，遮罩被收掉、擷取當場結束）。

刻意沒採用的作法

  • 偵測擷取結果是不是空的再重試：老師本來就可能在空白頁上擷取，判準無法區分真假。
  • 用「有沒有 VSApi」當條件：遮擋發生在合成層，每條路線最後都讀合成結果 （含 VSPictureManager.screenshot），「VSApi 不受影響」沒有實測支持； 而且 ARC 上沒有 VSApi，等於死條件。
  • 執行期偵測「這台會不會中」：做不到。判斷依據是 SurfaceFlinger 的 VisibleRegion，屬內部合成狀態、要 shell 權限；app 拿得到的 View.getWindowVisibility() / isShown() / onWindowFocusChanged 都只描述自己的視窗， 而這個 Activity 在所有平台上都是「可見」的。

5. 還沒驗證的範圍

2026-09-23 實測更新：「對所有機型套用也無妨」不成立。 把 ARC 條件拿掉、在 Pixel Tablet（Android 16，persistent session 路線）上測， 擷取出題畫面確實會閃一下 —— 很快但看得出來，使用者不會知道原因。 所以維持 ChromeOS 過濾，不放寬。

  1. 是不是所有 ChromeOS 都會中？未知，很可能不是。合成行為可能隨 ChromeOS 版本、ARC 版本、GPU 驅動而異。現行條件對所有 ARC 裝置套用是保守取捨。
  2. ChromeOS 升到 Android 14 之後？會改走 persistent session， 該路線的遮罩同樣由 ScreenshotActivity 顯示，推測一樣會中，但沒測過。
  3. VSApi 路線在 ARC 上是否受影響？ARC 上沒有 VSApi，無從驗證。

要縮小範圍（例如只對特定 ChromeOS 版本套用），需要先在多台不同 ChromeOS 機型上 用下面的判準量一遍。

6. 查證指令

擷取當下（遮罩開著、還沒按 Capture）跑：

adb -s <device> shell dumpsys SurfaceFlinger | grep -A3 'MainActivity#'

看非 (Mirror) 的那個 layer：count=1 表示 myViewBoard 有參與合成、擷取拿得到畫面；count=0 就是被遮擋。

⚠️ 同一份輸出裡 (Mirror) 那個 layer 的 count 正常時也是 0， 不要拿它當判準 — 這點誤導了好幾輪。

確認 task 有沒有讓出去（合成清單裡不該有 ScreenshotActivity 的 task container）：

adb -s <device> shell dumpsys SurfaceFlinger | grep '^\* Layer' | sed 's/0x[0-9a-f]*//'

認出這台會不會走 legacy 路線：

adb -s <device> shell pm list features | grep chromium
adb -s <device> shell getprop ro.build.version.sdk

7. 已知問題：ARC 上遮罩期間按 Back

讓出 task 之後，取消用的 onBackPressedDispatcher 綁在已離開前景的 ScreenshotActivity 上，而 CS 的 overlay 全是 FLAG_NOT_FOCUSABLE， 所以 Back 會落到前景的 myViewBoard。

文件狀態修法前（baseline 實測）套用後
未修改只取消擷取myViewBoard 直接退出（無確認）
已修改只取消擷取遮罩退出 ＋ 跳儲存對話框

觸發條件：要送得出 Back

  • Chromebox（觸控）：實測按不到 —— 從底部上滑出來的是 ChromeOS shelf，沒有 Back。後果是用 adb shell input keyevent KEYCODE_BACK 強制送出才觀察到的。
  • Chromebook（鍵盤）：按得到，鍵盤上就有 Back 鍵 —— 只有這台是使用者碰得到的途徑。
  • 非 ARC：不適用（不套用 workaround，Pixel Tablet 實測行為與修法前相同）。

⚠️ ScreenshotActivity.kt 那句「swipe from the bottom edge brings the bar back」是在 IFP 上量的，ChromeOS 上不成立。我一度把它當成 ChromeOS 的依據引用，是同一類「把 A 系統的量測外推到 B」的錯。

決定：列為已知問題，先不修（2026-09-24）

要同時滿足「ChromeOS」＋「送得出 Back」＋「遮罩期間按下去」才會發生，頻率低； 而兩條修法的成本都不成比例（動 CS window framework 核心 / 跨 repo 改 myViewBoard）。

⚠️ 討論中原本的安全網假設「畫面上有東西就會跳對話框」不成立 —— PageSetModel.isModified() 比的是「相對於開啟時有沒有被編輯」，不是畫面有沒有內容。 所以開啟既有教材、未編輯就出題的情況會無確認直接退出。 這個例外當場被指出，團隊仍決定降級 —— 記下來是為了讓判斷可追溯，不是沒想到。

考慮過的修法

方案狀態
setTranslucent(true) 取代 moveTaskToBack ❌ 實測無效：系統回 false（theme 本來就 translucent，沒有可轉換的狀態）， VisibleRegion 仍 0。這條看起來最誘人，特別記下來不必再試
遮罩 overlay 自己 focusable 並攔 Back 未做。框架預設 overlay 為 NOT_FOCUSABLE，但執行期切換已是既有模式 （UrlMetaPreviewDialog.kt:188、CSCreateQuizCollectionFolderWidget.kt:99 都會在聚焦時清掉旗標）—— 我原本寫成「框架層開新能力」是誇大。真正的成本是遮罩要整個 session 保持 focusable （那兩處只在瞬間切換），動到觸控穿透與 IME；另外框架確實沒有任何按鍵處理程式碼，攔截要自己寫

8. 連帶回歸：拿掉 noHistory 之後的 Home（已修）

為了讓 moveTaskToBack 能用，manifest 的 android:noHistory="true" 被移除。 但那個旗標同時也是一張網：「Activity 離開前景就銷毀」→ onDestroy 送 CANCELED。

⚠️ 這個回歸不限 ChromeOS：noHistory 在 manifest 層， 不像 moveTaskToBack 有 org.chromium.arc 守著，所以 Pixel、IFP 全都中。 這是 PR reviewer 的 MINOR 建議挖出來的，我原本低估了它。

實測重現（Pixel Tablet，未修版）

遮罩開著按 Home
  → ScreenshotActivity 仍存活、完全沒有 sendResult
  → 再按截圖鈕：沒有任何 onCreate（被 re-entrant 守衛擋死）
  → isCaptureInFlight 放不掉、CS 視窗一直藏著，直到 process 結束

waitUntilVirtualDisplayReady 沒有 timeout，所以那個狀態不會自己結束。

修法：onStop 補網

在 onStop() 取消這一輪，排除三種情況：自己讓出 task、config change、已送出結果。 修後同一台：onStop → sendResult CANCELED → 遮罩收掉 → VirtualDisplay 釋放， Activity 存活數歸零。

⚠️ 這張網在 ARC 上補不回來（yieldTaskToMyViewBoard 已經先把 Activity 停掉， 之後按 Home 不會再觸發 onStop），所以 ChromeOS 上「Home 缺口」與 Back 並列為已知代價。

兩個自己埋的坑

  • 旗標沒吃回傳值：原本 isYieldingTask = true 設在 moveTaskToBack() 之前，它回 false 時旗標仍是 true， 會把下一次真正的「使用者離開」吃掉 —— 等於這張網被消音一次。reviewer 抓到的。
  • 未驗證的等價宣稱：欄位 KDoc 原本寫「比照 noHistory 當初的語意」， 但兩者的觸發面從沒逐項比對過。實測熄屏（mWakefulness=Dozing）時 Activity 仍存活、沒有任何 onStop，所以熄屏不會取消擷取、 也不需要 isInteractive 判斷。KDoc 改成只寫這條量過的，不宣稱等價。

9. 這輪的教訓

八個假說全錯的共同形狀：只看了「壞掉那次」的數據。看到任何異常 （ARC session timeout、GPU fallback、viewport metrics、mirror 的 vis=0）就當成病因， 卻沒去確認正常那次是不是也長這樣。實際比對之後，那些異常全部兩次都有。

真正有效的一步是請人在遮罩出現時停手，讓我在同一輪流程裡抓下第一次與第二次的 完整 dump —— 有了對照組，唯一的實質差異當場浮出來。

把一次讀到的值當成不變的事實

調查初期讀到 mvbf 的 finch-ref.properties 是 vb-2077-mvb-sync-20260914，之後一整天的建置都沿用這個值當 override。 但那個檔案在 09-22 就被改釘 v2.11.23 了（commit 6b85d2c77）， 我完全沒察覺 —— 因為 gradle 的 incremental build 不會重新評估 :app， 直到換了 CS 的 checkout 路徑才炸出「找不到 QuizRequestType.aidl」。

也就是說：先前那些 APK 編的是舊版 Finch 介面（修正後重建的兩顆大了約 54 MB， 可以反證）。實測行為沒受影響，但這完全是運氣。

這正是 km rules「不要記會漂移的指標」的同一族 —— 我把「某次 cat 到的值」 當成常數帶著走。判準：每次建置前重讀版本釘選檔，不要從對話歷史裡撈。

同一個「半改」被抓到兩輪

/review-local 連續兩輪都抓到「同一份文件／同一個 repo 裡並存兩種說法」：

  • 第一輪：onCreate 的註解仍宣稱「never leaves RESUMED」（正是 workaround 打破的前提）； 文件「未驗證的範圍」還寫「只在一台驗證過」，而同一份文件前面已經寫了兩台。
  • 第二輪：「階段 2」段落還寫著「Back 鍵的歸屬也不會變」，跟新加的表格正好相反； ScreenshotActivityBackPressTest 的 KDoc 還宣稱真機已驗過 Back 會結束 session。

我每次都只改「我正在寫的那一處」，沒有回頭 grep 被推翻的說法。 判準：推翻一個說法之後，先 grep 關鍵字掃全 repo（含測試檔的 KDoc）， 再繼續寫新的。

「我沒看到」不等於「沒有」

我寫「讓遮罩 overlay focusable 等於在框架層開新能力」，理由是「所有 overlay 都假設 FLAG_NOT_FOCUSABLE」。reviewer 指出 repo 裡已經有兩處在執行期切換 （UrlMetaPreviewDialog.kt:188、CSCreateQuizCollectionFolderWidget.kt:99）， 一 grep 就看得到。

這個誇大會影響決策 —— 它是「不修」的理由之一。 判準：寫「框架沒有 X」之前先 grep X 的反例；成本估算要能指出具體阻礙 （本例真正的成本是「整個 session 保持 focusable，動到觸控穿透與 IME」），而不是「沒有先例」。

反過來，review 的意見也要驗

同一輪 review 推測「Chromebox 接 USB 鍵盤按 Esc 就會送 BACK，觸發範圍比文件寬」。 查該機的 /system/usr/keychars/Generic.kcm：key ESCAPE 是 base: none（只有 alt/meta → HOME、ctrl → MENU）， 這條不成立。但他同時提的滑鼠側鍵沒被驗掉，所以文件把結論 收窄成「觸控與一般鍵盤碰不到」，滑鼠那條標為未驗證 —— 驗掉一半、保留一半。

另一個自傷的例子：我寫的空白偵測判準是「四個抽樣點全為 0」，但實際畫面是遮罩的灰 A39C96，判準在結構上就看不到目標狀態，所以我寫的重試機制 從頭到尾沒執行過，而 log 看起來一切正常。換成無條件存圖、用眼睛看，才看見真相。
