0. 一句話

換窗的前擋圖是用軟體 Canvas 截的，而軟體 canvas 畫不出 elevation 陰影； 視窗在換窗那 49–107 ms 內整個掉陰影與輪廓，再突然長回來。改成硬體算繪截圖後， Pixel Tablet 上完全不閃，IFP92 大幅改善，IFP34 仍然 100% 會閃且尚未診斷。

1. 被推翻的假說（這段比結論有用）

按提出順序，每一條都是當時「看起來很合理」的判斷：

#假說怎麼死的
1交棒太早：awaitVisible() 只等到 layout，舊窗被拆時新窗第一幀還沒 commit，中間有空白幀實測三次，frame_commit 每次都在 old_window_removed 之前 1 ms。沒有空窗期
2尺寸不一致：bitmap 用 floatingView.width、新窗用 getCurrentSize()實測 bitmap=2085x1190 floatingView=2085x1190 currentSize=2085x1190，三者相同
3density 造成擋圖縮放該機 wm density 320、無 override，排除
4SurfaceView / TextureView 截不進圖全 repo 零個
5reviewer 提的：overlay 是軟體算繪，所以「硬體截圖＝跟真實視窗一致」這個歸因有問題dumpsys 顯示實際 flags 有 HARDWARE_ACCELERATED（框架自動補的）。反而是 repo 既有 8 處註解的前提是錯的

共同教訓：前四條都是讀碼推論，全錯；真正的成因是靠裝置上的畫素比對找到的。 第 5 條則是差點被既有註解帶偏 —— 那 8 處註解寫「no FLAG_HARDWARE_ACCELERATED」， 程式碼裡確實搜不到那個字串，但 runtime 的 flags 不是這樣。 不要從「程式碼裡有沒有這個字串」反推行為。

2. 找到成因的那一步

做了一個可用 adb 開關的 hold：讓換窗流程停在「畫面上只剩前擋圖」15 秒， 期間截圖，恢復後在同一位置再截一張，逐像素比對視窗左緣。

x    擋圖(軟體)  真內容
124     255       249
136     255       226
142     255       206     ← 平的 255 = 陰影完全不存在

改成 RenderNode + HardwareRenderer 之後，同一個位置擋圖與真內容最大差 6 階。

3. 另一條路：單一 overlay window ＋ 真 z-index（spike 後放棄）

Jay 問「只改 z-index 技術上可不可行」，做了完整 spike。結論：公開 API 做不到。

兩道平台牆（實測，細節在團隊 repo 的文件裡）：

  1. InternalInsetsInfo.touchableRegion 在真機上反射也拿不到（NoSuchFieldException， 而 addOnComputeInternalInsetsListener / setTouchableInsets 都拿得到）→ 可觸控區縮不成子視窗的聯集
  2. 繞道用 FLAG_NOT_TOUCHABLE 讓觸控穿透 → 系統把該視窗壓到 alpha=0.8， 而且 app 明確設 alpha = 1.0f 會被覆寫（用一個 300×300 的對照視窗證實，與尺寸無關）

形成封閉循環：要穿透就得不可觸控 → 不可觸控就被降透明度 → 要不降透明度就得可觸控 → 可觸控就吃掉視窗之間的觸控 → 要兩者兼得就需要那個拿不到的欄位。

但 spike 也證實了視覺面完全達標：bringToFront() 換 z-order 只要 16–24 ms （現行做法 49–107 ms），全程不需要截圖、陰影不掉。所以這條路不是「不好」，是「被平台擋住」。

翻案條件寫在 → docs/ideas/cs-window-single-host-zindex.md
