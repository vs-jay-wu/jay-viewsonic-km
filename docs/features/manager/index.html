1. Manager 是什麼

myViewBoard Manager＝賣給學校／企業 IT 的裝置管理 SaaS（MDM）。 管 ViewSonic 的 IFP（互動大螢幕）機隊，以及機器上跑的軟體設定。 內部代號 DM（Device Management）——這點對讀 repo 名很關鍵： edu-dm-* 全都是 Manager，不是別的產品。

介面管什麼
Devices 頁機隊清單。主鍵是 serial number，agent 回報完整硬體／韌體／狀態
Software Instances 頁管機器上 myViewBoard 的設定（Check for Update、Local Save、Embedded Browser、Sign-in Function 等），可用 template 批次套用
遠端桌面從 Dashboard 直接看／控 IFP（WebRTC）

雲端掛在 myViewBoard 的網域底下，不是獨立產品線：

https://api.stage.myviewboard.com/api/dm/v2/api-docs   ← Swagger
https://dm.dev.myviewboard.cloud/api-docs

2. 規格的正解在 KB，不在這裡

Viewsonic-EDU/edu-dm-knowledge-base 是 Manager 的官方結構化知識庫。 涵蓋 18 個 feature 規格、355 個 API endpoint、跨平台對照、sprint 追溯。 自述主要消費者是 AI agent，人類透過 dm-kb plugin 存取。

要理解 Manager 的功能面，裝這個 plugin 比讀任何文件都快：

gh repo clone Viewsonic-EDU/edu-dm-knowledge-base
# 在 Claude Code 內：
#   /plugin marketplace add Viewsonic-EDU/edu-dm-knowledge-base
#   /plugin install dm-kb@viewsonic-edu-dm-kb
#   /dm-kb:setup
命令用途
/dm-kb:spec問「這個功能怎麼運作」，PM 語言回答，標示信心度
/dm-kb:spec-deep同上但強制查 code 佐證（spec ↔ L1 ↔ code 三方交叉驗證）
/dm-kb:feature-mapfeature 跨 frontend／backend／android 對照表
/dm-kb:review-story評 Jira ticket 是否 ready for dev

另有 edu-dm-opskit：DM 的 operation 任務工具箱， 同時是 Claude Code plugin、marketplace 與團隊 operation 知識庫。 解決的問題是「業務端的資料匯出、log 查詢除錯可能交給任何一位工程師， 而 session 結束就忘了」——讓過程中學到的東西以 PR 回寫、審核後分發。

5. AOSP vs EDLA：貫穿全線的分歧

這是理解 Manager 技術決策最有用的一把鑰匙，而且它不只影響 agent。

AOSP（傳統 IFP 韌體）EDLA（GMS 認證裝置）
agent 取得權限的方式sharedUserId="android.uid.system"，系統 appDevice Owner 模式
為什麼要分—GMS 認證裝置不能玩 system uid
讀得到 serial number 嗎平台簽章 system app 讀得到只有 Device Owner（＝dm）讀得到

最後一列直接決定了 §6 那條整合的方向。

6. 與 myViewBoard 的接點

兩個方向，都是同一台裝置上的 ContentProvider IPC：

方向內容狀態
dm → MVBMVB 讀 content://com.viewsonic.dmagent.provider/entity 拿 entity name 做 auto-enroll既有
MVB → dmMVB 開唯讀 provider 給 dm 讀 instance_idVSFT-9654 / VB-1399

為什麼需要第二條——這解釋了兩個產品的關係： Manager 雲端從 MVB 後端拿得到 instance 清單，但那是一排 hex 字串， 對不上「哪個 ID 在哪台機器」。缺的不是資料，是兩個資料世界的 join key：

  • Manager 的世界：裝置紀錄，主鍵 serial number＝IT 眼中的機隊
  • myViewBoard 的世界：instance 紀錄，主鍵 instance ID

為什麼方向是 MVB 給 dm、不是 MVB enroll 時帶 serial： EDLA 上 MVB 讀不到 serial（要 READ_PRIVILEGED_PHONE_STATE 或 Device Owner 身分）， 而 dm 是 Device Owner 永遠讀得到——能讀 serial 的一方必須是學到 instance ID 的一方。 方向是被 §5 的技術限制逼出來的，不是偏好。

這條整合的完整調查（含 headless Flutter engine、存取控制、實測競態）在 docs/features/manager-mvb-instance-id-provider/， 那份是從 MVB 側看過去的視角。

8. 證據等級與查證方式

本文的宣稱等級怎麼來的
repo 清單、語言、預設分支、pushed_at、archived 狀態實查gh api orgs/Viewsonic-EDU/repos（2026-09-22）
各 repo 的用途讀碼各 repo 的 README.md／CLAUDE.md
agent 的模組結構與技術棧讀碼edu-dm-agent-monorepo/CLAUDE.md

AMAPI 是否要取代自家 agent不下結論只有一個測試 repo，不足以支撐
四個 API repo 之間的取代關係不下結論名字像但沒查，不要用名字猜
重跑這份地圖的指令（repo 會增減，數字會過期）： 
gh api "orgs/Viewsonic-EDU/repos?per_page=100&sort=pushed" --paginate \
  --jq '.[] | select(.name|test("dm|manager|device-manager";"i"))
        | [.name, (.pushed_at|split("T")[0]), .default_branch,
           (.language//"-"), (if .archived then "ARCHIVED" else "" end)] | @tsv'
對照組：輸出裡要掃得到 edu-dm-agent-monorepo（已知一定在）。掃不到就是 filter 壞了。
