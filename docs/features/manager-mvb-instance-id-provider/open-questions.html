Q1. entity name 的定義與來源？

問誰 Peja / Stephen

Stephen comment 說 provider 要提供「entity name」，但 codebase 裡 entity 有三種語意，且目前沒有任何一處持久化 entity name 字串（詳見 findings §2）：

  • (a) 裝置 enroll 的 entity——目前只存 app_entityID，沒有 name
  • (b) 從 Manager agent / Activator 讀來的 entityName——transient，不落地；而且這個值本來就是 Manager 給的，若票要的是這個，Manager 自己就有，不合理
  • (c) 登入帳號的 entity——帳號層概念，跟「裝置 ↔ instance 對應」無關

推測是 (a)，但需要確認：

  • 後端 GET /api/v1/application/viewboard/{uid}/entity 的 response 是否已含 entity name？（若有，只需擴充解析；若無，要請後端加或另打 API）
2026-07-30 本機實驗補強：dmagent 端 DMService 從 DataStore 收 enrollEntityFlow（含 entityName + deviceName）——agent 自己就持有 entity name，要 MVB provider 回 entity name 的目的更需釐清（見 findings §7）。
✅ 目的已釐清（Aaron Chang，2026-07-31）：entity name 是授權護欄（tenancy guard），不是識別資料的重複—— (1) entity name 不會重複，可作識別； (2) dm 拿 MVB 的 entity name 與自己持有的比對，不同就不對該 MVB 做事； (3) 「MVB 註冊 entity A、Manager 註冊 entity B」雖少見，但同一台裝置上不同 entity ≠ 該 Manager 有權管理。
仍待解：MVB 端 entity name 的來源（後端 /{uid}/entity 是否回 name）與持久化——且回傳字串必須與 Manager 雲端的 entity name 逐字元一致（大小寫/空白正規化要跟 dm 對齊），否則護欄會誤攔。
✅ 來源已查證（2026-07-31，edu-mvb-api-core）：後端不用改。 GET /{instance_id}/entity 的 response（InstanceEntityObj，apps/mvb-app-api/src/module/whiteboard/dto/res-body.dto.ts:35-46）已含 entity_id / organization / name / beta_program——MVB 目前只解析 entity_id（mvb_activator.dart:433），其餘丟掉。只需擴充解析並持久化。
該用哪個欄位：dm 的 entityName 在 auto-enroll 走 POST /install/inspect body {organization: entityName} → 後端 Entity.findOne({where:{organization}})（entity.service.ts:53-57）精確等值比對 organization → provider 的 entity_name 應回 organization；後端是逐字元等值，MVB 原樣存、原樣回即可，無自訂正規化空間。會議上與 Manager team 確認 dm 端比對邏輯同為精確等值。

Q2. Manager agent（com.viewsonic.dmagent）用哪把簽章 key？

問誰 Manager team（VB-1399）

決定存取控制方案：

  • 若與 MVB ifp/edla 同為 MVBA_PlatForm.jks → 可用 protectionLevel="signature" 的自訂 permission，但 open/store flavor（Google Play key）會失效
  • 若不同 key、或需支援所有 flavor → provider 內做 runtime 檢查：getCallingPackage() + GET_SIGNING_CERTIFICATES 比對 SHA-256 allowlist

也需確認：這個 provider 是否只需要 ifp/edla flavor 提供？（Manager agent 場景應該只有 IFP 裝置，若確定，open/store 可直接不註冊 provider，signature permission 方案就成立）

2026-07-30 本機實驗補強：dmagent repo 的 keystore.properties 用的正是 MVBA_PlatForm.jks（alias platform）——與 MVB ifp/edla 同 key，signature 方案可行性高，待與 Manager team 確認正式包板也是同把 key。
✅ 範圍已確認（Jay，2026-07-31）：dm 只需要 ifp/edla，open/store 不管。 → 存取控制定向為 signature permission（protectionLevel="signature"），provider 註冊移到 flavor 專屬 manifest（src/ifp/、src/edla/），main manifest 不註冊——open/store 連 provider 都不存在。 剩餘確認項只剩：dmagent 正式包板是否同為 MVBA_PlatForm.jks（本機證據已支持，會議上一句話確認即可）。詳見 contract 草案 §2。
