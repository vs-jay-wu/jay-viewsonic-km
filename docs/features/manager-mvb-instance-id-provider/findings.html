0. 現況：instance ID 是怎麼給 Manager 的（= 缺口本身）

結論：裝置端目前完全沒有給，這正是本票要補的缺口。
  • 雲端側（Manager 看得到 instance ID 的原因）：MVB enroll 時把 instance ID 當 uid 上報 myViewBoard 後端（POST /api/v2/application/whiteboard，mvb_activator.dart:177-204）。裝置 enroll 進 entity 後，Manager 雲端「Software Instances」頁即可列出該 entity 下所有 instance ID 並套設定（票面附圖的列表就是這個）。所以 Manager 知道有哪些 instance。
  • 裝置側（缺口）：Manager agent（com.viewsonic.dmagent）在裝置上管理本機，但 MVB 沒有任何對外介面提供本機的 instance ID，agent 無從得知本機 MVB 是哪個 instance。結果是雲端有一排 instance ID，卻對不上「哪個 ID 是哪台裝置」。
  • 既有跨 app 通道只有反方向：裝置上 MVB ↔ Manager agent 唯一的整合，是 MVB 去讀 agent 的 provider content://com.viewsonic.dmagent.provider/entity 拿 entity name 做 auto-enroll（MainActivity.java:1855-1906）——資料方向 Manager → MVB，沒有 MVB → Manager。
  • 本票即是把方向反過來：MVB 開對稱的 ContentProvider 讓 agent 讀 instance ID（＋ entity_id），agent 回報雲端後，Manager 才能建立「instance ID ↔ 裝置」對應。

  • key app_instanceID（line 131 寫、143 讀）

1.1 Hive 的實際機制與「原生讀不到」的正確說法（2026-08-14 實機查證）

結論：不是「看不到」，是「沒有 parser」。否決直讀 Hive 的理由，與 POC v2 否決直讀 FlutterSharedPreferences 內部格式是同一個理由（依賴 undocumented 實作細節），這樣論述才自洽。

檔案位置與格式

  • 路徑：/data/data/com.viewsonic.droid/app_flutter/activate_db/activate.hive（實測 2046 bytes、權限 -rw-------）
  • 格式：append-only frame log——[uint32 frame長度][keyLen][key ASCII][typeId][value][uint32 CRC32]
    • 改值不是原地覆寫，而是再 append 一個新 frame，讀取時同 key 取最後一筆
    • 刪除＝寫 tombstone frame（Frame.deleted）
    • 檔案膨脹到閾值才 compaction 重寫整檔（版面因此會變）
    • 來源：hive_ce-2.19.3/lib/src/binary/frame.dart（string key 上限 255 bytes）、src/crypto/crc32.dart

實機證據——此 box 邏輯上只有 7 個 key，實體 frame 數卻是：

app_instanceID ×1   app_entityID ×1   app_whiteboardName ×1   app_email ×1
app_activated  ×1   StartupCount ×9   native_analytics    ×9

StartupCount 每次開機 +1 就多一個 frame——append-only 的直接證明。且值是明文：

0000000: 3d00 0000 010e 6170 705f 696e 7374 616e  =.....app_instan
0000010: 6365 4944 0420 0000 0034 3732 4342 3741  ceID. ...472CB7A
0000020: 4433 4335 4139 4533 3838 3144 4446 4343  D3C5A9E3881DDFCC

為什麼還是不在 provider 內直讀

要讀就得自己刻 frame 掃描器：長度前綴、typeId、tombstone、同 key 取最後一筆、CRC 驗證、compaction 後的版面變化——而這是套件的 undocumented 內部格式，hive_ce 升版即可能改。技術上做得到，但這正是 POC v2 否決「直讀 FlutterSharedPreferences」的那類耦合（silent desync 風險）。

1.2 儲存保護等級：Hive vs SharedPreferences（實機實測，2026-08-14）

結論：兩者保護等級相同，鏡射到 prefs 不會降低安全性。同一個 app-private 目錄、同 uid、都沒有加密（SecureDataStorage 名不符實，無 HiveCipher）。實測權限 activate.hive = -rw-------、prefs = -rw-rw----，差在 group 位但同 uid 存取結果一致——碰得到其中一個的，另一個也碰得到。

1.3 「搬到 SharedPreferences 會不會失去加密？」——沒有加密可失去（2026-08-17）

結論：Hive 現在也是明文，鏡射到 prefs 不降低任何保護。 誤解來源是類別名 SecureDataStorage——它沒有 HiveCipher，名不符實。實機 hexdump 已證明 instance ID 以明文 ASCII 存放（見 §1.1）。兩者都是 app-private 目錄的明文檔，靠 uid 隔離 + SELinux 保護，等級相同（見 §1.2）。

該不該改成加密儲存？不建議在本票做

  1. 金鑰要存哪？存在同一個 app-private 目錄等於沒加密（能讀檔就能讀金鑰）。真要做需用 Android Keystore（硬體支撐），屬獨立重構

  3. 加密不改變可及性：instance_id 本來就印在 Settings 畫面上

2.1 entity id / name 存 Hive 的篡改風險與護欄定位（2026-08-14 評估）

結論：風險可忽略。三根支柱—— (1) MVB 只是唯讀的資訊提供者，不執行動作、不因 dm 的話改變自身狀態； (2) 要篡改需先 root / 平台簽章，到那一步攻擊者能做的事遠比謊報 entity name 嚴重； (3) 真正有後果的動作（套設定、管理）都在雲端，有獨立的 tenancy 檢查。
層次結論
檔案本身的保護 activate.hive 在 app-private dir、無 cipher。一般 app 讀不到（uid 隔離 + SELinux），non-root adb 也動不了（run-as 只對 debuggable app 有效）——實測見 §1.2
既有 entity_id 為何多年無事 因為它沒被拿去做任何判斷——全 repo 唯一消費者是 analytics_helper.dart:105 的 'EntityID'（Amplitude user property）。篡改它最多污染自家分析數據
本票的差異點 原本擔心 entity_name 成為 dm 的本地護欄後，會從「純上報資料」變成會影響行為的輸入。
✅ 2026-08-17 定案後此顧慮消失：只給 entity_id，而 dm 手上沒有 id 可本地比對 → 判定必然在雲端
護欄的正確定位：防誤配置，不是防攻擊者。
  • 真正擋的是：MVB 在 entity A、Manager 在 entity B 的誤註冊——設定錯誤，護欄對此非常有效，這是它的價值
  • 但不構成安全邊界：要偽造得先 root / 平台簽章，而到那地步攻擊者能做的遠比謊報 entity name 嚴重（直接改 provider 回傳、換掉整個 app）
  • → 權威 tenancy 檢查要留在雲端；本地字串比對只是前置快篩，非最終授權依據
    ✅ 2026-08-17 定案後這點自然成立：provider 只給 entity_id，而 dm 端沒有 id 可在本地比對（EnrollEntity.kt:3 只有 entityName），比對必然落在雲端。本節「本地護欄被高估」的顧慮因此消失
  • ⚠️ 上述第 (3) 根支柱「dm 側有雲端複驗」為合理推定，未查證 Manager 後端——需向 dm 端確認他們不會因為有了本地護欄而省掉雲端檢查（已列入 contract §9）

5.1 範圍判定的決策軌跡（內部紀錄）

曾有一版錯誤結論：「dm 只需 ifp/edla → open/store 不註冊 provider → signature permission 即可」（2026-07-31 初判，2026-08-14 以 dm repo 佐證後仍維持）。
佐證本身沒錯：ModelFactory.kt dispatch 全數 ViewSonic 機型、VSApi/systemapi 為 compileOnly、Undefined -> vsApiDevice 在非 VS 韌體啟動即 crash；dm 產品型態只有 app_aosp/app_edla（release tag 僅 release/AOSP/*・release/EDLA/*）；正式包板簽 MVBA_PlatForm.jks（basic-vars.yml KEYSTORE_NAME）。
錯的是從這些前提推出的結論。
→ 教訓：「dm 只跑 ViewSonic 韌體」不等於「dm 遇到的 mvbf 一定是 ifp/edla 包」。 flavor 對應的是「那台機器上裝了哪個 mvbf 包」，不是「那台機器是什麼硬體」——A31 即兩者脫鉤之處。VPC 系列本就是抽取式模組，日後仍可能出現類似機型，判斷時要直接查「該機型出貨裝哪個 flavor」，不要從硬體類別推。
📌 附帶情報（同串對話，Evis）：「Manager 會自己 OTA，不用跟著 FW」——dm 可獨立於韌體升級。 對版本演進是好消息（舊 key 的 deprecation 週期好推）；反面是 mvbf / dm 版號各自漂移，更確認「行為分支一律用 presence 偵測、不看 contract_version」這條紀律（contract §7）。

10.1 為什麼一定要跑 Dart（原生捷徑走不通）

先排除「純原生產生 instance_id」的想法。原生自己算 md5(ts+androidId+uuid) 是容易的，但它無法知道 Hive 裡是否已經有值（無 parser），於是：

  • 可用的免 parser 判斷只有「activate.hive 檔案存不存在」
  • 但主要情境正是「檔案存在且有值、只是 Dart 沒跑過」（舊安裝升級後未開啟）——此時原生若自行產生就會造出第二個身分，而舊 ID 已在後端註冊並掛著 entity
  • → 原生捷徑只能解「全新安裝從未開啟」，而那個情境本來就會被首次開機的 BOOT_COMPLETED 覆蓋

因此 headless Dart 是必要條件，與 contract §8.1 的三層次分析一致。

10.2 需要的最小 Dart 路徑（比預期小很多）

本情境不需要「產生」，只需要「讀出來 + 鏡射」——產生只發生在全新安裝，那條路走正常啟動即可。
⚠️ 2026-08-19 更正：需求 3 要求「全新安裝未開啟時 dm 也能拿到」，所以 headless 最終也要能產生。 實際做法是照樣呼叫 MvbActivator.ensureInitialized()——它的 isEmpty 判斷讓「已有值」時是 no-op， 兩種情境用同一段程式碼（見 §13）。

@pragma('vm:entry-point')

  WidgetsFlutterBinding.ensureInitialized();
  // _load() 內部已呼叫 _mirrorToProviderInfo()（POC 既有行為）
  await SecureDataStorage.getInstance().initialize(false);

  • 不需要 androidID（那是產生時才要的），因此避開了 getDeviceModelFactory() 那條重依賴
    ⚠️ 2026-08-19 更正：需求 3（全新安裝未開）要求 headless 也能產生，所以 androidID 還是要。 好消息是它來自 AndroidUtilityHelperPlatformService.ensureInitialized()，確實不依賴 getDeviceModelFactory()——那條重鏈仍可略過。 但必須先 VSPlatformHelperImpl().ensureInitialized()，否則 _isChromeOS() 的 late 欄位會丟 LateInitializationError（見 §13.1 ③）

  • initialize(false) 的 false ＝ 不 reset（正確：headless 絕不該清資料）

10.5 唯一的實質風險：Hive 跨 isolate 併發

Dart 的 singleton 是 per-isolate 的，所以 headless isolate 會有自己一份 SecureDataStorage，可能與主 isolate 同時開同一個 Hive 檔。Hive 並非設計來跨 isolate 併發存取。
低成本的化解方式：headless 進入點先檢查原生 prefs 是否已有 instance_id，有就立即結束、不開 Hive。 因為鏡射在每次 app 啟動都會跑，prefs 有值即代表「app 已於本版執行過」→ 無事可做； 反之 prefs 為空幾乎必然代表 app 沒在跑，於是併發窗口實務上不存在。

13.1 過程中抓到的四個真問題

① ⚠️ 既有潛在 bug：首次啟動會清掉 headless 剛產生的 instance_id

需求 3 一開始失敗：headless 產生 0E23F872…，但開啟 MVB 後變成 CA1CFF14…。根因在 application_info.dart： 
_savedBuildNumber = prefs.getInt('ApplicationInfo_savedBuildNumber') ?? 0;
shouldResetActivationStorage = _buildNumber % 2 != _savedBuildNumber % 2;
build number 的奇偶用來編碼 stage／production。pm clear／全新安裝後 saved ＝ 0（偶數）， 而本版 build number 30110031 是奇數 → 誤判為「target 切換」→ reset 整個 activation storage 並重新產生 id。
這個 bug 一直存在但無害（全新安裝本來就沒資料可清）——是 headless 讓它顯形：headless 在使用者首次開啟之前就產生了 id。
修法：加守衛「saved == 0 代表沒有前一次紀錄，不該推論成切換」。isNewVersion 不受影響（它比的是相等而非奇偶），故不會吃掉版本升級的訊號。
修好後 log：[ApplicationInfo] build=30110031 saved=0 hasPrev=false reset=false reactivate=false
⚠️ 此修正動到共用邏輯（非 provider 專屬），正式 PR 時可考慮拆成獨立 commit。

② headless 的完成訊號抓錯，engine 在產生途中被 destroy

原本把「第一次 setInfo」當完成訊號，但一次 headless 執行可能鏡射兩次： _load() 先鏡射（此時可能是空的）→ 若 Hive 也空，MvbActivator.ensureInitialized() 產生後由 _save() 再鏡射一次。 結果 engine 在產生途中就被 destroy，prefs 只留下空的 instance_id。
修法：改為「拿到非空 instance_id 才收工」，真的產不出來則由 TIMEOUT_MS 兜底。

③ LateInitializationError: _isChromeOSCache——platformType 必須先初始化

§10.2 曾判斷「headless 不需要 platformType」——錯的。_isChromeOS() 讀的是 late 欄位，未初始化直接丟 LateInitializationError； 而 MvbActivator._generateInstanceID() 內部也會讀 platformType，所以這步跳不掉。
好消息是成本很低：Android 上 _initM1Detection() 早退、_initIsChromeOS() 只是一次 platform channel、 WindowManagerWrapper 是 NoWindowImp（init() 空實作）——故直接呼叫 VSPlatformHelperImpl().ensureInitialized() 即可。

④ ⚠️ registerContentObserver 在 authority 不存在時會丟例外（對 dm 正式實作重要）

SecurityException: Failed to find provider … expected to find a valid ContentProvider for this authority—— 與 query() 回 null 的行為不同。舊版 MVB／MVB 未安裝時註冊 observer 就會 crash（實測炸掉 dm 的 EnrollmentActivity）。
→ dm 端用 registerContentObserver 或 JobScheduler.addTriggerContentUri 訂閱 infoUri 時務必包 try/catch。 已在 MvbInstanceInfoReader.infoUri 的 KDoc 標注警告。

13.2 entity name 已完全移除

依 §3.1 的決議清乾淨：entityOrganization（Dart 欄位／介面／Hive key app_entityOrganization）、Pigeon 的 entityName 欄位（已重新產生）、_getEntityID() 的 record 回傳（回復為 Future<String>）、Java 側 KEY_ENTITY_NAME。全 repo grep 無殘留，dart analyze 無 error。

14.2 ⚠️ 觸發點不能放在「只執行一次」的生命週期

同一類錯誤犯了兩次，是本次最容易重演的坑。
  1. 第一版把「讀 provider ＋ NOT_INITIALIZED 時要求初始化」放在 DMService.onCreate → 永遠卡在 NOT_INITIALIZED，因為 dm 的 process 常常一直活著，onCreate 不會再跑
  2. 修完第一個後，畫面的讀取仍掛在 Activity 的 onCreate → Activity 已存在時只是被帶到前景、onCreate 不重跑，畫面停在舊狀態
原則：觸發要放在「每次觀察到該狀態」的地方，而不是「元件建立時」。 完整位置比較見 contract §8.2。

💡 這也解釋了一個測試現象：如果 dm 一直停在前景不動、又沒有輪詢，什麼都不會發生—— 使用者回報「一直卡在 NOT_INITIALIZED」時，先確認觸發點會不會重複執行，再懷疑 provider。

15. ⚠️ 競態：headless 與正常啟動同時產生 instance id（2026-08-20 已實測重現並修正）

這不是理論風險，是實測可重現的缺陷。 問題由 Jay 提出（「dm 開始初始化，同時打開 mvbf，會不會同時寫入？」），實測在特定時序下確實會產生兩個 instance id。

15.1 機制：問題出在記憶體快取，不是檔案鎖

兩條路徑在同一個 process（全 manifest 無 android:process），但是兩個 FlutterEngine ／兩個 Dart isolate； 而 Dart 的 singleton 是 per-isolate，所以各有一份 SecureDataStorage。

關鍵：getInstanceID() 讀的是 _load() 當時載入的記憶體快取，不是即時讀 Hive。而 MVB 正常啟動從 _load() 到 MvbActivator.ensureInitialized() 中間隔了十幾秒（PDF factory、WindowManager、DeviceModelFactory… 一長串 await）：

MVB 正常啟動                          headless
─────────────────────────────────────────────────────
T+0   _load() → 讀到空 → 快取 ''
                                      T+5  _load() → 也是空
                                      T+7  產生 E0799707 → 寫 Hive + prefs
T+12  ensureInitialized()
      檢查快取（仍是 ''）→ 產生 191C4CA0
      → 寫 Hive + prefs（覆蓋）

因此這是典型的 check-then-act 競態，而那十幾秒就是窗口。

15.2 偵測方法：利用 Hive 是 append-only

改值不是原地覆寫而是 append 新 frame（見 §1.1），所以若真的產生兩次，檔案裡會同時留著兩個 id——證據不會消失：

實測結果（先開 MVB、+5s 由 dm 觸發 headless）：

⚠️ 時序敏感：+0s 與 +2s 都沒重現（headless 較精簡、通常比 MVB 先到達產生那一步），+5s 才命中。這也說明為什麼不能靠「測不出來」判定安全。

15.3 損害邊界

面向結論
資料損壞✅ 不會。Hive 與 prefs 最終都收斂到最後寫入的那個，兩者一致
真正的風險❗ 中間窗口若被 dm 讀到，它會把之後不存在的 id 回報雲端 → Manager 有一筆指向不存在 instance 的對應，且靜默無錯

15.4 修法：雙層防護（A ＋ B）

A. app 已在執行時 headless 直接跳過

理由不是妥協而是本來就該如此：app 正在跑，它自己就會初始化，headless 根本沒必要跑。 而這剛好封掉 15.1 那個十幾秒的大窗口。
兩條路徑同 process，故一個 static volatile boolean 即足夠： MainActivity.configureFlutterEngine 設 true、onDestroy 設 false， InstanceInfoSyncJobService 在 schedule() 與 onStartJob() 都檢查 （排程與執行之間使用者可能才開啟 app）。

B. 產生前即時重讀 Hive，不信任記憶體快取

新增 DataStorage.reloadInstanceIDAsync()，MvbActivator.ensureInitialized() 改用它的回傳值判斷， 讓「不會重複產生」這個性質不依賴於哪條路徑先跑，而非只在守衛生效時才成立。

⚠️ A 與 B 不是替代關係：A 省掉浪費的第二個 engine、B 縮小窗口（十幾秒 → 微秒級）。 B 仍是 check-then-act，沒有消除競態——徹底消除要靠 15.5 的單一寫入權威。

15.4.1 ⚠️ 驗證 B 時發現：Hive 有 lock 檔，併發會丟例外

為了證明 B 有效，暫時停用守衛 A 讓兩條路徑真的並行。結果 headless 的 Dart 失敗於一個具體錯誤： 
[InstanceInfoHeadless] failed: PathNotFoundException: Cannot delete file,
path = '…/activate_db/activate.lock' (OS Error: No such file or directory, errno = 2)
Hive 有 lock 檔（activate.lock），兩個 isolate 併發開關同一個 box 會撞上。三個結論：
  1. 併發存取 Hive 確實不安全——這是實證，不是推測
  2. 但失敗模式是丟例外而非靜默損壞，比預期的好
  3. 守衛 A 因此不只是優化，而是必要的——併發跑 headless 根本不可靠
❗ 這也暴露 B 本身引入的新風險，必須一起修

17. Headless 啟動成本拆解（分段實測，2026-08-20）

問題起點：headless 是否會把整段 main() 跑過？能不能再切一個更精簡的 Dart 入口，讓 IFP34 這種慢機也快？ 做法是在 Java 與 Dart 兩側插臨時計時 log（量完已移除），在 Pixel Tablet 3629105H804NHC（edla debug） 以 pm clear 冷啟動重複量 3 次，數據一致。

17.2 答案：已經是兩個入口，而且沒有東西可以再切

  • headless 不會跑 main()。Dart 端有兩個入口：main（正常啟動）與 @pragma('vm:entry-point') instanceInfoHeadlessMain（headless）。 _initApp() 那條重鏈（PDF factory、WindowManager、DeviceModelFactory…）headless 完全沒跑。
  • Dart 段那 1.8 s 的四項都拿不掉：platformHelper 是為了避免 LateInitializationError: _isChromeOSCache（見 §10.7）、 storage 初始化是主體、產生是目的、binding 是前提。
  • automaticallyRegisterPlugins=false 不是解方：plugin 自動註冊實測只 10–26 ms， 而關掉它會拔掉 headless 真正需要的 path_provider（Hive.initFlutter）與 device_info_plus（androidID）。省 20 ms、換來手動註冊耦合 plugin 內部類別，不值得。

17.3 log 裡那些「不該出現」的東西不是我們的

headless process 的 log 會看到 TextToSpeech、GoogleTagManager、 AdvertisingIdClient、ProfileInstaller。這些是 process 級初始化 （androidx startup／ContentProvider 自動啟動），process 因為任何原因被拉起就會有，與我們的 engine 無關，也關不掉。

另外會看到一條非致命錯誤：

⛔ Error on detecting chromeos: MissingPluginException(No implementation found for
   method detectChromeos on channel com.viewsonic.droid/detectChromeos)

原因：MainActivity 手寫註冊的 MethodChannel 在 headless engine 不存在（已被 catch，走預設值）。 對照之下 device_info_plus 這類正式 plugin 會被自動註冊，所以 androidID 拿得到 —— 實測產生的 instance_id 正常（A83A0049BFDB108245F6F66B48CEB797）。
→ 教訓：headless 可以依賴 plugin，不能依賴 Activity 手寫 channel。

17.4 ⚠️ 量測順帶抓到的 bug：同一次流程起了兩顆 engine

三次量測都出現兩組完整時間軸、同一個 PID。原因：

  1. dm 在輪詢期間會重複呼叫 provider 的 call("ensureInitialized")；
  2. 守衛 hasMirroredInstanceId() 只看 prefs 的結果，鏡射完成前恆為 false；
  3. 同 JOB_ID 再排一次會取代舊 job，但前一顆 engine 已經在跑 → 同一 process 兩顆 engine、兩個 isolate 同開同一個 Hive 檔， 正是 §15.4.1 的 activate.lock 併發情境。

修法：第三層守衛 sSyncInFlight（volatile static）， 在 onStartJob() 設起、cleanupEngine() 清掉，schedule() 與 onStartJob() 都檢查。 驗證後只剩一顆 engine：

InstanceInfoSync: skip schedule (provider.call): a headless sync is already in flight
InstanceInfoSync: headless mirror: instance_id=(empty)
InstanceInfoSync: headless mirror: instance_id=present
MvbInstanceInfo: ✅ instance_id=A83A0049BFDB108245F6F66B48CEB797  (dm overlay，同一秒)

至此 headless 有三層守衛：sMainEngineAlive（app 在跑就不做）、 hasMirroredInstanceId（做過就不做）、sSyncInFlight（正在做就不重做）。

17.5 對 IFP34 的結論

  • release 版會比實測快：不需解壓 kernel_blob.bin（省掉冷啟那 ~0.7 s），直接用 APK 內的 libapp.so。
  • IFP34 的 12.4 s（§16）是同一組分佈被慢硬體放大，主要壓在 Flutter VM／isolate 啟動—— 那不是我們控制得了的部分，寫再精簡的 Dart 入口也不會變快。
  • 真正有效的加速已經在做：MY_PACKAGE_REPLACED／BOOT_COMPLETED 提前觸發， dm 來問的時候通常早就鏡射完（同步回答，0 等待）。只有「更新後從未開機、dm 立刻問」才會撞到冷啟成本。
  • 因此 TIMEOUT_MS = 20 s 維持不變即可（IFP34 實測 12.4 s，餘裕 ~7.6 s）； 不需要第二個 Dart 入口，README 的「評估調高 timeout」待辦可視為已評估。

18. preload 部署的前提條件（2026-08-20 實測釐清）

起點是一個部署面的問題：MVB 若 preload 在廠商 FW 裡，第一次開機收得到 BOOT_COMPLETED 嗎？ 過程中把兩份外部意見（另兩個 AI 的建議）拿實機一條條驗過，結論如下。 基礎機制整理在 basics §2.6，這裡只留決策與待辦。

18.1 決策：exported="false" 不要改成 true

兩份外部意見都指出「接收系統廣播必須 exported="true"，否則收不到」。這是錯的，已否證。 留下紀錄是因為這個誤解很常見，未來 code review 很可能再被提出來。

  • dumpsys activity broadcasts：重開機的 BOOT_COMPLETED 對 InstanceInfoSyncReceiver 的紀錄是 exported=false ＋ DELIVERED ＋ terminal +32ms。
  • adb install -r 觸發 MY_PACKAGE_REPLACED：process 為了這個 receiver 冷啟動， 一路跑到 InstanceInfoSync: receiver: android.intent.action.MY_PACKAGE_REPLACED。
  • 原理：exported 管的是「別的 app 能不能戳我」；系統派送 protected broadcast 不在其管轄內。 Android 12 起官方指南的建議值對「只收系統廣播」的 receiver 就是 false。
⚠️ 改成 true 不會換到任何功能，只會把 receiver 暴露給第三方 app ——是安全性退步。

過程中也踩到一個量測陷阱：第一次重開機後 grep log 找不到 receiver，誤判成「沒觸發」。 實際是 main buffer 被 Play Store 洗版擠掉（buffer 最早只到 receiver 執行後 33 秒）。 → 驗證廣播有沒有派送，要看 dumpsys activity broadcasts，不要只 grep log。

18.2 preload 收不收得到廣播：預設會，但 Android 14+ 起不是保證

傳統行為（Android ≤ 13）：preload 在 system 分區的 app 開機掃描時就被標成「非 stopped、已 launched」， 所以第一次開機收得到——這正是 preload 相對 sideload 的好處，剛好補掉 notLaunched=true 那個洞。

Android 14（API 34）加了變數：平台允許把非必要的 preload 在第一次開機就掃成 stopped。 實測 Pixel Tablet（Android 16）：scannedAsStoppedSystemApp=true 有 4 個、=false 有 385 個， 其中 com.android.virtualization.terminal（codePath=/apex/…/priv-app/…、flags=[ SYSTEM … ]） 到現在還是 stopped=true。→ 預設會，少數會被關掉，不能當保證。

⚠️ 更該擔心的是「假預載」

廠商說「已預載」有兩種意思，行為天差地遠：

預載方式系統怎麼看第一次開機
燒進 system image（/system/priv-app 等）系統 app，flags 含 SYSTEM✅ 收得到（除非被掃成 stopped）
OOBE 腳本 adb install 到 /data/app一般 user app，notLaunched=true❌ 完全收不到
但架構上不需要賭這件事。 最壞情況（假預載或被掃成 stopped）只是 receiver 這條預熱路徑啞掉； dm 的 provider query 照樣把 MVB 拉起來、順手清掉旗標（§17.6），代價是「晚幾秒」而不是「拿不到」。 這也是 receiver 從一開始就設計成 nice-to-have 的理由。

18.3 ⚠️ 獨立限制：鎖屏未解鎖前，instance_id 讀不到

dumpsys 顯示我們的 receiver 是 directBootAware=false，收的是 BOOT_COMPLETED 而非 LOCKED_BOOT_COMPLETED——要等使用者解鎖才派送。

比 receiver 更關鍵的是資料本身：instance_id 存在 SharedPreferences／Hive， 兩者預設都落在 credential-encrypted (CE) storage，未解鎖前根本掛不上來。 所以這個時間窗內不只 receiver 不跑，dm 來 query provider 也讀不到值。

IFP 一般不設鎖屏、開機即解鎖，實務上碰不到。但若客戶設了 PIN 且開機後沒人解鎖， dm 會看到「provider 通、但沒有值」——落在§12 的哪一類需要確認（目前會被歸成 Failed 或「沒有值」，而非「尚未可用」）。這是與 stopped 無關的獨立限制。

18.4 為什麼這些不列成待辦

直覺上會想開一串「跟 FW 廠商確認預載方式／確認 allowlist」的待辦。 想清楚之後不需要——因為兩種結果我們都已經測過，而且行為都正確。

被當成 stopped非 stopped
開機時receiver 啞掉，什麼都沒發生receiver 觸發，開機就把值備好

stopped 那一欄不是推論，是實測過的路徑（收掉 dm 之後全新安裝 → stopped=true notLaunched=true ＋ 沒有 process → dm 一來 query，4 秒內產生完成，全程沒人碰螢幕）。

差別只在「值什麼時候備好」，不在「拿不拿得到」。 dm 是輪詢的，兩條路最後收斂到同一個狀態。
→ 唯一會讓它變成 bug 的前提是「dm 只 query 一次就定案」， 而那個問題在 §14.2 已經處理掉了，且與 preload 無關。
→ 所以 preload 方式是「知道了比較好，但不影響正確性」的資訊，不是阻塞項。

真的要查的時候一行就夠，留在這裡當除錯用（不是待辦）：

adb shell dumpsys package com.viewsonic.droid \
  | grep -E "codePath|flags=\[|scannedAsStopped|stopped=|notLaunched"

同理，18.3 的鎖屏時間窗也不列待辦：dm 看到的是「provider 通但沒有值」， 跟「還沒產生完」無法也不需要區分，兩者的正確行為都是「稍後再問」。

19. ⚠️ 與 MVBA（前一代原生 app）遷移的衝突（2026-08-21）

從 review lib/application_info.dart 的 hasPreviousRecord 修正一路追出來的， 是目前最可能讓 instance_id 不穩定的路徑，而且完全不在原需求描述裡。

19.1 問題：headless 產生的 id 註定會被覆蓋

main() 在 isNewVersion 時會跑 MVBA 遷移，而遷移會覆寫 instance_id：

// AppUpdateHelper._transferNativeDatabaseData()
var db = await openDatabase(database.path, password: password);   // MVBA 的 sqlcipher DB
List<Map> list = await db.rawQuery("SELECT * FROM vBoardInstanceInfo");
var instanceId = list.first["UniqueID"];
await dataStorage.setAsync(instanceID: instanceId, …);            // ← 覆蓋本地值

意圖是合理的——同一台機器從 MVBA 升到 MVBF，身分該延續。但 headless 不跑 main()， 所以它完全跳過這段遷移：

1. dm query → headless 產生 instance_id = X → 鏡射 → dm 上報 X
2. 使用者第一次開啟 MVBF → transferNativeData() → instance_id 變成 MVBA 的 Y
3. 雲端上 X 這筆對應作廢，而 dm 已經報過了
⚠️ 這條路與 hasPreviousRecord 那個修正無關，是既有的：production（偶數 build） 的 shouldResetActivationStorage 本來就是 false，現在就走 transferNativeData()。
根本張力：headless 的職責是「使用者開啟前就備好 id」，但「這台機器的真實 id 是什麼」 在 MVBA 遷移跑完之前還沒有答案。

19.2 三個方案與取捨

方案做法最壞情況
Aheadless 也搬 MVBA 的 DB（只搬決定身分那半段）踩到沒預期的相依或搬錯欄位 → id 是錯的
C（採用）偵測到有未遷移的 MVBA 資料就不產生，等使用者開 appid 晚一點才有（極端情況：沒人開就一直沒有）
B把 getPreference 從 MainActivity 改成真 plugin，整段共用乾淨，但動到既有 OTA 路徑，風險外溢出本票

A 曾實作過又撤掉。撤的理由不是「比較複雜」，是失效模式的性質： 「錯的 id」比「晚來的 id」嚴重得多，而 A 是為了越來越小的族群去承擔前者。 而且 A 走的是 sqlcipher 開檔 / 解密 / schema 對映——手邊機器驗不了（沒有 myViewBoard.db）。

⚠️ A 還有一個會造成不可逆資料遺失的陷阱

不能直接在 headless 呼叫 transferNativeData()：

transferNativeData() {
  await _transferNativePreferences();   // ← headless 會整段失敗（見下）
  await _transferNativeDatabaseData();  // ← 照樣跑（instance_id 搬到了）
  await _removeMvbaData();              // ← 照樣跑（MVBA 資料被刪）
}

_transferNativePreferences() 靠 OtaPlugin.getPreference()，而那個 channel (com.viewsonic.droid.whiteboard/app_update) 是 MainActivity 手寫註冊的 （MainActivity.java:906）——headless engine 上不存在，丟 MissingPluginException 被那邊自己的 try/catch 吞掉，只留一行 log。於是設定沒搬、MVBA 資料卻被刪了： 語言／主題／字級／工具列位置永久遺失。
→ §17.3 那條教訓（headless 可依賴 plugin、不可依賴 Activity 手寫 channel） 的第二次現身，這次代價是不可逆的。

另一個陷阱：isNewVersion 的來源有副作用

那段的守衛是 ApplicationInfo.isNewVersion，但 ApplicationInfo.ensureInitialized() 結尾會寫入 savedBuildNumber ＋ isFirstInstall。headless 一旦為了讀它而呼叫， 就把「第一次啟動」這個一次性事件消耗掉，導致正常啟動時整段遷移不再執行。 現行 headless 刻意完全不碰 ApplicationInfo，這不是巧合。

19.3 採用 C 的實作

  • AppUpdateHelper.hasPendingMvbaMigration()——只做 File.existsSync()， 不開 DB、不需要密碼，因此不依賴任何 Activity 手寫 channel。
  • headless 的守衛是 before.isEmpty && await …：已經有 id 的機器完全不受影響 （情境 1 的舊版升級照常鏡射），短路求值讓常見路徑連 existsSync() 都不會呼叫。
  • guard 有明確退場條件：遷移完成後 _removeMvbaData() 已刪檔 → 回 false， 現場已無 MVBA 機器時整段可移除。

19.4 新增 pending_reason：狀態要曝光，錯誤不要

C 帶來一個新問題：dm 分不出「還在產生中」與「不會自行產生」。 後者繼續輪詢不會有結果，需要的是人——這是本票第一個「知道原因會導致不同動作」的狀態， 所以值得曝光。

這也修正了本文件早先（§17.6 一帶）的立場 「失敗不必回報給呼叫端，因為動作都是稍後重查」——那個論點對會自癒的失敗成立， 對需要外部介入的狀態不成立。

error_code / error_messagepending_reason
語意這次 query 失敗了provider 正常，但值尚未存在且不會自行產生
值的集合開放（可夾帶任意例外訊息）封閉、可枚舉
要不要配 message要——「我們不知道發生了什麼」的逃生口不要——每個值都是自己寫死的，沒有未知

刻意不做成 pending_code ＋ pending_msg 的對稱形狀：那是假一致。 message 只會落得兩種下場——常數字串複述 code（日後漂移），或動態文字誘使 dm 拿去顯示給使用者 （一個不列入合約、未翻譯的英文字串變成 UI）。形狀不對稱本身在傳達「這是封閉 enum」。 未來若真需要更多資訊，正解是加具名結構化欄位（如 pending_since=<epoch ms>），不是自由文字。

收錄規則（寫進兩邊註解）

只有「需要外部介入才會改變的狀態」才進 pending_reason。 會自癒的失敗（engine 起不來、Dart timeout）一律不收，靠 log 診斷——一旦欄位存在， 早晚有人寫成 if (pending != null) 放棄，而那是錯的。
今天符合的只有一個值：REQUIRES_APP_LAUNCH。

為什麼成本很低

  • 加一列是向後相容的：dm 的 reader 是 Map<String, String>， 不認識的 key 直接忽略，contract_version 不用動（只有移除或改名才要）。 dm 不改也不會壞；要用它才需要在 dm 端加分支。
  • 「空值省略該列」的既有規則直接給了「缺列 = 沒被擋住」，不需要定義 sentinel。
  • 自動清除：正常流程每次鏡射都不傳 pendingReason（null → 空字串 → 省略）， 所以使用者開過 app 之後這一列自己消失。不會有 stale 值——這正是 init_last_error 那種事件式欄位做不到的事。

兩個實作上的坑

  • ⚠️ pendingReason 必須併進 ProviderInfoMirror 的 dirty check snapshot， 否則「只有它改變」的那次鏡射（剛被擋住／剛解除）會被擋掉，變成靜默不更新。
  • ⚠️ 常數 REQUIRES_APP_LAUNCH 在 Dart 與 Java 各寫一份，沒有編譯期保護 （兩邊註解都標了「必須一致」）。
  • 下一次 headless 執行時，_load() 的鏡射會先清掉這一列、隨後再寫回，中間有極短空窗。 dm 若剛好讀到，看到的是「沒有值也沒有 pending_reason」→ 動作是重查 → 無害，不需要同步。

19.6 驗證範圍與「決定不驗」（2026-08-21 定案）

已確認：Dart analyzer 乾淨、:app:compileEdlaDebugJavaWithJavac 成功、 測試 16 支全綠。

① MVBA 正向路徑：決定不驗

Pixel 與 IFP34 都沒有 databases/myViewBoard.db，新分支永遠早退； 人工偽造不現實（要複製 MVBA 的 sqlcipher schema，密碼還得從 androidID 推導）。

不驗是可接受的，因為採用方案 C 之後這條路只是「一個 File.existsSync() 判斷」。 它不開 DB、不解密、不做 schema 對映——沒有那些會出錯的東西。 判斷錯的後果也只是「該早退卻沒早退」（＝退回原行為，id 會被覆蓋一次）或 「不該早退卻早退」（＝晚一點才有 id），兩者都不是錯誤的 id。 這正是 §19.2 選 C 而不是 A 的理由在驗證成本上的回報。

② IFP34 慢機重跑：決定不做，沿用 §16 的數據

§16 那輪之後的改動不影響它的結論：

  • sSyncInFlight（§17.4）在那台機器上本來就測不到。 §16 記載該機的 dm 是 2.4.11 正式版、不含 MvbInstanceInfoReader， 故該輪「只驗 MVB 側」。而這個守衛防的是呼叫端重複呼叫 ensureInitialized—— 沒有 reader 就不會有重複觸發，守衛不會被啟動。 且它的邏輯與機器速度無關（main thread 上讀寫一個 boolean）， 慢機只會讓窗口變寬、讓守衛更常生效，失效方向不是時序造成的。
  • 時序數據仍然有效。pending_reason 只多寫一個 prefs 字串 ＋ dirty check 多比一段字串；decideActivationTransition 是純重構； MVBA guard 在無 .db 時是一次 existsSync()；其餘全是註解。 都在噪音級以下，12.4s／20s（餘裕 7.6s）那組數字不需要重測。

→ 兩項都不列為待辦，也不視為缺口。 時序／TIMEOUT_MS 的評估本身早已結案（維持 20s，見 §17）；剩下的「慢機上守衛是否只起一顆 engine」 需要「dm 在 IFP 上輪詢」與「兩個觸發落在 engine 啟動窗口內」同時成立才觀察得到， 而守衛的失效方向不依賴機器速度——是 edge case，實務上安全。

19.7 ⚠️ 交叉 review 抓到的兩件事（2026-08-21）

① pending_reason 讓一個既有守衛的隱含假設破功 → 無限迴圈

schedule() 與 onStartJob() 的早退條件裡， hasMirroredInstanceId() 有一個沒寫出來的假設： 「instance_id 是空的」代表「還沒好」，也就是暫時的。 §19.3 的情境 3 直接打破它——那條路的定義就是 永遠不會寫出 instance_id，直到有人親自開 app。

後果（review 指出、追code 確認成立）：

dm 每一輪輪詢 ensureInitialized
  → 三個守衛全部通過（instance_id 確實是空的）
  → 排 job → 起一顆完整 FlutterEngine（IFP34 實測 ~12s）
  → Dart 走情境 3 → mirror(pendingReason) → setInfo 拿到空 id
  → hasId == false → **不呼叫 finishJob**
  → engine 閒置到 TIMEOUT_MS(20s) 才被收掉
  → 下一輪輪詢，重來

一台待遷移的機器會這樣無限期反覆啟動 engine，直到使用者開 app。

修法（兩處都補）
  • isBlockedPending() 守衛加進 schedule() 與 onStartJob()： prefs 的 pending_reason 非空就不排、不跑。 自我解除：正常啟動的鏡射一律不帶 pendingReason，原生側寫成空字串 → 守衛失效。造成阻塞的解法（開一次 app）與解鎖條件是同一件事，不會卡死。
  • CompletionSignallingPlugin 收到帶 pendingReason 的 setInfo 時立即收工——「被擋住」是這一輪的終端狀態， 等下去只是空轉。這對「第一次」那輪有效（那時 prefs 還沒有 pending，守衛擋不住）。
教訓：新增一個「永久性狀態」時，要回頭檢查所有以「結果為空」為條件的守衛。 這類守衛通常隱含「空是暫時的、再試一次就會有」，而永久狀態讓「再試一次」變成 純粹的浪費。加欄位的人不會自然想到要去看守衛——兩者在不同檔案、不同語言。

② sMainEngineAlive 的殘留窗口，後果被我低估了

該旗標只擋「之後的 schedule()」，攔不住已在執行的 job。 我原本把撞鎖後的行為描述成「已知且有處理的降級」——那是錯的。 實際的因果鏈是：

headless 產生 id X → commit 進 provider prefs → notifyChange → dm 可能已讀走並回報雲端
使用者此時開 app → 主 isolate 撞 activate.lock
  → reloadInstanceIDAsync() catch → 退回記憶體快取（空）
  → 判定「還沒有 id」→ **再產生 Y 並覆蓋**
→ 雲端持有的 X 從此不存在

這正是§15 那個競態、也正是本功能存在要防止的那個失敗， 而且靜默。守衛 A 只把它壓縮成「in-flight 窗口」，沒有消除。

決定：延後，但把它寫進程式碼

正解是在 setMainEngineAlive(true) 時 JobScheduler.cancel(JOB_ID) （執行中的 job 會收到 onStopJob → cleanupEngine()，現有結構接得上）。 刻意未做：那會在 Dart 可能正在寫 Hive 時 destroy engine，把問題換成「寫入被中途打斷」。 Hive 是 append-only ＋ CRC、尾端不完整的 frame 下次開檔會被跳過，理論上安全， 但必須實機驗過才能換，而目前沒有可用機器。

三件事（前提／破掉的後果／屆時正解）已寫進 setMainEngineAlive 的 javadoc ——這條不能只留在文件裡，因為下一個動那個旗標的人是看程式碼的。

  • ERROR_STORAGE 夾帶 e.getMessage() 也不必收： checkCaller() 排在它之前（provider 的 184 行 vs 208 行）， 所以那個訊息只到得了已通過 package ＋ 憑證驗證的呼叫端。 對已授權者曝光例外訊息是診斷資訊，收掉只會讓現場少一條線索。
