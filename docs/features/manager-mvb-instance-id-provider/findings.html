0. 現況：instance ID 是怎麼給 Manager 的（= 缺口本身）

結論：裝置端目前完全沒有給，這正是本票要補的缺口。
  • 雲端側（Manager 看得到 instance ID 的原因）：MVB enroll 時把 instance ID 當 uid 上報 myViewBoard 後端（POST /api/v2/application/whiteboard，mvb_activator.dart:177-204）。裝置 enroll 進 entity 後，Manager 雲端「Software Instances」頁即可列出該 entity 下所有 instance ID 並套設定（票面附圖的列表就是這個）。所以 Manager 知道有哪些 instance。
  • 裝置側（缺口）：Manager agent（com.viewsonic.dmagent）在裝置上管理本機，但 MVB 沒有任何對外介面提供本機的 instance ID，agent 無從得知本機 MVB 是哪個 instance。結果是雲端有一排 instance ID，卻對不上「哪個 ID 是哪台裝置」。
  • 既有跨 app 通道只有反方向：裝置上 MVB ↔ Manager agent 唯一的整合，是 MVB 去讀 agent 的 provider content://com.viewsonic.dmagent.provider/entity 拿 entity name 做 auto-enroll（MainActivity.java:1855-1906）——資料方向 Manager → MVB，沒有 MVB → Manager。
  • 本票即是把方向反過來：MVB 開對稱的 ContentProvider 讓 agent 讀 instance ID（+ entity name），agent 回報雲端後，Manager 才能建立「instance ID ↔ 裝置」對應。

1. Instance ID 現況

命名與擁有者

Codebase 內叫 instanceID（後端 API 欄位名 uid；SSO URL query 為 instance_id），核心擁有者是 MvbActivator。

角色位置

產生邏輯lib/mvb_activator/mvb_activator.dart:116-139 _generateInstanceID()

產生方式

md5(timestampMillis + androidId + uuidV4)，androidId 來自 AndroidUtilityHelperPlatformService().androidID（底層 DeviceInfoVs.getAndroidID）。只在 getInstanceID().isEmpty 時產生一次，之後永久沿用。

儲存位置（⚠️ 實作關鍵）

存在 Hive，不是 SharedPreferences：

  • Hive.initFlutter('activate_db')（secure_data_storage.dart:26），box name activate（line 16）
  • key app_instanceID（line 131 寫、143 讀）
  • 同 box 還有：app_entityID、app_whiteboardName、app_email、app_activated、StartupCount、native_analytics
  • class 名為 SecureDataStorage 但未加密（無 HiveCipher），檔案在 app documents dir 下 activate_db/activate.hive
Hive 是 Dart 專有 binary 格式，Kotlin/Java 側（ContentProvider）讀不到——這是本票最大的實作障礙。

2. Entity 現況（三種語意，⚠️ 需釐清票要哪個）

(a) 裝置層 entity ID — 最可能是票要的

  • mvb_activator.dart:153-155 getEntityID() / 419-441 _getEntityID()
  • 來源 GET /api/v1/application/viewboard/{uid}/entity → response entity_id（line 433）
  • 存 Hive app_entityID（secure_data_storage.dart:132,144）
  • 只有 ID，沒有 name——目前 codebase 沒有任何地方持久化 entity name

(b) 從 Manager agent / Activator 讀來的 entity name（transient）

  • lib/entity_info_fetcher.dart:20-58：先問 Manager agent，fallback 問 Activator apk
  • 拿到後打 POST /api/v1/application/viewboard/install/inspect body {'organization': entityName} 換 alias_email；entityName 本身不儲存

(c) 登入使用者的 entity（帳號層）

  • lib/model/user_data.dart:51 entityId（login response default_entity），存 VSSharedPreferences
  • name 要另打 GET /me/entity（lib/helper/rest_api_helper.dart:1170-1200，model lib/model/mvb_entity.dart），只用於 Amplitude user properties，不常駐儲存

3. ContentProvider / permission 現況：零先例

  • android/app/src/main/AndroidManifest.xml 只有兩個 androidx.core.content.FileProvider（line 306-325），皆 exported=false；全 repo 無自訂 ContentProvider 子類別
  • 無任何自訂 <permission> 宣告、無 protectionLevel、無 component 掛 android:permission=
  • 無任何 runtime signature 檢查（GET_SIGNING_CERTIFICATES / getCallingPackage 等全數 0 hit）
  • 有 exported=true 的 MainActivity / FileOpenActivity / 兩個 receiver，都未加 permission 保護

7. Manager agent 本機實驗（2026-07-30，Pixel Tablet）

為加深對 Manager agent 的理解，實際 build Viewsonic-EDU/edu-dm-agent-monorepo（develop @ d2e892e1）並跑在非 IFP 裝置（Pixel Tablet）上。

Build 需求

  • monorepo 內 app_aosp（system app、sharedUserId="android.uid.system"，只能裝真 IFP）與 app_edla（Device Owner 模式，一般裝置可裝），共用 applicationId com.viewsonic.dmagent
  • 簽章：repo 根目錄 keystore.properties（debug 也要），用 MVBA_PlatForm.jks（alias platform）——與 mvbf ifp flavor 同一把 key，密碼可沿用 mvbf 的 key.properties
  • VSApi / systemapi 皆為 compileOnly AAR（function/build.gradle.kts:18-24），執行期預期由 IFP 韌體提供
  • Build：./gradlew :app_edla:syncVersion → :app_edla:assembleDevDebug

在非 IFP 裝置跑起來的三個障礙（依序遇到）

#障礙處理（本地 hack，勿 commit）
1 ModelFactory 認不得機型 → ModelType.Undefined fallback 到 vsApiDevice → 韌體沒有 com.viewsonic.vsapi.VSNetworkManager → 啟動即 NoClassDefFoundError ModelFactory.kt:192 改 SystemApiDevice(context, UndefinedDevice(context))（仿 VPC01_AN 先例）
2 WorkerService 啟動 mediaProjection FGS（遠端桌面），需簽章級 CAPTURE_VIDEO_OUTPUT（IFP 平台簽章才有）或 PROJECT_MEDIA appop adb shell appops set com.viewsonic.dmagent PROJECT_MEDIA allow
3 systemapi AAR 的 SelfRegisterReceiver 註冊自訂 broadcast 未帶 RECEIVER_EXPORTED/NOT_EXPORTED flag，targetSDK 36 在 Android 14+ 直接 SecurityException（真 systemapi IFP 是舊 Android 無此檢查；此路徑是 hack #1 引入的） DMService.kt selfReceivers = emptyList() 跳過註冊

結果：EnrollmentActivity 正常起來，可操作 enroll UI（dev 環境）。

對本票的收穫

  • agent 端持有 entityName：DMService.kt:373-378 從 DataStore 收 enrollEntityFlow，內含 entityName + deviceName（來源是 Manager enroll 流程）——與 §4「MVB 讀 agent provider 拿 entity name」互相印證。強化 Q1 疑點：agent 自己就有 entity name，Stephen comment 要 MVB provider 回 entity name 的目的需釐清
  • 同一台 Pixel Tablet 上現有 com.viewsonic.droid（MVB）+ com.viewsonic.dmagent 可跑，之後做 MVB ContentProvider 時可直接在這台驗證 agent → MVB 的讀取路徑
  • ⚠️ 本機 repo（Orgs/Viewsonic-EDU/edu-dm-agent-monorepo）目前帶著 hack #1、#3 兩個未 commit 改動，做正事前先 git stash

8.1 POC v2（2026-07-31）：entity name、即時更新、Pigeon 解耦

三項升級，皆已在 Pixel Tablet 驗證通過。

(a) entity name 持久化

  • _getEntityID() 改回傳 record ({String entityID, String organization})，一併解析後端已回的 organization（兩處呼叫點同步更新）
  • DataStorage 介面 + SecureDataStorage 新增 entityOrganization（Hive key app_entityOrganization）
  • provider 白名單新增 entity_name

(b) 即時更新：notifyChange + ContentObserver

  • MVB 每次鏡射後對 provider URI 呼叫 notifyChange
  • dmagent EnrollmentActivity 註冊 ContentObserver，onChange 重讀並更新 overlay（顯示更新次數／觸發源／時間戳），onDestroy 解除訂閱

演示（pm clear 清空 MVB 資料後）：

10:32:24  MVB 啟動 → 鏡射寫入 → notifyChange → dm onChange ×3

dm 全程在背景、無輪詢——驗證了 contract §8 建議的「NOT_INITIALIZED → 訂閱 → 即時就緒」狀態機。

(c) Pigeon 解耦：不再依賴 shared_preferences 內部格式

問題：v1 的 provider 直接讀 FlutterSharedPreferences 檔與 flutter. 前綴——那是 shared_preferences 套件的實作細節，不是公開合約。 最現實的風險不是套件改名（八年未變），而是我們自己遷移到新 API（SharedPreferencesAsync / SharedPreferencesWithCache 底層改用 Jetpack DataStore，檔案位置與格式全不同） → Dart 寫進新儲存、Java 仍讀舊 XML → silent desync：provider 永遠回舊值且無任何錯誤，dm 拿到過期資料還以為是真的。
檔案內容
pigeons/instance_info_pigeon.dart（新）InstanceInfoData + @HostApi InstanceInfoPlugin.setInfo()（照 repo 既有 pigeon 慣例）
lib/generated/pigeons/instance_info.g.dart、android/.../pigeon/InstanceInfo.javapigeon 產生
android/.../pigeon_impl/InstanceInfoPluginImpl.java（新）寫入自持 prefs instance_info_provider + notifyChange，同一次呼叫完成
InstanceInfoProvider.java改讀自持 prefs；key 常數集中於此供 impl 共用；新增 infoUri()
MainActivity.java改用 InstanceInfo.InstanceInfoPlugin.setUp(...)（移除中繼版的手寫 MethodChannel）
lib/mvb_activator/provider_info_mirror.dart改呼叫 Pigeon，移除 shared_preferences 依賴

裝置驗證：

  • 新檔 shared_prefs/instance_info_provider.xml 出現，內容即 contract key（無 flutter. 前綴）
  • FlutterSharedPreferences.xml 內 provider_info_* 比對數 = 0（新版完全不寫該處）
  • content query 與 dm 即時更新皆與 v1 行為一致

附帶收穫：寫入與通知合併為單次原生呼叫（commit() 同步落地後才 notifyChange），消除 v1「鏡射成功但通知先到」的排序縫隙。

待收尾

  • 簽章 permission（等 Q2 最終確認）；POC 的裸 export 只可留在測試機，正式版 provider 註冊須移至 ifp/edla flavor manifest
  • entity_name 目前為空值缺列——open flavor 在 dev 環境 auto-enroll 未掛 entity（entity_id 同樣為空）。程式路徑已就緒，需以有 entity 的帳號手動 enroll 才能完整驗證
  • 連續多次 onChange（init 期間 mirror() 被呼叫多次）——正式版可在 Dart 側加「值有變才通知」的 debounce
  • 既有安裝殘留的 flutter.provider_info_* 值無害（已無程式讀取），正式 PR 可視需要加一次性清除
  • dmagent repo 本地 hack 累計 4 處（ModelFactory、DMService receiver、POC hook、EnrollmentActivity overlay + observer），勿 commit

9. 實作方向結論

  1. 資料鏡射：Dart 側把 instanceID / entity name 鏡射寫進 FlutterSharedPreferences（鏡射點 secure_data_storage.dart _save()/_load()，POC 已實作），ContentProvider 從 prefs 讀。
  2. entity name 需新增取得與儲存：擴充 _getEntityID() 解析（若後端 response 有 name），或改抓 GET /me/entity——取決於 Q1 答案。
  3. ContentProvider：以 MainActivity.java:1855-1906（讀 dmagent provider）為對稱範本設計 contract（POC 已實作 InstanceInfoProvider.java）。
  4. 存取控制：視 Manager agent 簽章 key（Q2）決定 signature permission 或 runtime SHA-256 allowlist（需支援所有 flavor 的話大概率要走 allowlist）。
