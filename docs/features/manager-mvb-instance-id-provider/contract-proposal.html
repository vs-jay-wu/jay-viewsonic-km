ContentProvider Contract 草案（MVB → Manager agent）

2026-07-30 起草、07-31 補 §7/§8 · 供與 VB-1399 工程師討論用，尚未定案
📘 總覽 (overview) 🛠️ 調查 findings ❓ open questions 📐 contract 草案
設計原則：v1 資料給最小集，但合約形狀按「一定會擴充」設計——之後加欄位是一行 code + 一行文件，不重談合約。
定位原則（2026-07-31）：本 provider 是 read-only 的身分/狀態曝光，不是本地控制通道。 控制面（改設定、下命令）一律維持雲端路徑（Manager 介面 → myViewBoard 後端 → MVB 拉取）； 若未來有「本地即時性」需求，上限是 push-to-pull 通知（dm 本地通知 MVB「去雲端拉最新設定」，值仍以雲端為權威）， 不開放本地寫值——理由：真相源分裂、授權語意弱化（字串護欄 ≠ 雲端 tenancy 檢查）、稽核斷鏈、寫入攻擊面。

1. 合約形狀

  • Authority：<applicationId>.instanceinfo.provider（用 ${applicationId} 前綴避免多 flavor 同裝置衝突；對向先例 com.viewsonic.dmagent.provider 是固定字串，可在會議上對齊）
  • URI：content://<authority>/v1/info
  • Cursor 形狀：key-value 多列（不是固定欄位單列）
columntype說明
keyString資料項目名
valueString值（bool 用 "true"/"false"，int 用十進位字串，缺值列不出現）
  • Agent 以「有哪些列」做 feature detection，遇到不認得的 key 忽略——加 key 不破壞舊 agent
  • 版本演進策略見 §7（2026-07-30 與 Stephen 討論後傾向 key 版本制，path 版本待定）

2. 存取控制

2026-07-31 定向：signature permission。已確認（Jay）provider 只需 ifp/edla flavor 提供，open/store 不管——ifp/edla 與 dmagent 同為 MVBA_PlatForm.jks 簽章，signature 方案成立。
  • 採用方案：MVB 宣告自訂 <permission android:protectionLevel="signature">，provider 掛 android:permission=。系統只將此 permission 授予與 MVB 同簽章的 app——dm（MVBA key）自動取得，第三方 app 安裝時即被拒
  • Flavor 範圍：provider 註冊放 flavor 專屬 manifest（android/app/src/ifp/AndroidManifest.xml、src/edla/），main manifest 不註冊——open/store 上 provider 根本不存在（POC 目前註冊在 main，正式版要搬）
  • 備案（若正式包板 key 不同才啟用）：provider query() 內做 runtime SHA-256 簽章 allowlist（getCallingPackage() + GET_SIGNING_CERTIFICATES）
  • 安全模型備忘：ContentProvider 本身沒有「同簽章才能用」的內建限制——exported=true 未加 permission 時任何 app 皆可 query（POC 即是）；簽章限制是靠 signature-level permission 的授予機制達成

6. 鏡射機制（MVB 內部實作）

2026-07-31 定案：Pigeon + 原生自持儲存（POC v2 已實作驗證，見 findings §8.1）。
  • Dart 側（ProviderInfoMirror）經 Pigeon InstanceInfoPlugin.setInfo(InstanceInfoData) 把白名單欄位交給原生層
  • 原生層（InstanceInfoPluginImpl）寫入自持的 SharedPreferences 檔 instance_info_provider，key 直接等於 contract key（無前綴翻譯），寫入後同一次呼叫內 notifyChange(infoUri)
  • Provider 只讀這個自持檔——對 shared_preferences 套件的內部格式零依賴
  • 鏡射點：SecureDataStorage._save() 與 _load()（_load 也鏡射 → 既有安裝啟動即生效），以及 ITAdminSettings 寫入處（若日後曝光設定值）
  • 未 enroll 時：instance_id 缺列（只回 contract_version），行為與 §8 對齊

為什麼不直接讀 FlutterSharedPreferences（否決 POC v1 做法）

方案評估
直讀 FlutterSharedPreferences + flutter. 前綴 ❌ 依賴套件實作細節而非公開合約。主要風險不是套件改名（八年未變），而是自家遷移新 API（SharedPreferencesAsync 底層改 Jetpack DataStore）→ Dart 寫新儲存、Java 讀舊 XML → silent desync，provider 回過期值且無錯誤
Pigeon + 原生自持儲存（採用） ✅ 合約資料的所有權回到自己手上；key 名即 contract key；型別安全 codegen 且符合 repo 既有 pigeons/ 慣例；寫入與通知併為單次原生呼叫（commit() 後才 notify），消除排序縫隙
Provider 直讀 Hive ❌ Dart 專有 binary 格式，原生層讀不到

邊界說明：Pigeon 呼叫需 Flutter engine 存活——但鏡射本來就只發生在 Dart 執行期，非新增限制；provider 讀取端不需要 engine（冷啟動 query 讀的是已落地的 prefs 檔），未初始化情境不受影響。

entity name 的持久化決策（2026-07-31）

  • 採「持久化 + 鏡射」：_getEntityID() 解析 /{uid}/entity response 時一併取 organization 存 Hive（如 app_entityOrganization），鏡射為 entity_name。後端已回此欄位，零額外請求
  • 否決「query 時打 API 換 name」：provider query 須快速同步（網路呼叫 = ANR）；冷啟動時 Flutter 未跑，Kotlin 重刻 x-vs-key 認證不可取；離線答不出來，護欄失效
  • 否決「只留 name、刪 entity_id」：name 可變（組織改名）、id 是穩定主鍵，角色不同（id 對帳、name 護欄）；且 entityID 有既有用途（analytics），刪除超出 scope
  • 新鮮度補丁：MVB 每次啟動且 activated 時重打 GET /{uid}/entity 更新 Hive + 鏡射 + notifyChange——組織改名的漂移窗口縮到下次啟動前（IFP 幾乎天天重開）

7. 版本演進策略——方案比較（2026-07-31 補充）

背景：Stephen（2026-07-30 口頭）傾向 key 版本制（語意/格式變更 → 新 key 如 instance_id_v2），而非 path 版本（/v1 → /v2）。以下為完整比較：

方案做法優點缺點
A. Path 版本 破壞性變更開 /v2/info 整份合約切版清楚；能處理 cursor shape 本身的變更 粒度太粗——改一個欄位就要整版切換；遷移期 agent 要同時支援兩個 path
B. Key 版本（Stephen） 變更 = 新 key（instance_id_v2），舊 key 保留 粒度細；新舊值並存於同一回應，agent 可逐欄位、無痛遷移；實作零成本 key 命名空間隨時間累積雜訊；「哪個是現行版」要靠文件；無法處理 shape 變更
C. 回傳值帶版本（contract_version row） 任何合約變更 bump 整數 agent 一行 log 即可診斷「對面是哪一版」；便於客服/除錯 單靠它不夠——版本號不等於能力，agent 仍要維護「版本 → 差異」對照
D. Cursor 加 version 欄 每列自帶欄位版本（key, value, version） 欄位級版本顯式 與 B 功能重複（新 key 名本身就是版本宣告），徒增合約複雜度
E. Presence-based（純能力偵測） agent 只看「row 存在與否」，無版本概念 KV 形狀天生支援，最簡 對「同 key 改值定義」無解——正是 Stephen 擔心的 case

建議：B 為主幹 + C 輔助 + 三條紀律（B/C/E 不互斥）

  1. Published key 永久凍結——一旦發布，語意與格式不再變。要改 → 新 key（instance_id_v2，或更好的做法：取語意化名稱，如假設 v2 是改成 UUID 格式，命名 instance_uuid 比 _v2 自我描述）
  2. 舊 key 進 deprecation 週期——文件標註 deprecated + 預告移除版本，等 agent 全面遷移後才移除
  3. contract_version 保留——任何 key 新增/棄用都 bump，僅供 log 與除錯，agent 不得拿它做行為分支（行為分支一律用 presence 偵測，方案 E）
  4. Path 固定單一 /info（對 Stephen 的方向讓步），但文件保留「cursor shape 若真要變 → 新 path」作為逃生門——shape 變更是 key 版本制唯一蓋不住的洞

8. instance_id 空值（MVB 未初始化）處理——方案比較（2026-07-31 補充）

關鍵事實（決定了方案取捨）

  1. instance ID 不只是識別碼：它是 MVB 後端的 identity key，參與認證加密（x-vs-key）、MQTT topic、enroll——所有權在 MVB，產生演算法（md5(ts+androidId+uuid)）是其內部細節
  2. MVB 沒啟動過 → instance ID 不存在 → 後端也沒有這個 instance → Manager 雲端根本沒有可對應的 Software Instance 頁。所以「空」是語意正確的狀態（「這台裝置尚無 MVB instance」），不是錯誤
  3. query 未啟動 app 的 provider 會拉起其 process（Android 標準行為），provider 能回應——但 Flutter/Dart 未跑、鏡射未發生，所以回傳只有 contract_version 一列。這天然就是「未初始化」的訊號
  4. IFP 實務上 MVB 常設開機自啟（BootReceiver + app_startAppAtBootUp），「從未啟動」的窗口很小，但仍必須定義行為

方案比較

方案說明評估
(1) 空值 → dm 報錯 agent 讀到空就 error ❌ 原樣不可取——「空」是合法狀態非錯誤；但改良版是正解，見下
(1′) 空值 → dm 回報狀態 + 訂閱變更 agent 把空值視為 NOT_INITIALIZED 狀態回報雲端；MVB 鏡射時 notifyChange(uri)，agent 用 ContentObserver 訂閱、免輪詢 ✅ 建議方案：語意正確、實作最小、完整涵蓋舊版相容（見狀態表）
(2a) dm 生成後回寫 mvbf dm 產 ID 寫入 MVB 儲存 ❌ 強烈反對：(i) 所有權倒置——外部 app 操縱 MVB 的認證身分材料，嚴重安全問題；(ii) 產生演算法是 MVB 內部細節，dm 無從正確生成；(iii) race——dm 寫入後 MVB 首啟又自己生成，衝突；(iv) 恰恰無法解決舊版相容：舊版 MVB 沒有回寫介面，而它正是最需要 fallback 的對象
(2b) 雙 ID + 後端 mapping dm 與 MVB 各持 ID，後端對應 ⚠️ 不需要「第二個 instance ID」——輕量版早已存在：dm 本來就有自己的裝置身分（serial number，enroll 於 Manager 雲端）。只要把 mvb_instance_id 當作 dm 裝置紀錄上的 nullable 屬性回報，mapping 天然就在 Manager 後端，無需新機制
(3) dm 觸發 MVB 初始化 MVB 加一個受簽章保護的「ensure initialized」入口（broadcast/service），dm 呼叫後 MVB 背景產生 instance ID ⚠️ 可作 phase 2：解「零接觸部署後立即要看到 instance」需求；但同樣需要新版 MVB（對舊版無效），且多數 IFP 開機自啟已覆蓋此場景
