ContentProvider Contract 草案（MVB → Manager agent）

2026-07-30 起草、07-31 補 §7/§8 · 供與 VB-1399 工程師討論用，尚未定案
📘 總覽 (overview) 🛠️ 調查 findings ❓ open questions 📐 contract 草案
設計原則：v1 資料給最小集，但合約形狀按「一定會擴充」設計——之後加欄位是一行 code + 一行文件，不重談合約。
定位原則（2026-07-31）：本 provider 是 read-only 的身分/狀態曝光，不是本地控制通道。 控制面（改設定、下命令）一律維持雲端路徑（Manager 介面 → myViewBoard 後端 → MVB 拉取）； 若未來有「本地即時性」需求，上限是 push-to-pull 通知（dm 本地通知 MVB「去雲端拉最新設定」，值仍以雲端為權威）， 不開放本地寫值——理由：真相源分裂、授權語意弱化（字串護欄 ≠ 雲端 tenancy 檢查）、稽核斷鏈、寫入攻擊面。

1. 合約形狀

  • Authority：com.viewsonic.droid.instanceinfo.provider（POC 以 ${applicationId} 前綴寫成；現況兩種寫法字串完全相同，見下方註記。對向先例 com.viewsonic.dmagent.provider 是固定字串，可在會議上對齊慣例）
  • URI：content://<authority>/v1/info
    ⚠️ /v1 不代表採用「path 版控」——它是命名空間標記，日常不會變。加欄位／改語意一律走 §7 的 key 版本制；只有 cursor shape 本身變更（key-value 兩欄改成別的形狀）才會出現 /v2/info。保留版本段是為了讓那個逃生門有乾淨的命名。
  • Cursor 形狀：key-value 多列（不是固定欄位單列）
columntype說明
keyString資料項目名
valueString值（bool 用 "true"/"false"，int 用十進位字串，缺值列不出現）
  • Agent 以「有哪些列」做 feature detection，遇到不認得的 key 忽略——加 key 不破壞舊 agent
  • 版本演進策略見 §7（2026-07-30 與 Stephen 討論後傾向 key 版本制，path 版本待定）
📌 ${applicationId} 前綴 vs 固定字串——實質差異為零（2026-08-14 查證）
mvbf 的 applicationId "com.viewsonic.droid" 宣告在 defaultConfig，四個 flavor（ifp/edla/open/store）都沒有自己的 applicationId 或 applicationIdSuffix（android/app/build.gradle:137；beta 環境也只換 appLabel/appIcon，package 不變）。因此：
  • 「多 flavor 同裝置共存」不會發生——同 applicationId 的 app 在 Android 上無法並存。先裝 edla 再裝 ifp 是覆蓋（兩者同 MVBA_PlatForm.jks，覆蓋成功、只有一份 provider）；跨簽章（如 edla → open）則安裝直接被拒（INSTALL_FAILED_UPDATE_INCOMPATIBLE）。兩種情況都不會有兩份 provider，也就沒有 authority 衝突
  • 前綴的真正用途：Android 要求 provider authority 全裝置唯一（兩個 app 宣告同 authority → 後安裝者 INSTALL_FAILED_CONFLICTING_PROVIDER），拿 package name 當前綴是官方保證唯一的慣例——與 flavor 無關
  • 唯一的實質差異在未來假設：若哪天真的加 applicationIdSuffix（例如要讓 beta 與正式版並存），${applicationId} 會讓 authority 跟著變，而 dm 端 query 是硬編字串 → 反而讀不到。這個情境下固定字串對 dm 更穩定
  • 結論：現況兩種寫法產出的字串一模一樣（com.viewsonic.droid.instanceinfo.provider），選擇僅是慣例對齊問題，不是正確性問題

2. 存取控制

❗ 2026-08-14 定案改寫：改以 runtime SHA-256 allowlist 為主要防線（原「signature permission + 只做 ifp/edla」方案作廢）。 觸發原因：Evis Cheng 確認「Manager 都要簽 system key」，而 A31 上的 mvbf 是 store flavor（Google Play key）—— A31 因此是「dm 在、mvbf 非平台簽章」的真實交集，protectionLevel="signature" 在該裝置必然失效，且 store flavor 必須支援。 詳見 open questions Q2。
flavormvbf keydm keyprotectionLevel="signature"
ifp / edlaMVBA_PlatForm.jks同一把✅ 成立
store（A31）Google Play keyMVBA_PlatForm.jks❌ 失效（跨 key）
  • 採用方案：provider query() 內做 runtime 檢查——getCallingPackage() 取呼叫端，以 PackageManager.hasSigningCertificate(pkg, sha256, CERT_INPUT_SHA256) 比對 MVBA_PlatForm.jks 憑證的 SHA-256 allowlist。單一機制、全 flavor 行為一致
  • 為何不做混合方案（ifp/edla signature + store runtime）：兩套機制＝兩條測試路徑卻換不到安全性。而且 runtime 檢查比 signature permission 更嚴——signature permission 授予所有同簽章 app（IFP 上平台簽章的 ViewSonic app 不只 dm），runtime 則釘住 package + 憑證。改用 runtime 是收緊不是降級
  • Flavor 範圍：provider 註冊維持在 main manifest（全 flavor）——安全性由 runtime gate 保證，而非靠 manifest 分 flavor；也免掉「將來發現 A31 其實走 open flavor」之類的意外。（原計畫「搬到 src/ifp/、src/edla/」作廢）
  • signature permission 可在 ifp/edla 額外掛著當 defense-in-depth（零成本），但不是主要防線，不得作為 store 上的替代
  • 「OEM board-flash 是否另外重簽」已排除，不需詢問（2026-08-17）：dm 只有一條 packing pipeline、一把 keystore、單一 APK，卻要跨 CVTE/KTC/ATop/OStar 等所有機型；而 app_aosp 宣告 sharedUserId="android.uid.system"——這要求它必須用該裝置韌體的平台 key 簽章。單一 APK 能在所有機型當 system app，反推 MVBA_PlatForm.jks 就是 ViewSonic IFP 韌體的平台 key。若真被重簽成別把 key，dm 自己就裝不成 system app
  • 實作陷阱：
    • 用 hasSigningCertificate() 而非自行比對 GET_SIGNING_CERTIFICATES——它會正確處理簽章輪替的歷史憑證。API 28 起可用，mvbf minSdk = 30（android/build.gradle:19）無虞
    • getCallingPackage() 可能回 null（非直接 binder 路徑）→ null 即拒絕；保險可再用 Binder.getCallingUid() + getPackagesForUid() 交叉驗證
    • allowlist 做成憑證集合（set）而非單一常數——不是懷疑目前有第二把 key，而是簽章輪替本來就可能發生；做成 set 的成本是零，將來要加不必改結構
  • 安全模型備忘：ContentProvider 本身沒有「同簽章才能用」的內建限制——exported=true 未加保護時任何 app 皆可 query（POC 即是）

3.1 只給 entity_id、不給 entity_name（2026-08-17 會議定案）

✅ 決議：provider 只提供 entity_id。 entity_id ↔ organization 在後端是 1:1，而 entity_id 是穩定主鍵（組織改名不變）、零網路、既有安裝的 Hive 早已存著。

🎉 這個決定消掉了一整串複雜度

原本必須做的事現在
_getEntityID() 改回傳 record、一併解析 organization❌ 不用做
DataStorage / SecureDataStorage 新增 entityOrganization（Hive key app_entityOrganization）❌ 不用做
每次啟動重打 GET /{uid}/entity 做 backfill（既有安裝的 entity_name 永久為空問題）❌ 整個問題消失——entity_id 早就在 Hive 裡
refresh「只在成功時覆寫」的 guard（一次網路失敗會清空既有值）❌ 不需要（沒有 refresh 就沒有這個坑）
「MVB 曾離線啟動 → 只有 id 沒有 name」的 edge case❌ 不存在

換言之，Q1 延伸 (a) 記錄的那個「最嚴重的實作坑」——既有安裝升級後永遠補不上值——因為這個決議而不再存在。

⚠️ 一個推論：護欄的比對位置移到雲端

dm 端目前只存 entityName、沒有 entity_id（EnrollEntity.kt:3：data class EnrollEntity(val entityName: String, val deviceName: String)）。 因此 provider 只給 entity_id 時，dm 無法在本地完成 Aaron 原先描述的「與自己持有的 entity name 比對」——該比對必然落在雲端（Manager 後端有 entity 表，resolve 得了 id）。
這與我們原本的建議一致（權威 tenancy 檢查本就該留在雲端，見 findings §2.1），也讓「本地字串護欄 ≠ 安全邊界」的顧慮自然消失。
✅ 已確認（2026-08-17 會議，Manager team 同意）：dm 走雲端用 entity_id 換 name，本地不做 entity 比對。

3.2 錯誤回報（error_code / error_message）——2026-08-17 會議新增

做法：錯誤以資料列回傳，不丟 exception、不回 null。 cursor 仍帶 contract_version，另加 error_code（＋選配 error_message），且不回任何資料列。
dm 以 error_code 的 presence 判斷這次 query 是否失敗——與合約既有的 presence 偵測紀律一致，無需新機制。
❗ 最重要的一條紀律：「資料還沒有值」不是錯誤，不可回 error_code。 未初始化／未 enroll 是語意正確的合法狀態（見 §8），表現方式是該列不出現而非錯誤。 若把它當錯誤回報，dm 會把正常的部署過程當成故障上報雲端——製造大量假警報。

為何不用其他傳遞方式

方式評估
丟 exception❌ 跨 binder 只有少數 exception 型別能正確傳遞；且會迫使 dm 用 try/catch 處理正常分支。例外：SecurityException 是 Android 對權限拒絕的慣例，但我們用 cursor row 更一致、且能附帶原因
回 null cursor⚠️ 保留給「provider 不存在／完全無法回應」——dm 需要靠它區分「舊版 MVB 沒這個 provider」。若錯誤也回 null，這兩件事就分不開了
Cursor.setExtras() Bundle⚠️ 可行且是正式 API，但比資料列難發現、也與現有 key-value 形狀不一致
error 資料列（採用）✅ 沿用既有形狀與 presence 紀律；dm 端零新概念

v1 錯誤碼（字串，非數字）

error_code何時發生dm 應如何反應
UNAUTHORIZED 呼叫端未通過 package ＋ 憑證檢查（§2） 回報異常。實務上最常見於開發期——用非 MVBA key 簽的測試包會落在這裡，明確的錯誤碼可省下大量排查時間（若回 null 會被誤認為「provider 不存在」）
UNSUPPORTED_URI path 不是 /v1/info 檢查是否用了未來版本的 path（見 §7 逃生門）
STORAGE_ERROR provider 讀自持 prefs 失敗（檔案損壞等） 回報異常並重試；非「未初始化」

為何用字串而非數字：自我描述、不必維護對照表、log 直接看得懂——與 key 版本制「取語意化名稱」的原則一致。新增錯誤碼時舊 dm 只會看到不認得的字串，應一律視為「未知錯誤」而非崩潰。

回傳範例

// 正常（已 enroll）
contract_version | 1
instance_id      | 8E28AD2200B4D06A06E456FB70C45B4F
entity_id        | 3327

// 正常（尚未初始化）—— 注意：這不是錯誤，只是列不出現
contract_version | 1

// 錯誤（未授權）
contract_version | 1
error_code       | UNAUTHORIZED
error_message    | caller signature mismatch

⚠️ error_message 內容不列入合約穩定性保證（措辭可隨時調整），因此 dm 只能寫 log、不可解析。

5. 明確排除（機敏，不給）

⚠️ 判準原則：「UI 上看得到」不等於「可以透過 provider 提供」。 Settings > About 其實也顯示 email（about_list_view_bloc.dart:53-56），但它明確排除於本合約——這兩件事不衝突，因為兩種暴露性質不同：
螢幕顯示provider

6. 鏡射機制（MVB 內部實作）

2026-07-31 定案：Pigeon + 原生自持儲存（POC v2 已實作驗證，見 findings §8.1）。
  • Dart 側（ProviderInfoMirror）經 Pigeon InstanceInfoPlugin.setInfo(InstanceInfoData) 把白名單欄位交給原生層
  • 原生層（InstanceInfoPluginImpl）寫入自持的 SharedPreferences 檔 instance_info_provider，key 直接等於 contract key（無前綴翻譯），寫入後同一次呼叫內 notifyChange(infoUri)
  • Provider 只讀這個自持檔——對 shared_preferences 套件的內部格式零依賴
  • 鏡射點：SecureDataStorage._save() 與 _load()（_load 也鏡射 → 既有安裝啟動即生效），以及 ITAdminSettings 寫入處（若日後曝光設定值）
  • 未 enroll 時：instance_id 缺列（只回 contract_version），行為與 §8 對齊

鏡射的成本與時機——dirty check + 移出啟動關鍵路徑（2026-08-14 定案）

原則：provider 曝光是旁路關注點（side concern），不進 app 初始化序列。 對啟動關鍵路徑的增加成本要是 0，不是「小」。

(a) set 路徑：mirror 是既有成本的零頭

_save() 現況已是「開 box → 7 次 put() → 關 box」（secure_data_storage.dart）。多一個 mirror＝1 次 platform channel + 1 個小 XML 寫，相對既有成本是零頭，且為 O(1) 固定成本——不隨資料量或啟動次數增長，不存在「越來越慢」的機制。（結構比較，未實測數字。）

(b) ⚠️ _load() 的無條件鏡射應改為 dirty check

POC 在 _load() 無條件寫一次，而其中約 99.9% 是寫入完全相同的值——一個永遠在跑、幾乎永遠沒用的動作。改成「先讀回 prefs 比對，值有變才寫 + 才 notifyChange」：

情境成本
穩態啟動（絕大多數）1 次小檔 prefs 讀取，零寫入、零 notifyChange
舊版升級 backfill（見 Q1 延伸 (a)）第一次啟動寫一次，之後不再寫
enroll / entity 更新正常寫 + 通知（真事件，本來就該做）

附帶解掉 findings 待收尾的「連續多次 onChange」——原本列為 nice-to-have 的 debounce，其實是讓 _load() 鏡射站得住腳的前提條件。

(c) mirror 移出初始化關鍵路徑

  • dm 是非同步讀且有 ContentObserver 訂閱——不在乎 instance_id 是啟動後 50ms 或 3 秒才就緒
  • → mirror 掛在第一帧之後（post-frame callback / post-init microtask），啟動關鍵路徑增加成本 = 0
  • 代價：冷啟動後有短窗口 provider 尚無值——已被 §8 的 NOT_INITIALIZED + ContentObserver 狀態機涵蓋，無功能退化。當初為「舊版/未啟動」設計的狀態機，順便讓這個延後合法化

為什麼不直接讀 FlutterSharedPreferences（否決 POC v1 做法）

方案評估
直讀 FlutterSharedPreferences + flutter. 前綴 ❌ 依賴套件實作細節而非公開合約。主要風險不是套件改名（八年未變），而是自家遷移新 API（SharedPreferencesAsync 底層改 Jetpack DataStore）→ Dart 寫新儲存、Java 讀舊 XML → silent desync，provider 回過期值且無錯誤
Pigeon + 原生自持儲存（採用） ✅ 合約資料的所有權回到自己手上；key 名即 contract key；型別安全 codegen 且符合 repo 既有 pigeons/ 慣例；寫入與通知併為單次原生呼叫（commit() 後才 notify），消除排序縫隙
Provider 直讀 Hive（原生自刻 parser） ❌ 與否決直讀 FlutterSharedPreferences 同一個理由：Hive 是 append-only frame log（同 key 多筆取最後、tombstone、CRC32、compaction 重排），屬套件 undocumented 內部格式，自己刻 parser 等於逆向且隨升版可能失效。
⚠️ 注意措辭：不是「原生讀不到檔案」——檔案同 app-private 目錄、同 uid 完全存取得到，缺的是格式解析（實機驗證見 findings §1.1）
Provider 於 query() 內起 headless Flutter engine 讀 Hive
（＝「不鏡射、要用時才現讀」）		 ❌ 會阻塞呼叫端——見下方 §6.2

邊界說明：Pigeon 呼叫需 Flutter engine 存活——但鏡射本來就只發生在 Dart 執行期，非新增限制；provider 讀取端不需要 engine（冷啟動 query 讀的是已落地的 prefs 檔），未初始化情境不受影響。

entity name 的持久化決策 2026-08-17 整段作廢

❌ 本節規劃的工作全部不需要：會議定案 provider 只給 entity_id。見 §3.1。
  • 不需擴充 _getEntityID() 解析 organization / 改回傳 record
  • 不需在 DataStorage 新增 entityOrganization（Hive app_entityOrganization）
  • 不需「每次啟動重打 GET /{uid}/entity」的 refresh／backfill，連帶也不需要它必須配的「只在成功時覆寫」guard
entity_id 既有安裝的 Hive 早已存著——直接鏡射即可，零網路、零額外請求。

保留供追溯的兩個論點（其中第二點正是本次決議選 id 的依據）：

  • 否決「query 時打 API 換 name」：provider query 須快速同步返回（網路呼叫 ＝ 阻塞呼叫端／ANR）；冷啟動時 Flutter 未跑，而認證在 Dart 側
  • 「name 可變、id 是穩定主鍵」：組織改名會動到 name，不會動到 id——這正是只給 id 更穩健的理由

6.2 為什麼不能「不鏡射、query 時才用 Dart 現讀 Hive」（2026-08-17）

常見的追問：既然 §8.1 (3″) 可以 headless 跑 Dart，那 provider 何不在 query() 時直接起 engine 讀 Hive？這樣就一份資料、沒有同步問題。答案是不行，理由與拒絕「query 時打 API」相同，且更嚴重。

⚠️ 先修正一個常見誤解：沒有「只啟動 Dart、不啟動 Flutter」這種選項。 本 codebase 的 Dart VM 內嵌在 Flutter engine 內；headless 指的是「engine 照常啟動、但不掛 UI（無 FlutterActivity／render surface）」，不是更輕量的 runtime。啟動成本仍是完整 engine 啟動（數百 ms～數秒＋記憶體），省下的只有畫面。
#阻礙
1 query() 是同步 binder 呼叫，呼叫端會被阻塞。流程會變成：dm 呼叫 → MVB 起 engine（數百 ms～數秒）→ 開 Hive → 回傳，dm 全程卡住，ANR 風險落在對方身上
2 provider 可能在冷進程被喚起——ContentProvider.onCreate() 執行於 Application.onCreate() 之前，在該時點拉起 Flutter engine 既重且脆弱
3 若 engine 已在跑，query 需跨執行緒等 Dart isolate 回應，而 isolate 可能正忙 → 延遲不可控，並有 deadlock 風險

→ provider 必須從原生可直接讀取的儲存同步服務。鏡射不是為了方便，是為了讓 query() 能在毫秒內返回。

那「同步問題」現在有多嚴重？

  • 鏡射發生在 _save() 與 _load() 兩處，且 POC v2 已把「寫入 + notifyChange」合併為單次原生呼叫（commit() 落地後才通知）
  • → 只要 Dart 跑過，兩邊即一致。這是「每次 Dart 執行就收斂」的最終一致性，對「provider 提供快照」這個用途足夠
  • → 唯一的分歧窗口是「Hive 有值但 Dart 從未跑過」（升級後未開啟），而 §8.1 (3″) 正是為它設計

若真要「一份資料」，方向是反過來（v1 不建議做）

讓原生 prefs 成為這幾個欄位的唯一真相源，Dart 也改經 Pigeon getter 讀它、不再寫 Hive。確實能消除同步問題，但代價：

  • SecureDataStorage 仍存 email／whiteboardName／analytics 等欄位，Hive 不會消失，只是部分欄位搬家——複雜度未降反升
  • 遷移本身仍需 Dart 跑一次，同樣的雞生蛋沒有解掉
  • Dart 每次存取都要過 platform channel，比現行的記憶體快取難用

結論：維持鏡射。純度不值得這個重構，唯一的破口已由 (3″) 兜住。

7. 版本演進策略——方案比較（2026-07-31 補充）

背景：Stephen（2026-07-30 口頭）傾向 key 版本制（語意/格式變更 → 新 key 如 instance_id_v2），而非 path 版本（/v1 → /v2）。以下為完整比較：

方案做法優點缺點
A. Path 版本 破壞性變更開 /v2/info 整份合約切版清楚；能處理 cursor shape 本身的變更 粒度太粗——改一個欄位就要整版切換；遷移期 agent 要同時支援兩個 path
B. Key 版本（Stephen） 變更 = 新 key（instance_id_v2），舊 key 保留 粒度細；新舊值並存於同一回應，agent 可逐欄位、無痛遷移；實作零成本 key 命名空間隨時間累積雜訊；「哪個是現行版」要靠文件；無法處理 shape 變更
C. 回傳值帶版本（contract_version row） 任何合約變更 bump 整數 agent 一行 log 即可診斷「對面是哪一版」；便於客服/除錯 單靠它不夠——版本號不等於能力，agent 仍要維護「版本 → 差異」對照
D. Cursor 加 version 欄 每列自帶欄位版本（key, value, version） 欄位級版本顯式 與 B 功能重複（新 key 名本身就是版本宣告），徒增合約複雜度
E. Presence-based（純能力偵測） agent 只看「row 存在與否」，無版本概念 KV 形狀天生支援，最簡 對「同 key 改值定義」無解——正是 Stephen 擔心的 case

先釐清：這份合約裡有三個不同的「版本」概念

最常見的誤讀是把 URI 的 /v1 和回傳裡的 contract_version 當成同一件事。它們正交，管的東西不同。
path /v1contract_version 那一列key 名稱本身
管什麼回傳的結構形狀（兩欄 key/value、多列）診斷用流水號個別欄位的語意與格式
何時變shape 改變時（幾乎不會）任何 key 新增／棄用就 +1該欄位語意或格式改變時
怎麼變/v1/info → /v2/info1 → 2 → 3新增 instance_uuid，舊 key 保留
可否做行為分支✅ 可（不同 path ＝ 不同解析器）❌ 絕對不可✅ 以 presence 偵測
預期頻率幾乎不變偶爾少

比喻：path ＝ 這份文件是 CSV 還是 JSON（格式）；contract_version ＝ 文件角落的版次編號（對帳用，看不出改了什麼）；key ＝ 文件裡有哪些欄位（內容）。

為何 contract_version 不能做判斷：它告訴你的是身分不是能力——版本號本身不指出哪個 key 變了。更麻煩的是反向情況：entity_id 可能因執行期原因缺席（尚未 enroll），此時 contract_version 完全沒變，靠它判斷就會誤以為讀得到。presence 才是唯一可靠訊號。

三者正交：實務上最可能的情形是 contract_version 一路 1→2→3→4，而 path 永遠停在 /v1。

建議：B 為主幹 + C 輔助 + 三條紀律（B/C/E 不互斥）

📖 會議展示用的具體範例（v1 → v2 加欄位 → v3 改格式的時間線、dm 端讀法程式碼、反例對照）見 open questions Q4 範例。
  1. Published key 永久凍結——一旦發布，語意與格式不再變。要改 → 新 key（instance_id_v2，或更好的做法：取語意化名稱，如假設 v2 是改成 UUID 格式，命名 instance_uuid 比 _v2 自我描述）
  2. 舊 key 進 deprecation 週期——文件標註 deprecated + 預告移除版本，等 agent 全面遷移後才移除
  3. contract_version 保留——任何 key 新增/棄用都 bump，僅供 log 與除錯，agent 不得拿它做行為分支（行為分支一律用 presence 偵測，方案 E）
  4. Path 維持 /v1/info 不動——/v1 只是命名空間標記，不作為日常演進機制：加欄位、改語意一律走 key 版本制（紀律 1），/v1 完全不變。
    只有 cursor shape 本身要變（例如從 key-value 兩欄改為一列多欄）才 bump 到 /v2/info——這是 key 版本制唯一蓋不住的洞，也是保留版本段的用意。
    ⚠️ 2026-08-17 更正措辭：本條原寫「Path 固定單一 /info」，與 §1 及 POC 實作的 /v1/info 不一致。實作是對的——帶著 /v1 讓逃生門更乾淨（否則 shape 變更時得取 /info2 這類醜名字）。

8. instance_id 空值（MVB 未初始化）處理——方案比較（2026-07-31 補充）

關鍵事實（決定了方案取捨）

  1. instance ID 不只是識別碼：它是 MVB 後端的 identity key，參與認證加密（x-vs-key）、MQTT topic、enroll——所有權在 MVB，產生演算法（md5(ts+androidId+uuid)）是其內部細節

  3. query 未啟動 app 的 provider 會拉起其 process（Android 標準行為），provider 能回應——但 Flutter/Dart 未跑、鏡射未發生，所以回傳只有 contract_version 一列。這天然就是「未初始化」的訊號
  4. ⚠️ 2026-08-17 更正：「從未啟動」的窗口可能不小。 早期版本寫「IFP 實務上 MVB 常設開機自啟，窗口很小」——此宣稱無根據：app_startAppAtBootUp 預設為 false（app_preference_settings.dart:70；BootReceiver.java 讀取時 default 亦為 false），是使用者自行在 Settings > System Config 開啟的選項（system_config_list_view.dart:261,268），我們沒有現場開啟率的資料。
    真正縮小窗口的是「總會有人打開白板來用」——但這個假設恰在本功能最有價值的場景失效：IT 零接觸批次部署（例如一次上架 100 台，尚無人到機器前操作）時 instance ID 全都不存在。

(3″) MVB 開 headless 初始化觸發點——唯一同時滿足「不彈 UI」+「全 flavor」+「所有權正確」

MVB 提供受簽章保護的 BroadcastReceiver／Service，dm 送 intent 後 MVB 在背景跑自己的 ensureInitialized() + auto-enroll，不彈任何畫面。

🔑 關鍵：不需要原生判斷「是否已初始化」，也不需要任何 flag。
dm 只負責送觸發訊號；決策者是 Dart，而 Dart 讀得到 Hive。既有程式碼本來就是 idempotent： 
// mvb_activator.dart:94-104
static Future ensureInitialized() async {
  if (mvbActivator.getInstanceID().isEmpty) {   // ← 值來自 Hive
    ...產生並寫入
  }
}
因此「Hive 有值但 prefs 沒值」（新版已安裝但從未開啟）這個最棘手的情境會自動走到正確結果：
  1. dm query provider → 無 instance_id → 送觸發
  2. MVB headless 醒來 → Dart _load() 讀 Hive → 發現已有值 → 不重新產生 → 鏡射寫入 prefs → notifyChange
  3. dm 再讀 → 拿到原本那個正確的 id
該情境退化成「補做一次鏡射」，不會生出第二個身分、無 race。
對照 (2a)「dm 代寫 prefs」為何無解：那裡的決策者是 dm，而 dm 只看得到 prefs——看到空的就以為要初始化，於是在「Hive 有值」時憑空生出第二個身分。 舊身分已在後端註冊、有 entity 關聯與歷史；prefs 優先則拋棄既有身分（雲端該筆 instance 記錄變孤兒），Hive 優先則 dm 已把錯的 id 報給雲端。
「MVB 開啟時寫 flag」的 workaround 救不了它——flag 同樣是原生寫的、同樣反映不出 Hive 狀態，除非 Dart 跑過才寫得對，又回到同一個雞生蛋。

先回答核心問題：「能不能不啟動就完成初始化？」（2026-08-17 定論）

必須先拆解「啟動」的三個層次，答案才明確：
層次能否避免
① 啟動 UI（白板畫面彈出）✅ 可以避免
② 拉起 process❌ 無法避免，但使用者無感
③ 執行 Dart 程式碼❌ 無法避免
③ 是硬限制：instance_id 的演算法在 Dart、儲存在 Hive（Dart 專有格式）、後端註冊亦在 Dart。 沒有任何方法能在「MVB 程式碼從未執行」的前提下產生合法的 instance_id——該值的定義與所有權都在 MVB 手上（這也是否決 (2a) dm 代寫 的根本理由）。
→ 結論：UI 可以不啟動，但 Dart 一定要跑一次。

結論：MVB 端不需要任何額外的通知設計（現有 notifyChange 已足夠）；要補的是 dm 端「別只靠 ContentObserver」的紀律。不加跨後端通知。

三種選項的釐清

選項評估
(a) MVB set 時本地通知 dm
notifyChange + ContentObserver		 ✅ 已實作並實測（POC v2，實測 update #6）。成本＝一行，且在同一次 Pigeon 呼叫內與寫入一起完成。保留
(b) 靠既有 enroll 流程就好 ⚠️ 概念錯位：enroll 是 MVB 端寫入的時機（本來就是這樣做），但 dm 觀察不到 enroll 事件——它只看得到 provider。所以 (b) 不是 (a) 的替代品
(c) enroll 後由後端通知 dm ❌ 不需要且應避免。這正是 overview §3.3 理由 #4「組織耦合」要避開的：provider 方案的主要優點就是兩邊後端 schema 都不動、無需後端對後端呼叫；加這條就把優點還回去，換到的只有延遲，而延遲已被 (a) 解掉

⚠️ notifyChange 的限制——為什麼 push 不能是唯一機制

  • notifyChange 不會喚醒沒在跑的 process，通知也不會排隊。若 MVB 寫入的那一刻 dm 未註冊 observer（process 被殺、開機順序較晚、observer 尚未 register），該次通知永久遺失
  • 反直覺但關鍵：「變更很少」讓 fallback 更重要，不是更不重要。instance_id 產生一次幾乎不再變、entity 只在 enroll／改名時變——下次變更可能是幾個月後。一次遺失的通知不會被後續變更自動修正，那台機器就一直對不上

ContentObserver 的成本與定位

registerContentObserver(uri, false, observer) 不是輪詢——沒有計時器、沒有自己的背景執行緒，註冊只是在系統 ContentService 留一筆記錄。

狀態成本
閒置（無變更）≈ 0——system_server 內一筆註冊記錄 ＋ 一個 binder reference
收到 notifyChange一次回呼 ＋ dm 重新 query（毫秒級）

→ 「值很少變」不構成反對理由：閒置成本為零的機制不會因閒置而浪費。真正的成本來自通知過於頻繁（POC init 期間連續多次 onChange），已由 §6.1 dirty check 解決；加上之後穩態幾乎不會觸發。

定位：延遲優化，不是正確性機制。它唯一真正派上用場的時刻，剛好是整個功能最關鍵的一次轉換——NOT_INITIALIZED → 取得 instance_id。每台機器一生只發生一次，但那一次決定對應建不建得起來。

建議做法（dm 端分層）

  1. 保留 notifyChange（MVB 端已完成）——一行、與寫入同一次 Pigeon 呼叫內完成
  2. 優先建議 dm 用 JobScheduler 的 TriggerContentUri，而非單純 ContentObserver： 
    new JobInfo.Builder(id, componentName)
    .addTriggerContentUri(new JobInfo.TriggerContentUri(uri, 0))
    .build();
    系統代為監看該 URI，變更時主動拉起 JobService——即使 dm 當下沒在執行。這正好補上 ContentObserver「process 沒跑就永久遺失」的缺口，而本情境（一次性、可能發生在 dm 未執行時）恰恰如此。
    代價：有批次延遲（可用 setTriggerContentMaxDelay 調整），且 force-stop 後失效——但「等一次初始化」延遲數秒完全可接受
  3. dm 在組 static_info payload 時現讀 provider——最終正確性保證：雲端每次詢問都會自我修正，遺失的通知不會累積成永久錯誤。且 instance_id 語意上就屬於 static_info，不需新機制，只是既有 payload 多一個欄位
  4. ContentObserver 作為 dm 前景執行時的即時加分項（可選）
  5. 不碰後端
📌 dm 的回報管線實情（2026-08-14 查證，修正早期誤述）：static_info / dynamic_info 是 MQTT command handler——雲端下指令、dm 回答（DynamicInfoCommandHandler.kt、InfoDispatcher.kt:74、Config.kt:103-105），不是本地週期回報。 dm 的 PeriodicWorkRequest 僅有 OTA／MQTT 重連（小時級）與 location（天級）（WorkerController.kt:32-58）。 早期文件曾寫「dm 本來就有週期回報（dynamic_info / 180s）」——該敘述有誤。這不影響建議：雲端問的時候現讀 provider，效果與週期回報等價。
