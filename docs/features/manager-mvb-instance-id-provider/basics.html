這份文件是什麼

做這張票的過程中冒出來的基礎 Android／Flutter 觀念，集中放這裡。 每一則都用本票的實際情境當例子，這樣不是背定義，而是知道「它在我們的架構裡是哪一塊」。

邊界：決策與查證結果寫在 findings／contract； 這裡只放「通用知識」——換一張票也還是對的東西。

1. Process 與 IPC

1.1 IPC / Binder

IPC = Inter-Process Communication，跨 process 通訊。

每個 app 預設跑在自己的 process，而 process 之間的記憶體是作業系統強制隔離的 ——A 的 heap、A 的 static 欄位，B 完全看不到，也拿不到指標。這是 Android 安全模型的地基 （否則任何 app 都能直接讀別人記憶體裡的密碼）。所以資料要跨 process，就必須走 OS 提供的管道，那個管道就叫 IPC。

Android 的 IPC 底層是 Binder（一個 kernel driver）。日常寫的 API 幾乎都是它包出來的：

你寫的東西是 IPC 嗎說明
contentResolver.query(...)✅dm process → binder → MVB process
contentResolver.call(...)✅同上
notifyChange → 對方的 ContentObserver 被喚醒✅反方向的 binder callback
getCallingUid() / getCallingPackage()✅就是在問 binder「這通是誰打來的」
jobScheduler.schedule(...)✅你的 app → system_server
sMainEngineAlive 讀寫❌同 process，純記憶體
MethodChannel / Pigeon❌同 process 內 Java ↔ Dart，走 Flutter 自己的橋

本票兩種通訊剛好對比得很乾淨：

dm  ──IPC(binder)──▶  MVB 的 InstanceInfoProvider     ← 跨 process，一定要 IPC
                          │
                          ├── sMainEngineAlive          ← 同 process，static 就夠
                          └── MethodChannel / Pigeon    ← 同 process，Java ↔ Dart

三個延伸重點：

  1. IPC 有成本：參數要序列化（marshalling）、過 kernel、對端反序列化。 單筆 binder transaction 有 約 1MB 上限（超過丟 TransactionTooLargeException） ——這也是 provider 只回幾個短字串、不回整包資料的理由之一。
  2. 隔離是 OS 強制的，所以存取控制才有意義：dm 只能走我們開的那一扇門（provider）， 門上檢查 package name ＋ 簽章 SHA-256。它沒有別的路摸到 MVB 的記憶體或 Hive 檔。
  3. binder 呼叫是在對方 process 的執行緒上跑的：provider 的 query()／call() 由 binder thread pool 執行，不是 MVB 的 UI thread。所以碰到的共享狀態要考慮執行緒安全 （這就是 volatile 的來由，見下一節）。

1.2 為什麼 static 能當共享狀態

private static volatile boolean sMainEngineAlive = false;

static 欄位屬於 class，class 屬於 ClassLoader，ClassLoader 屬於 process。 MVB 的 manifest 整份都沒有 android:process，所以 MainActivity、 InstanceInfoSyncJobService、InstanceInfoProvider、receiver 全部在同一個 com.viewsonic.droid process、同一個 ClassLoader → 看到的是同一個 sMainEngineAlive。一邊寫、另一邊立刻讀得到，不需要任何 IPC。

  • volatile 是必要的：MainActivity 在 UI thread 寫， schedule() 可能在 binder thread 讀。少了 volatile， 不同 CPU core 可能各讀自己 cache 裡的舊值。
  • process 死掉自動回 false——剛好是正確語意（新 process 裡本來就沒有 Activity engine 活著）， 所以不需要持久化。
  • ⚠️ 這是隱性依賴：若有人給該 service 加 android:process=":headless"， 就變成兩份 static、永遠讀到 false，競態靜默回歸，沒有編譯期保護。 （已寫進程式碼註解。）

1.3 「哪一層是分開的」對照表

直覺容易以為「headless 跟正常啟動當然是分開的」，但分開的其實是別的層：

層級分開嗎說明
Android process❌ 不分開沒有 android:process → 所有元件同 process、同 Java heap
Java static❌ 不分開上一層的直接結果
Dart isolate✅ 分開main 與 headless entry point 是兩個 isolate，記憶體不共享 → 各有一份單例
FlutterEngine✅ 分開兩顆獨立 engine，各自的 channel 註冊
這張表就是本票競態的成因。Dart 兩個 isolate 各有一份 SecureDataStorage 記憶體快取、 彼此看不到對方，才會出現「headless 寫了 Hive，主 isolate 仍用舊快取判斷『還沒有 id』又產生一個」。 Dart 側沒有共享狀態可用，就往下借 Java 那層唯一共享的東西——static。 （案例見 findings §15。）

1.4 system_server：「系統」到底是誰

前面一直說「系統決定何時執行 job」「系統把 process 拉起來」「系統保證 process 不被回收」。 那個「系統」有具體的身分——它是一個叫 system_server 的 process。

開機到 app 啟動的鏈

Linux kernel
  └─ init                          （PID 1）
       └─ zygote                   ← 預先載入好 framework 類別的「模板」process
            ├─ system_server       ← 第一個 fork 出來的孩子
            └─ 你的 app process    ← 每個 app 都是從 zygote fork 出來

實機確認（Pixel Tablet）：

USER      PID  PPID   RSS      NAME
root      860    1     99444    zygote64
system   1268  860    631432    system_server     ← 父程序就是 zygote

兩個附帶知識點：

  • app 啟動很快是因為 fork zygote——framework 類別已經載好、記憶體 copy-on-write 共享， 不必每個 app 從零載入。
  • system_server 不是 kernel，它就是一個（很大的）Java process。 實機上 RSS 約 600MB、將近 290 個 thread。

它裡面住著什麼

Android 的系統服務幾乎都是它裡面的一個模組（各自跑在自己的 thread）。 adb shell dumpsys -l 在這台列出 313 個服務，本票碰到的有：

服務做什麼本票的哪個行為
AMS（ActivityManagerService）管 process、Activity、廣播 dm query 一個沒在跑的 provider → 把 MVB process 拉起來；am force-stop 的 stopped=true 旗標也是它維護的
JobSchedulerService排程 job schedule() 記下來、挑時機、綁定你的 JobService、算 onStartJob 的 watchdog
PMS（PackageManagerService）裝了哪些 app、誰註冊了什麼 authority、簽章是什麼 authority → 找到 MVB；hasSigningCertificate() 驗簽章
ContentService分派 notifyChange MVB notifyChange → 喚醒 dm 的 ContentObserver
WMS / PowerManagerService / AlarmManagerService…視窗、電源、定時（本票沒直接用，但同一個 process）
所以 getSystemService(...) 拿到的不是本機物件，是代理。 jobScheduler.schedule(job) 看起來像普通方法呼叫，實際上是一次 binder IPC 打到 system_server。你寫的每一行「跟系統要東西」的程式碼都是跨 process 呼叫。
⚠️ 一個例外要分清楚：Binder.getCallingUid() 不是問 system_server， 而是 binder driver（kernel）直接提供的——所以它無法被冒用，這正是它能當存取控制依據的原因 （見 §2.4）。

為什麼值得知道這件事

  1. log 裡的小 PID 就是它，而它印的 log 比你自己的更權威。 本票測試時看到的這兩行都來自 PID 1268——就是上面那個 system_server： 
    1268 11503 W JobInfo     : Job '…#96540001' has a deadline with no functional constraints…
1268  1775 W JobScheduler: Job didn't exist in JobStore: … #u0a404/96540001
    那是「系統對你的看法」——你的 job 到底有沒有被收下、被取代、被判逾時，問它最準。
  2. system_server 掛掉 ＝ 整台機器 soft reboot。 所以系統對 app 極度防禦性：各種 watchdog（No response to onStartJob、ANR）、 背景限制、隱式廣播限制，動機都是「不能讓 app 拖垮我」。 理解這點之後，那些看起來很煩的限制就有邏輯可循，而不是規則背誦。
  3. 它是唯一有權限做這些事的地方，所以繞不過去。 「把別的 app 拉起來」「保證 process 不被回收」「跨 app 傳訊」都只有它能做—— 這也是為什麼跨 app 一定要走它認得的機制（provider、broadcast、job）， 不能自己想辦法。

dumpsys 就是問它要狀態

dumpsys <service> 等於「叫 system_server 裡的某個服務把內部狀態印出來」， debug 時非常有用：

指令看什麼
dumpsys jobscheduler我的 job 到底排進去了沒、條件、上次執行
dumpsys activity activities現在前景是誰、Activity 堆疊
dumpsys package <pkg>權限、簽章、provider／receiver 註冊狀況、stopped 旗標
dumpsys -l列出所有服務（這台 313 個）

2. 四大元件與生命週期

Android app 由四種元件組成，都要在 manifest 宣告，都由系統（system_server）決定何時實例化：

元件用途本票用到嗎
Activity有畫面的一頁MVB 的 MainActivity（headless 不經過）
Service沒有畫面的長時間工作InstanceInfoSyncJobService
BroadcastReceiver接系統／app 事件InstanceInfoSyncReceiver
ContentProvider把資料以 URI 形式曝光給別的 appInstanceInfoProvider

另外有一個不是元件、但每個 process 都有的東西：Application。 它代表整個 process——一個 process 一份， Application.onCreate() 一個 process 只跑一次。

⚠️ 一個 process 一份，不是一個元件一份

這是很容易誤解的地方：啟動元件不會各自產生 process、也不會各自產生 Application。

第一個被需要的元件  → 系統發現沒有 process → 建立 process → Application.onCreate()   ← 只有這一次
之後其他元件        → 直接在同一個 process 裡 new 出來 → Application 不再跑

元件只是那個 process 裡的普通 Java 物件，由系統幫你 new 出來、呼叫它的 onCreate()。它們共享同一個 Application 實例、同一個 heap、同一份 static（＝ §1.2 的前提）。 只有 process 被殺掉之後又被需要時，Application.onCreate() 才會再跑一次。

本票的實測就是證據——一個 PID 10504 裡同時裝著 provider、JobService、 以及（bug 那次）兩顆 engine：

10504 10504 I InstanceInfoSync: starting headless Flutter engine
10504 10504 I InstanceInfoSync: headless mirror: instance_id=present
process 起來（一次）  → Application.onCreate ＋ init providers      ← headless 也會跑
  ├─ MainActivity     → engine #1 → main
  └─ JobService       → engine #2 → instanceInfoHeadlessMain        ← 沒有 Activity

⚠️ ContentProvider 比 Application.onCreate() 還早

直覺會以為「Application 一定最早」，但實際順序是 （ActivityThread.handleBindApplication）：

1. Application 建構子
2. Application.attachBaseContext()
3. ContentProvider.onCreate()        ← 比 Application.onCreate 還早！
4. Application.onCreate()
5. Activity / Service / Receiver 的 onCreate()

provider 是唯一比 Application.onCreate() 早的元件。 這個冷知識有很實際的用途：Firebase、GoogleTagManager、ProfileInstaller、 androidx startup 都是故意把自己註冊成 ContentProvider， 來取得「最早的初始化 hook」——函式庫因此不需要你在 Application 裡寫任何一行 code 就能自動初始化。

這也解釋了為什麼 headless 的 log 裡會看到 GoogleTagManager、 AdvertisingIdClient、ProfileInstaller、TextToSpeech ——那些是 process 級初始化，process 因任何原因被拉起就會跑， 跟我們的 engine 無關，也關不掉。

2.1 ContentResolver（客戶端）

ContentProvider 是伺服端，ContentResolver 是客戶端。 提供資料的 app 寫 provider；要資料的 app 用 resolver 去拿。同一個 app 可以同時是兩者。

// dm（客戶端）
Cursor c = context.getContentResolver()
        .query(Uri.parse("content://com.viewsonic.droid.instanceinfo.provider/info"), …);

getContentResolver() 拿到的不是「連到某個 app」的連線，而是 「通往全裝置所有 provider 的單一入口」。你只給它一個 URI，它負責：

  1. 從 URI 取出 authority（com.viewsonic.droid.instanceinfo.provider）
  2. 問 PackageManager：誰註冊了這個 authority
  3. 那個 app 沒在跑 → 把它的 process 拉起來
  4. 透過 binder 呼叫過去（＝ IPC）
  5. 把結果（Cursor 或 Bundle）帶回來
為什麼要有這層間接？因為呼叫端不需要知道對方的 package name、class 名稱、 有沒有在跑、跑在哪個 process。它只認一個 URI——概念上跟「你發 HTTP 請求只認 URL， 不需要知道對方跑在哪台機器」是同一件事。

常用方法（前四個是 CRUD，後三個本票都用到）：

方法用途
query()讀，同步回 Cursor（找不到 authority → 回 null）
insert() / update() / delete()寫（本票的 provider 是唯讀，不實作）
call()雜項 RPC：不是查資料，而是叫對方做事，回 Bundle
registerContentObserver()訂閱變更（⚠️ 找不到 authority → 丟 SecurityException，見 §2.3）
notifyChange()發出「我變了」的通知（provider 端用）

⚠️ ContentResolver 是原生 API，Dart 側沒有對應物。 所以 dm 讀 MVB 是在 Kotlin 端做（MvbInstanceInfoReader.kt）； 如果哪天 Flutter app 要當客戶端，得自己寫 plugin 包一層。

2.2 ContentProvider（伺服端）

把資料用 content:// URI 曝光給別的 app 的標準機制。核心概念：

  • authority：URI 裡的「網域」，全裝置唯一（兩個 app 用同一個 authority，後裝的裝不起來）。 慣例是拿 package name 當前綴，如 com.viewsonic.droid.instanceinfo.provider。
  • exported="true"：外部 app 才進得來。設 false 就只有自己用。
  • query() 是同步的：呼叫端 query() 回來就拿到結果（或 null）。 它不能「等一下再回答」。這正是本票要另外設計 call("ensureInitialized") ＋ notifyChange 的原因：資料還沒準備好時，同步回一個「尚未初始化」，非同步把它做出來，做完再通知。
  • Cursor：query 的回傳型別，概念上是「一張表 + 一個游標」。 本票不是真的資料庫，所以用 MatrixCursor 手工造列（key-value 兩欄）。 設計上「缺值就不列出那一列」，讓呼叫端用 presence 判斷、而不是比對版本號。
  • call()：provider 的「雜項 RPC 出口」，不是查資料而是叫對方做事， 回傳一個 Bundle。本票用它觸發 headless 初始化。
  • ⚠️ provider 會讓 process 被拉起：外部 app 一 query，若 MVB 沒在跑，系統會為它啟動 process。 這是「MVB 從未被開啟也能回答」能成立的前提。

2.3 notifyChange / ContentObserver

provider 端資料變了就呼叫 getContext().getContentResolver().notifyChange(uri, null)； 對方若有 registerContentObserver(uri, ...)，就會被喚醒去重新 query。等於「push 通知」， 省掉呼叫端無腦輪詢。

⚠️ 踩過的坑：當 authority 不存在（沒裝 MVB、或裝的是舊版）時， query() 只是回 null，但 registerContentObserver() 會直接 丟 SecurityException。兩者行為不一致，一定要 try/catch，否則呼叫端會 crash。

2.4 「呼叫我的是誰」——存取控制的基礎

provider 是 exported="true"，任何 app 都能敲門，所以要在程式裡驗身分。三種手段：

手段意思強度
getCallingPackage()binder 告訴你的呼叫端 package name⚠️ 只驗「名字」，名字可以被冒用
Binder.getCallingUid() ＋ getPackagesForUid()交叉確認 uid 與 package 對得上中
hasSigningCertificate(pkg, sha256, CERT_INPUT_SHA256)驗簽章——只有握有私鑰的人簽得出來✅ 強（且能處理 key rotation）

另有一個 manifest 層的做法：android:protectionLevel="signature"。它比較寬—— 授權給所有同簽章的 app；而執行期比對 allowlist 是「指定的那幾個 package ＋指定的那把簽章」，更嚴。

驗證存取控制要做反向測試：故意改呼叫端的 package name／簽章，確認真的被拒。 只測「允許的情況會過」是不夠的——那不能證明拒絕邏輯有效。

2.5 JobService

一句話：把「要做的事」登記給系統的排程器，由系統決定何時執行、並在執行期間保證你的 process 不被殺。

關鍵差異在「誰啟動它」：

一般 ServiceJobService
誰啟動你（startService / bindService）系統（你只 schedule 一次，之後不管）
背景限制⚠️ Android 8+ 背景 app 不能隨意啟動 service✅ 這就是官方指定的替代方案
執行期間 process不保證✅ 系統保證不回收
可以附條件嗎不行✅ 充電中／連 Wi-Fi／閒置／延遲 N 秒…

那為什麼不用更簡單的做法？

  • 開一個 Thread 就好？——不行。工作跑在 process 裡，而 process 隨時可能整個被系統回收，thread 跟著沒了。
  • 在 receiver 裡做完？——不行。receiver 只有數秒（約 10s）， 而我們要啟動 Flutter engine（實測慢機要十幾秒）。
  • AlarmManager？——語意不同。那是「時間到了叫我」， 不含「保證我能跑完」，而且省電限制（Doze）會把它推遲。

呼叫流程（三方：你的 code、system_server 裡的 JobScheduler、你的 process）：

你的 code                    system_server                 你的 process
scheduler.schedule(job) ─IPC─▶ 記下來
                               （挑時機、檢查條件）
                               ─── 綁定 service ───▶ onStartJob()   ← main thread！
                                                     return true    ← 「還沒做完」
                                                     …真正的工作…
                               ◀──── jobFinished() ───              ← 你要主動回報
                               ─── onStopJob() ───▶                 ← 若系統要提前收回

接下來是實作上真正會咬人的細節：

  • onStartJob() 的回傳值語意： true = 「我還在做，做完會呼叫 jobFinished()」； false = 「已經做完了」。
  • ⚠️ onStartJob() 不能久留：它在 main thread 上跑，且系統有 watchdog。 本票踩過——在裡面同步啟動 Flutter engine（debug 版含解壓，好幾秒）→ 系統判定 No response to onStartJob 並把服務拆掉，Dart 根本來不及跑。 正解：立刻 return true，把真正的工作 post 到 main looper。
  • onStopJob()：系統要收回資源時叫你收工，回傳值代表「要不要重排」。
  • 同一個 JOB_ID 再 schedule 會取代舊的——但如果前一次已經在跑， 取代的是「排程」而不是「執行中的工作」，於是可能同時有兩份工作在跑。 本票因此需要一個 in-flight 旗標（案例見 findings §17.4）。

JOB_ID 怎麼定：技術上沒有規則，只有唯一性

JobScheduler 以 (uid, jobId) 為 key。所以：

  • 它活在你自己 app 的命名空間裡——跟別的 app 不會撞（uid 不同）。
  • 唯一的硬性約束是同一個 app 內要唯一。任何 int 都可以，沒有規定要挑什麼。
  • 撞號的表現是「取代」（cancel 舊的 ＋ 排新的），不是錯誤—— 所以撞到時沒有任何訊息，只是某一邊的 job 悄悄消失。
⚠️ 真正的碰撞風險來自函式庫，不是你自己。 WorkManager 底層也是 JobScheduler，會自己產生 job id 且預設從小數字遞增。 所以 JOB_ID = 1 這種寫法最危險——症狀是「我的 job 沒跑」或「別人的背景工作不見了」， 而且兩邊都不會報錯。
結構性的解法是 WorkManager.Configuration.Builder.setJobSchedulerJobIdRange(…) 把 WorkManager 明確圈在一個區段；沒做的話就只能靠「挑一個不可能落在低位區的數字」這種慣例式避讓。

各種常見做法的評價：

做法評價
集中在一個常數檔（JobIds）✅ 最有效。「唯一」是全 app 的性質，各 class 各自寫 private 常數在結構上無法保證
從 1 開始遞增⚠️ 很常見，但正是會撞函式庫的做法
功能／票號編碼（如 96540001）少見；可回溯，但可讀性 100% 靠註解
R.id.xxx 或字串 hashCode❌ 別用。R.id 重新編譯就會變，而 job id 需要跨版本穩定（否則 cancel() 找不到舊 job）
⚠️ 不要用 Java 7＋／Kotlin 的數字底線寫成 9654_0001。 它與 96540001 完全等價（純編譯期），可讀性也更好——但要查 「這個 id 有沒有被用過」的人會直接 grep 數字，底線會讓搜尋落空， 而落空看起來就像「沒有重複」。在沒有集中登錄檔的情況下，可被 grep 比視覺分組重要。
這是一個通則：當某個字面值是別人未來會用文字搜尋的東西時，不要把它拆開。

另外，「跨版本穩定」這條的強度取決於 job 是否持久化： 沒有 setPersisted(true) 且 setOverrideDeadline(0) 的 job（排了就馬上跑完、 不跨重開機）不會留下孤兒，改 id 的風險小得多。

BIND_JOB_SERVICE 常見誤解

android:permission="android.permission.BIND_JOB_SERVICE" 寫在 <service> 上， 它是「限制」而不是「申請」：意思是「只有持有這個權限的人可以綁定我」， 而持有者只有系統。它不是 <uses-permission>， 不會出現在上架權限清單、不需要使用者授權、 呼叫端（dm）也不需要宣告任何東西。 沒寫反而是問題：任何 app 都能綁你的 service。

2.6 BroadcastReceiver

  • MY_PACKAGE_REPLACED：自己被更新後收到（首次安裝不會）。 它豁免 Android 8+ 的隱式廣播限制，所以 manifest 靜態註冊有效。
  • BOOT_COMPLETED：開機完成。需要 RECEIVE_BOOT_COMPLETED 權限（normal 級，不需使用者授權）。
  • ⚠️ receiver 只有數秒（約 10s）。要做久的事就在 receiver 裡排 job，不要在裡面做完。
  • ⚠️ 觸發點不要放在「只執行一次」的生命週期：本票踩過——把讀取放在 Service.onCreate／Activity.onCreate，結果 process 還活著時就不會再跑， 畫面永遠停在舊狀態。要放在每次「觀察」的時機（如 onResume）。
⚠️ 測試陷阱：am force-stop 之後收不到廣播。 它會設 stopped=true 旗標，而 am kill 清不掉。 要「殺掉 process 但保留可收廣播」，用 am kill。這個坑本票踩了兩次。

stopped 旗標到底擋什麼（實機釐清）

「永久收不到」講得太重了——實測後精確的說法是：

行為stopped=true 時
收廣播（含 MY_PACKAGE_REPLACED、BOOT_COMPLETED）❌ 擋掉
別的 app query() 你的 ContentProvider✅ 照樣通，而且系統會把你的 process 拉起來
旗標本身被任何 explicit start 清掉——包括別的 app 來 query 你的 provider，不必使用者親自開 app
被擋掉的 BOOT_COMPLETED系統延後保留，在 process 下次啟動時補送

實測（stopped=true ＋ process 死著，呼叫端來讀）：

ActivityManager  : Start proc 12376:com.viewsonic.droid for content provider {InstanceInfoProvider}
InstanceInfoSync : receiver: android.intent.action.BOOT_COMPLETED          ← 延後的廣播被補送
BroadcastQueue   : BOOT_COMPLETED_BROADCAST_COMPLETION_LATENCY_REPORTED …
（之後）stopped=false                                                      ← 旗標被清掉了
所以這個坑只咬開發測試，不咬產品。 測試時你 force-stop 再 install -r，期待 MY_PACKAGE_REPLACED 觸發——收不到， 因為中間沒有任何人 explicit start 過。 但產品路徑上呼叫端一定會先 query()，那次 query 就把旗標清掉、 順手把延後的廣播補送回來——自癒。
→ 一般化的教訓：「provider 讀取」跟「廣播觸發」是兩條獨立的路， 前者不受 stopped 影響。所以呼叫端不需要、也無法分辨對方是不是被強制停止過 ——那個狀態對它是透明的。

manifest 靜態註冊 vs 程式碼動態註冊

manifest（靜態）Context.registerReceiver（動態）
誰記住它PackageManager，安裝時寫進系統的 package 資料庫你的 process 的記憶體
app 沒在跑時✅ 廣播會把 process 拉起來再送❌ 隨 process 一起消失
重開機✅ 存活（不需要使用者開過 app）❌ 沒了

所以 BOOT_COMPLETED 的流程是：AMS 查 PackageManager 找到有註冊的元件 → fork 一個新 process → 跑 onReceive()。這是「app 從沒被開過也能做事」的唯一入口。

❌ 迷思：exported="false" 會擋掉系統廣播

非常常見的誤解（本票被兩個外部意見同時指出「應該改成 true」）。不要改。 實測：重開機後查 AMS 的廣播歷史 adb shell dumpsys activity broadcasts——

BroadcastRecord{… android.intent.action.BOOT_COMPLETED/u0/0xc1} to user 0
  caller=null null pid=1251 uid=1000 realCallingUid=1000
  DELIVERED scheduled +24s351ms terminal +32ms (-1) #219: (manifest)
      name=com.viewsonic.droid.instanceinfo.InstanceInfoSyncReceiver
      enabled=true exported=false directBootAware=false      ← false，狀態是 DELIVERED

再用 adb install -r 觸發 MY_PACKAGE_REPLACED（同樣由系統發送）做決定性驗證：

ActivityManager  : Start proc 9152:com.viewsonic.droid
                   for broadcast {com.viewsonic.droid/.instanceinfo.InstanceInfoSyncReceiver}
InstanceInfoSync : receiver: android.intent.action.MY_PACKAGE_REPLACED
InstanceInfoSync : skip schedule (…): prefs already mirrored

process 是為了這個 exported=false 的 receiver 冷啟動的。

原理：exported 管的是「別的 app 能不能戳我」，不是「系統能不能派給我」。 系統派送 protected broadcast 不在這個檢查的管轄內——這是設計語意，不是「系統特權硬闖」， 所以它是穩定契約，不會哪天被收掉。
而且 Android 12 起官方指南的建議正好相反：「若這個 receiver 只接收系統廣播， exported 應設為 false」。BOOT_COMPLETED／MY_PACKAGE_REPLACED 都是 protected broadcast，第三方 app 本來就發不出來，改成 true 只是白白擴大攻擊面。
⚠️ 別把 lint 的要求記錯：Android 12+ 要求「有 intent-filter 就必須明確宣告 android:exported」，不是「必須設 true」。

進入 stopped state 的三條路（含 preload）

情況旗標備註
裝好但從沒被啟動過stopped=true
notLaunched=true		 Android 3.1 起的機制。產品上最常見——預載機器的使用者可能一年沒點開過
使用者按「強制停止」stopped=true
notLaunched=false		上面那段講的情形
Android 14+ preload 被掃成 stoppedscannedAsStoppedSystemApp=true 平台允許把「非必要的」預載 app 在第一次開機就標成 stopped（框架端有 allowlist 控制）

第三條是 Android 14（API 34）才有的，很容易被舊資料誤導成「preload 一定豁免」。 實測這台 Android 16（dumpsys package packages）：

scannedAsStoppedSystemApp=true   → 4 個
scannedAsStoppedSystemApp=false  → 385 個     ← 預設仍然是「不 stopped」

→ 正確說法是「preload 預設會收到第一次開機的廣播，但 Android 14+ 的 FW 可以關掉」， 比例上是少數，但不能當保證。

真預載 vs 假預載（跟廠商交涉時的自保工具）

廠商說「已預載」有兩種完全不同的意思：

  • ✅ 燒進 system image（/system/app、/system/priv-app、apex 的 priv-app） → 被視為系統的一部分，預設不 stopped
  • ⚠️ 開機流程（OOBE）用腳本 adb install 到 /data/app → 系統當成一般 user app，notLaunched=true，第一次開機完全收不到廣播

驗證方式（新裝置／新 FW 交付時必跑）：

adb shell dumpsys package <pkg> | grep -E "codePath|flags=\[|scannedAsStopped|stopped="
# 期待：codePath=/system/priv-app/… 且 flags 含 SYSTEM 且 scannedAsStoppedSystemApp=false
# 若看到 codePath=/data/app/… 且 flags 沒有 SYSTEM → 是假預載

收廣播的成本：process 起來 ≠ engine 起來

「manifest receiver 會不會把 plugin／Pigeon 都註冊起來、很吃效能？」——不會。

BOOT_COMPLETED → process 起來 → Application.onCreate() → onReceive() → schedule()
                                                              ↑ 到這裡結束，沒有 engine
  • plugin 註冊發生在 GeneratedPluginRegistrant.registerWith(flutterEngine)， 只有建立 FlutterEngine 時才跑。Pigeon 更只是 MethodChannel 的 codegen， 沒有「註冊時機」，是 engine 建好後才掛上去的。
  • 真正在 process 起來時被跑的是 ContentProvider（見 2.0 的順序）。 實機查 MVB 合併後有 10 個，其中 4 個是真的做事的 init provider： FirebaseInitProvider、MlKitInitProvider、 androidx.startup.InitializationProvider、ClassSwiftFusionInitProvider； 其餘是 InstanceInfoProvider ＋ 4 個 FileProvider ＋ speech 的 provider。 這筆帳不是 receiver 造成的，是「process 被拉起來」造成的，任何原因拉起都一樣付。
  • 而且多數時候立刻早退——上面那段 log 的 skip schedule (…): prefs already mirrored 就是連 job 都沒排。
一句話：廣播的成本上限是「process 初始化」，不是「Flutter 初始化」。 兩者差一個數量級（幾十 ms vs 數秒）。

⚠️ directBootAware=false：BOOT_COMPLETED 要等解鎖

上面 dumpsys 輸出裡有 directBootAware=false，意思是這個 receiver 收的是 BOOT_COMPLETED 而不是 LOCKED_BOOT_COMPLETED—— 要等使用者解鎖（credential-encrypted storage 可用之後）才會派送。

IFP 一般不設鎖屏、開機即解鎖，實務上沒差。但若客戶設了 PIN，開機後沒人解鎖之前： receiver 不會跑，而且呼叫端就算來 query provider 也讀不到值——因為 instance_id 存在 SharedPreferences／Hive，兩者預設都在 CE storage。 這是跟 stopped 無關、但落在同一個時間窗的獨立限制。

2.7 一次完整的呼叫流程（把上面全部串起來）

情境：MVB 裝了新版但從來沒被開過，dm 想要 instance_id。

dm (process A)                          MVB (process B，可能還沒起來)
──────────────────────────────────────────────────────────────────────────
query(content://…/info)  ──IPC──▶  ① 系統把 MVB process 拉起來
                                    ② provider.query() 在 binder thread 執行
                         ◀──────    ③ 同步回答：缺 instance_id 那一列
                                       → dm 判定 NOT_INITIALIZED

call("ensureInitialized") ─IPC──▶  ④ 排一個 job
                         ◀──────    ⑤ 立刻回 {scheduled:true}   ← 不等工作做完

                                    ⑥ onStartJob() → return true（立刻！）
                                       post 到 main looper
                                    ⑦ new FlutterEngine(...)     ← headless，無 Activity
                                    ⑧ 補註冊 Pigeon handler
                                    ⑨ 跑 instanceInfoHeadlessMain（不是 main）
                                    ⑩ Dart：讀 Hive → 沒值就產生
                                    ⑪ Pigeon setInfo → prefs.commit()
                                    ⑫ notifyChange(uri)
◀── ContentObserver 被喚醒 ─IPC──
query(...) 再讀一次        ──IPC──▶
                         ◀──────    instance_id=…  ✅
為什麼要拆成「同步先回答 ＋ 非同步做事 ＋ 做完通知」三段？ 因為 query() 不能「等一下再回答」（§2.2）。 它必須馬上回一個答案，所以「還沒準備好」本身就得是一個合法答案 ——這就是錯誤回報（error_code / error_message）在 contract 裡是必要欄位、 而不是可選的原因。

兩個容易誤解的地方：

  • 不是靠 polling：主要機制是 ⑫ 的 notifyChange → ContentObserver（push）。 呼叫端每秒輪詢只是我們驗證用 overlay 額外加的保險，正式整合不需要。
  • ⑤ 回 {scheduled:true} 不代表成功，只代表「已受理」。 真正的結果要等 ⑫ 之後重讀才知道——所以呼叫端必須有「受理了但最終還是失敗」的處理路徑 （例如 headless 逾時）。

3. Flutter 側

3.1 Engine / isolate / entry point

  • FlutterEngine：一顆 Flutter 執行環境（Dart VM isolate ＋ 渲染 ＋ channel 匯流排）。 FlutterActivity 會自動幫你建一顆；也可以自己 new FlutterEngine(context)——那就是 headless（沒有畫面）。
  • isolate：Dart 的並行單位，記憶體不共享（不像 Java thread）。 兩顆 engine = 兩個 isolate = 各一份單例／static。
  • entry point：Dart 側的進入函式。預設是 main，但可以有多個： 
    @pragma('vm:entry-point')   // 告訴 AOT tree-shaking「別砍它」
Future<void> instanceInfoHeadlessMain() => runInstanceInfoHeadlessSync();
    原生側用 DartEntrypoint(bundlePath, "instanceInfoHeadlessMain") 指定。
    ⚠️ 兩個限制：函式必須宣告在 main 所在的 library（即 lib/main.dart）， 且一定要加 @pragma('vm:entry-point')，否則 release build 會被 tree-shake 掉。
  • 選了 headless entry point，就不會跑 main——這是「headless 很省」的來源： main 裡那條又長又重的 app 初始化鏈完全跳過。
  • headless 沒有任何 Activity：所以 MainActivity.configureFlutterEngine() 不會執行（見下一節）。

3.2 plugin vs 手寫 MethodChannel（headless 的關鍵差異）

正式 pluginActivity 手寫 MethodChannel
註冊時機new FlutterEngine() 建構時自動註冊全部在 configureFlutterEngine() 裡手動 new MethodChannel(...)
headless 拿得到嗎✅ 拿得到❌ 拿不到（沒有 Activity）
例子path_provider、device_info_plusdetectChromeos、vsCommand…（MVB 有二十幾條）

實測表現就是一條非致命錯誤：

⛔ Error on detecting chromeos: MissingPluginException(No implementation found for
   method detectChromeos on channel com.viewsonic.droid/detectChromeos)
教訓：headless 可以依賴 plugin，不能依賴 Activity 手寫 channel。 需要的話就在建立 headless engine 之後自己補註冊（本票就是這樣補 Pigeon handler 的）。

順帶：自動註冊全部 plugin 聽起來很貴，實測只 10–26ms。 關掉（automaticallyRegisterPlugins=false）省不到什麼，還會弄丟真正需要的 plugin。

3.3 MethodChannel 與 Pigeon

  • MethodChannel：Java ↔ Dart 的原始通訊方式。用字串當方法名、 Map 當參數 → 打錯字要到執行期才炸。
  • Pigeon：程式碼產生器。你在 pigeons/*.dart 用 Dart 寫介面 （@HostApi = Dart 呼叫原生，@FlutterApi = 原生呼叫 Dart）， 它產出兩側型別安全的樣板。改介面時兩邊一起壞在編譯期，比執行期才發現好。
  • ⚠️ handler 是綁在「某一顆 engine」上的： InstanceInfoPlugin.setUp(engine.getDartExecutor().getBinaryMessenger(), impl) 只對那顆 engine 有效。本票踩過——只在 MainActivity 註冊，headless engine 就 MissingPluginException，而它被 catch 後靜默什麼都沒做。

3.4 「對面做完了嗎」——用 inbound 呼叫當完成訊號

Java 啟動 Dart 是 fire-and-forget：

engine.getDartExecutor().executeDartEntrypoint(entrypoint);
// ← 這行立刻回來。沒有 Future、沒有 callback、沒有回傳值。
//    Dart 那邊做完了沒有，Java 這邊無法直接觀察。

所以唯一可靠的完成訊號是讓 Dart 主動打回來。剛好 Dart 做完事情本來就要 呼叫 Pigeon 的 setInfo() 把結果交給原生——那次呼叫本身就是「我做完了」。

本票的 CompletionSignallingPlugin 就是這個角色，它是 decorator：

class CompletionSignallingPlugin implements InstanceInfo.InstanceInfoPlugin {
    private final InstanceInfoPluginImpl delegate;   // 正式的寫入邏輯，原封不動
    private final JobParameters params;

    public void setInfo(InstanceInfoData info) {
        delegate.setInfo(info);                       // ① 該做的事照做
        if (hasId) { finishJob(params, false); }      // ② 額外：把它當完成訊號
    }
}

三個設計點：

  • 用 decorator 而不是改 impl：正式路徑（MainActivity 的 engine）註冊 InstanceInfoPluginImpl、headless 註冊包一層的版本， 寫入邏輯只有一份。Pigeon 產生的是 interface，所以隨便你塞什麼實作。
  • 它是 inner class（非 static）：因為要呼叫外層的 finishJob()、 也要捕捉「這一次」的 JobParameters。
  • ⚠️ 完成訊號可能來好幾次——本票踩過：一次 headless 執行會鏡射兩次 （載入時先鏡射一次，此時 id 可能還是空的；產生後再鏡射一次）。 把「第一次呼叫」當完成，會在產生途中就 destroy engine，實測結果是 prefs 只留下一個空的 id。
通則：當你無法 await 對面時，讓對面主動回報；而完成條件要看「內容」而不是「第幾次」。
並且一定要有 timeout 兜底——對面可能永遠不回報（崩了、卡住、根本沒跑到那行）， 沒有 timeout 的話 job 就永遠不結束，系統資源也不會釋放。 本票是「拿到非空 id 才收工，產不出來交給 TIMEOUT_MS」。

這個形狀在別處也會遇到：任何「啟動一個你無法 await 的東西」都適用 —— 起 process、丟 broadcast、交給另一個 app 處理。差別只在回報的管道是 Pigeon、binder 還是寫檔。

4. 儲存

4.1 SharedPreferences

  • key-value 的 XML 檔，放在 /data/data/<pkg>/shared_prefs/，權限 -rw------- （只有 app 自己的 uid 讀得到；未 root 的 adb 讀不到）。
  • apply() vs commit()： apply() 立刻更新記憶體、非同步寫檔（不回傳結果）； commit() 同步寫完才回傳 boolean。
    → 如果寫完馬上要 notifyChange 通知別的 process 來讀，用 commit() 才能消掉「對方讀到舊檔」的時序縫隙。
  • Flutter 的 shared_preferences 套件底下就是它，但 key 會加前綴、值有自己的編碼 → 不要從原生去直讀那個檔（依賴 undocumented 格式）。要共享就明確寫一份自己的 prefs。

4.2 Hive

  • 純 Dart 的本地 key-value 資料庫（本專案用 hive_ce）。檔案如 app_flutter/activate_db/activate.hive。
  • append-only frame log：每次寫入是追加一個 frame（含 CRC32），刪除是寫 tombstone， 開檔時重播成記憶體 map，過期資料靠 compaction 清。
    → 副作用（很好用的偵錯技巧）：strings -a activate.hive | grep -oE '[0-9A-F]{32}' | sort -u 可以看出「歷史上總共產生過幾個 id」，本票就是這樣抓到重複產生的。
  • 原生沒有 parser：不是「看不到檔案」，是「沒有官方格式規格可以在 Java 端解」 → 這正是需要跑 Dart（headless）才能判斷「Hive 裡到底有沒有值」的原因。
  • ⚠️ 不適合多 isolate 併發：有 activate.lock 鎖檔，兩個 isolate 同時開同一個 box 會丟 PathNotFoundException: Cannot delete file … activate.lock。 單例是每個 isolate 一份，所以「同一個 app 內」也會撞。
    → 別人怎麼解這類問題、以及為什麼「加個鎖就好」是錯的方向，見 §4.3。

4.3 多開 ≠ 多寫：併發存取怎麼解

上面說「Hive 不適合多 isolate 併發」，但更值得學的是別人是怎麼解的—— 因為「同一個 app 開了好幾份、都要寫同一個檔」是通用問題，不是 Hive 專屬。

三種儲存層、三種併發策略

儲存層併發策略撞到時的行為
SQLite / LevelDB
（Chrome、Room 用）		 ✅ 設計上就支援併發：讀寫鎖分等級、WAL 讓讀者不擋寫者、拿不到鎖會 busy-retry 等一下再試，通常成功
SharedPreferences ⚠️ per-process 單例 ＋ 內部同步：同 process 內安全，跨 process 不安全（官方明講不支援，MODE_MULTI_PROCESS 已 deprecated） 跨 process 會靜默不一致
Hive ❌ 假設單一 isolate 獨佔：.lock 檔更像「防呆」而不是併發控制 直接丟例外（PathNotFoundException: Cannot delete file … activate.lock）

所以「加個鎖就好」是錯的方向——SQLite 那種鎖是整套機制（等級、升級、退讓、重試），不是一個布林旗標。

更根本的答案：單一寫入權威（single-writer authority）

Chrome 是多 process 架構（每個 tab 一個 renderer process），但 renderer 完全不碰資料庫 ——一律 IPC 給 browser process，由它單獨讀寫。也就是說「多開」跟「多寫」是兩件事： 可以開很多份，但寫入口只有一個。

情境誰是唯一寫入者
Chrome 多 tabbrowser process（renderer 只能 IPC）
Android 跨 app 共享資料ContentProvider（＝本票在做的事）
Room / SQLite一個 process 一個 instance

補充一個常見誤解：Android 上 Chrome 的多視窗，那些 Activity 其實都在同一個 process、 共享同一份 Java 單例 → 天然就只有一個寫入者。真正多 process 的是 renderer，而它們沒有 DB 存取權。

回到 MVB：為什麼結構上撞不到（以及什麼情況會撞到）

  • MVB 有 2 個 activity，但只有 MainActivity 是 FlutterActivity （FileOpenActivity 是純 AppCompatActivity，沒有 engine）。
  • MainActivity 宣告 android:launchMode="singleInstance" → 系統保證最多一個實例。所以 Activity 側只可能有一顆 engine。
  • ⚠️ 但這是 manifest 給的保證，不是 Flutter 給的： Flutter 預設每個 FlutterActivity 各自建一顆 engine （除非用 engine cache 或 FlutterEngineGroup）。 若哪天拿掉 singleInstance、或多加一個 FlutterActivity， 就會變成兩顆 engine → 兩個 isolate → 兩份單例，跟 headless 撞的是同一類問題。
本票的守衛屬於「壓縮窗口」，不是「消滅窗口」。 sMainEngineAlive ／ hasMirroredInstanceId ／ sSyncInFlight 是三個「大家別同時進來」的約定；正解是讓「檢查 + 產生 + 寫入」由唯一持有者原子化執行 ——這就是待辦裡「instance_id 單一寫入權威」的意思，不是隨口寫的未來式，而是上面那個標準 pattern。
⚠️ 也要記住守衛 A 的主要理由是記憶體快取造成的重複產生（語意錯誤）， Hive lock 只是它順帶封掉的第二個問題。把理由記成「為了避開 lock」， 將來有人拿掉守衛改成「加個檔案鎖就好」，快取競態會活過來。 （案例見 findings §15。）

5. adb 小抄與陷阱

指令用途 / 注意
adb connect <ip>:5555連 Wi-Fi 裝置
