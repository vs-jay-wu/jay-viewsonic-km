3. Background

  • Manager 的 Software Instances 頁可管理 myViewBoard 設定（Check for Update / Local Save / Embedded Browser / Sign-in Function / Allow Stay Signed In / Auto Sign-out Time），支援 template 批次套用。
  • 目標：IT 透過 Manager 單一介面管理 MVB 設定。
  • 缺口：Manager 存取得到 software instance 頁面，但不知道 instance ID 與裝置的對應關係，需要 myViewBoard 協助。

3.1 現況資料流與缺口（instance ID 目前是怎麼給 Manager 的）

結論：裝置端目前完全沒有給 —— 這正是本票要補的缺口。

路徑現況
雲端側 MVB enroll 時把 instance ID 當 uid 上報後端（POST /api/v2/application/whiteboard）。裝置 enroll 進 entity 後，Manager 雲端「Software Instances」頁即列得出該 entity 下所有 instance ID 並可套設定 —— Manager 知道有哪些 instance。
裝置側（缺口） MVB 沒有任何對外介面提供本機 instance ID，Manager agent 無從得知本機 MVB 是哪個 instance —— 雲端一排 ID 對不上「哪個 ID 是哪台裝置」。
既有跨 app 通道 只有反方向：MVB 讀 agent 的 content://com.viewsonic.dmagent.provider/entity 拿 entity name 做 auto-enroll（MainActivity.java:1855-1906）。沒有 MVB → Manager 的通道。

本票即是把方向反過來：MVB 開對稱的 ContentProvider 讓 agent 讀 instance ID（+ entity name），agent 回報雲端後才能建立「instance ID ↔ 裝置」對應（見 §2 資料流圖）。

3.2 補上 join 帶來的價值（對 PM 的論述）

精確地說，缺的不是機器資訊——MVB enroll 時有上傳自述硬體資訊（Brand / Manufacturer / OS 版本等，mvb_activator.dart hardwareProperty）——缺的是兩個資料世界之間的 join key：

  • Manager 世界：裝置紀錄（serial number 主鍵，dm 回報完整硬體/韌體/狀態）＝ IT 眼中的機隊
  • myViewBoard 世界：instance 紀錄（instance ID 主鍵）＋ 自述硬體字串
  • 兩者沒有可靠共同鍵：自述硬體同型號幾百台相同、IP 會變/NAT、Android ID 是 per-signing-key 的 analytics 欄位——都不是設計來 join 的

本票 = 在裝置上把 join key（instance ID）交給 dm，由 dm 帶著 serial number 回報——用「同一台裝置」的物理事實完成 join。之後才可能有：

#解鎖的能力現況為什麼做不到
1從裝置找軟體：Devices 頁點某台機器 → 直達它的 MVB instance 設定instance 清單是一排 hex 字串，IT 不知道哪台是哪台
2批次操作用裝置分群：「三樓所有 IFP」套 MVB templateinstance 清單無法用任何裝置屬性篩選
3Support 斷鏈接回：從裝置紀錄一鍵查到 instance要有人到機器前開 Settings > About 抄 instance ID
4Entity 錯配偵測：裝置在 entity A、MVB 在 entity B 可警示誤註冊完全隱形
5軟體資產盤點：哪些裝置裝了 MVB、啟用狀態、（未來）設定 drift兩邊資料各自為政，報表做不出來

3.3 替代方案比較：為什麼不是「MVB enroll 時帶上 serial number」？

直覺方案：MVB enroll 時一併上報 serial number，兩個後端就有共同 key，連 ContentProvider 都不用做。不採用，關鍵原因由強到弱：

#理由說明
1 EDLA 上 MVB 讀不到 serial（硬性技術阻斷） Android 10+ 讀 serial 需 READ_PRIVILEGED_PHONE_STATE（system/priv-app）或 Device Owner 身分。ifp flavor 是平台簽章 system app 讀得到；但 EDLA（GMS 認證）裝置上不能玩 system-uid——這正是 dmagent 要另做 app_edla（Device Owner 模式）的原因。同一限制下，MVB 在 EDLA 上拿不到 serial，而 dm（Device Owner）永遠拿得到——能讀 serial 的一方（dm）必須是「學到 instance ID」的一方 → 方向被迫是 provider
2 資料最小化 serial 是裝置識別碼，流進 myViewBoard（含消費者場景）後端 = 擴大其個資持有範圍；instance ID 流進 Manager（本來就是 MDM、已合法持有 serial）風險小得多。方向選擇本身就是隱私決策
3 生命週期與新鮮度 enroll 是一次性事件：MVB 重裝（instance ID 換新）、換 entity、主機板維修（serial 變）後 mapping 靜默過期。provider 方向 dm 可隨時重查 + ContentObserver 訂閱，且 dm 本來就有週期回報（dynamic_info / 180s）的管線
4 組織耦合 serial-at-enroll 要動 myViewBoard 後端 schema + 開 Manager ↔ myViewBoard 的後端對後端查詢/同步；provider 方向兩邊後端 schema 都不動，dm 只是在自己的裝置回報多帶一個欄位
5 key 品質 serial 唯一性由製造商保證（跨牌可重複、翻新機/韌體複製有髒資料）；on-device join 用的是「同一台裝置」物理事實，沒有 key 品質問題

附帶一提：Aaron 的 entity 護欄（dm 比對 entity name 決定是否管理）本來就需要 dm 在本地、行動前讀到 MVB 的狀態——這件事 serial-at-enroll 方案完全給不了。

4. Scope 與技術方向

  • 只做 Android myViewBoard；Windows 不需要。
  • 提供一個方法讓 Manager 讀到該裝置 MVB 的 instance ID，細節由工程師討論。
  • 技術方向（Stephen Yang, 07-29）：
    • MVB 透過 ContentProvider 提供 instance id、entity name 給 Manager agent
    • ContentProvider 限制 signed key

5. 程式碼現況摘要（edu-droid-flutter）

項目現況對本票的影響
instance ID 已存在。MvbActivator 產生（md5(ts+androidId+uuid)，一次性），存 Hive box activate key app_instanceID；為後端 enroll 的 uid ⚠️ Hive 是 Dart 專有格式，Java/Kotlin 的 provider 讀不到，需鏡射到 SharedPreferences
entity name 完全沒有持久化。Hive 只存 app_entityID（GET /viewboard/{uid}/entity 只取 entity_id） 需新增取得與儲存；且 codebase 有三種 entity 語意，要先釐清（Q1）
ContentProvider 先例 零。只有兩個 exported=false 的 FileProvider；無自訂 <permission>、無 signature 檢查 從零開始寫
Manager agent 整合 MVB 已會反向讀 content://com.viewsonic.dmagent.provider/entity（MainActivity.java:1855-1906）；dmagent 已在 <queries> 白名單 ✅ 本票即做對稱 provider，此段程式是最佳範本
簽章配置 ifp/edla 用 MVBA_PlatForm.jks（ifp 為 system app）；open/store 用 Google Play key ⚠️ protectionLevel="signature" 只在同 key flavor 成立；跨 key 需 runtime SHA-256 allowlist（Q2）
Java 讀 Flutter 資料 已有先例：BootReceiver.java:10 讀 FlutterSharedPreferences ✅ 鏡射方案有現成 pattern

完整細節（檔案路徑、行號、API 清單）見 findings.html。

6. 實作方向

  1. 資料鏡射：Dart 側將 instanceID / entity name 鏡射寫入 FlutterSharedPreferences（建議鏡射點：secure_data_storage.dart _save() 或 mvb_activator.dart:277-285）。
  2. entity name 取得與儲存：擴充 _getEntityID() 解析或改抓 GET /me/entity — 取決於 Q1 答案。
  3. 新增 ContentProvider：以 MainActivity.java:1855-1906（讀 dmagent provider）為對稱範本，與 VB-1399 共同定 contract（Q4）。
  4. 存取控制：視 Manager agent 簽章 key（Q2）決定 signature permission 或 runtime SHA-256 allowlist；若 provider 只需 ifp/edla flavor 註冊，signature 方案可行性大增。
