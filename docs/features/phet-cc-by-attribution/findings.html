1. TL;DR

  • 上游未動工：editor（VSFT-9586）還沒把 attribution 打包進 .olf — 目前 attribution 字串只存在 Hub picker 的 UI i18n。mvbf 播放端沒有真實 .olf 樣本可對接，key 格式（名稱／層級／語言標記）也未定案。
  • sparrow 沒有 CC-BY 標註 POC：全分支查無 attribution 程式碼。使用者記憶中的「sparrow POC」應是 Activity Layer POC（PhET/HTML activity 播放分層架構，已 merge main），是播放基礎、不是標註功能。
  • mvbf 切入點已定位：olf_page_activity.dart（model）→ olf_reader.dart（解析）→ background_activity_overlay_layer.dart（呈現）；url_launcher 已在依賴中。
  • 發現 round-trip 風險：mvbf 存檔會以白名單欄位重寫 html-activity JSON，未知的 attribution key 會被洗掉 — 實作時必須一併處理（見 §6）。

2. attribution key 現況：OLF 規格尚未定義 未定案

  • OLF + HTML 規格頁（Confluence 468615756，v7，2026-04-02，Integrated Draft v1.0）：全文無任何 attribution / license / CC-BY 字樣。html-activity 目前欄位：id / x / y / width / height / matrix / category / source（PhET 為 category: "Activity_PHET"、source = PhET all-locales URL）。
  • edu-vboard-olfspec（OLF 正式 spec repo，僅 main）：同樣無 phet / attribution 內容。
  • 唯一的格式線索 = VSFT-9586 Remark 的 POC segments JSON（見 overview §6）。該 JSON 的字串逐字等於 Hub picker 的 i18n 字串（見 §3）— 推斷「POC 格式」是把 picker 現有文案直接轉成 segments，而票上已判定該文案不合 PhET 規範、僅 segments 結構可參考。
  • 結論：播放端可先按「html-activity.attribution.segments[]（text + 可選 url）+ 語言標記」設計並以假資料開發，但 key 名稱／層級／語言欄位需與 editor（VSFT-9586 owner）定案後才能對接。

6. ⚠️ Round-trip 風險：mvbf 存檔會洗掉 attribution key 必須處理

  • mvbf 存 .olf 時（FileOLFSaveHelper → PageActivity.toOlfJson → HtmlActivity.toJson/toOlfJson）是白名單重建 JSON：只寫出已知欄位（id/x/y/width/height/matrix/category/source），未知欄位一律丟棄。
  • 後果：老師在 mvbf 開啟 Hub 派來的 .olf → 寫筆記 → 存檔，attribution key 就從副本裡消失，之後再播放（mvbf 或轉給 mvbw）都不再顯示標註 → 合規閉環被 app 自己打破。
  • 解法方向：HtmlActivity 解析時保留 attribution 原始 JSON（或未知欄位 pass-through），toJson/toOlfJson 時原樣寫回。這點票上 AC 沒有明寫，建議補進票或至少在實作 PR 內涵蓋 + 測 round-trip。
  • 同理可檢查 sparrow 的存檔路徑（BridgeClient.AppendStagedResourcesToOlf patch ZIP 的方式對 content.json 的影響）— 屬 VSFT-9648 範圍，先記著。
