這份文件用人話說明自動化測試在測什麼、怎麼測、過了代表什麼。 技術細節（YAML 步驟、resource-id）不寫在這，只講「一個真人照著做會看到什麼」。

1. 這些測試在驗什麼

一句話：老師在 myViewBoard（白板 App，簡稱 mvbf）打開一份含題目的教材，按下「開始派題」， 題目要能正確送到 ClassSwift（簡稱 CS），學生用瀏覽器就能收到題目作答。

老師開教材 → 按「開始派題」 → mvbf 把題目送給 CS → CS 建立一場派題 → 學生瀏覽器收到題目

不同腳本各自負責驗證這條路上的「某一段」，從最單純（只驗 mvbf 有送出）到最完整（驗學生真的收到）。

2. 每個腳本在做什麼

1. batch-dispatch — 多題派題「完整閉環」（一條到底）

  • 情境：教材多題頁（11 題）按「開始派題」，一路測到學生真的收到。
  • 驗什麼（整段）：
    1. mvbf 判斷「題目 ≥ 2 → Batch」並送出 11 題；
    2. CS 被喚起、冷啟動、建立批次派題；
    3. 學生用訪客瀏覽器加入 → 答題頁顯示「X of 11」（真的收到 11 題）；
    4. 收尾在 CS 按「End and review question」收掉 ongoing batch。
  • 過了代表：老師派題 → CS → 學生收到，整條打通。
  • （此隻已合併原本分開的 batch-e2e / student-receive——一次測整段，不再拆兩份重疊跑。學生瀏覽器預設 headless，本機除錯可加 --headed。）

2. single-dispatch — 單題派

  • 情境：翻到只有 1 題的那一頁，按「開始派題」。
  • 驗什麼：mvbf 判斷「題目 = 1 → 走單題派題（Single）」，只送 1 題。
  • 過了代表：單題頁的派題決策 + 送出數量正確。

3. end-lesson — 派題中按鈕變灰、結束後恢復

  • 情境：派題後，「開始派題」按鈕的狀態變化。
  • 驗什麼：
    1. 正在派題時，「開始派題」按鈕應該是灰的（不能再按）；
    2. 老師在 CS 按「End and review question（結束並檢視）」結束後，按鈕恢復可按。
  • 過了代表：派題進行中/結束的狀態同步正確（避免重複派題）。
  • ⚠️ 注意：「按鈕恢復可按」的前提是 mission 真正走到 CLOSED。實測發現按「End and review question」 只會公布答案、進 review，若還有學生沒作答會再跳「End and push task」確認框——要按到確認、mission 真正結束， 按鈕才會恢復。詳見 overview Story 4-1 的本機補充。

3. 每次跑腳本的「開頭」與「收尾」

為了讓每次測試都從乾淨狀態開始、結束後不留垃圾，會派題的腳本都包了固定的前置與收尾：

開頭（把環境清乾淨）

  • 關掉會擋住操作的彈窗（新手教學、歡迎頁、更新提示…）。
  • 把白板收斂成單一乾淨空白分頁：App 跨次執行會保留分頁，若上一輪的教材還開著、還停在某一頁， 下一輪的翻頁步驟就會對不上而失敗。這一步讓「開檔」永遠是全新流程。

收尾（把這場派題收掉）

  • 結束這批派題（End and review question）：每次派題都會在後端開一場，不結束會一直累積。 收尾會先關掉蓋在上層的「Join Class」視窗（否則系統只看得到最上層那個視窗、找不到結束按鈕）， 再按「End and review question」把這批派題結束。
  • 刪掉推到裝置上的測試教材檔。

4. 怎麼跑
