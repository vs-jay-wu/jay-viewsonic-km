# 備案：IFP34 上換窗仍然 100% 會閃

**狀態：不做（2026-09-16 決定）。** 等產品端認為不可接受再回來。
主要缺陷已修（見 [調查紀錄](../repositories/Viewsonic-EDU/ragdoll-cat/features/window-switch-flicker/)），
這份記的是**剩下沒解的那塊**。

## 現況

同一份程式碼（commit `96cd5a2c6`）、同樣的 release APK：

| 機器 | 換窗閃爍 |
|---|---|
| Pixel Tablet（`tangorpro`） | 完全不閃 |
| IFP92 | 仍會閃，機率大幅降低 |
| IFP34 | **100% 會閃** |

## 討論出來的結論

### 1. 成因**還沒診斷**，而且有兩個互斥可能

|  | 若成立 | 對應的修法 |
|---|---|---|
| A | 硬體截圖在 IFP 上**靜默失敗**，一路跑軟體退路 | 修「為什麼失敗」（多半是 `HardwareBuffer` usage 或 `wrapHardwareBuffer` 不支援） |
| B | 硬體截圖有效，但機器慢到靜止畫面本身可見 | 才輪到討論要不要在該機型跳過整套擋圖機制 |

**分辨只要一行**（切幾次視窗後）：

```bash
adb logcat -b main -d | grep 回報不可用
```

有輸出 = A。這行 log 是這次特地補的，就是為了讓「靜默降級」不再靜默。

### 2. 「在 IFP34 上跳過這個機制」大機率沒用

Jay 一度提議直接跳過。但「跳過硬體截圖」＝退回軟體截圖，而那正是**原本掉陰影的那條路**：

- 若成因是 A → 它本來就在跑軟體版，跳過**完全沒差**
- 若成因是 B → 換窗變快，但**陰影缺陷原封不動回來**

### 3. CS 加機型分支會是開先例

查證過：**mvbf 確實有 IFP34 專屬分支**（`write_accelerator_plugin`、`image_widget` 的
`filterQuality`、`whiteboard` 擦除時序、`window_mode_app_launcher`、`mvb_webview` 等 8+ 處）。
**但 ragdoll-cat 零分支** —— `IFP34` 在 CS 只出現在註解裡描述現象，`Build.MODEL` 只用於回報。

所以「mvbf 都這樣做，CS 也照做」這個推論**不成立**，要做是開新慣例。

### 4. 主執行緒那段已經順手修掉了

原本整段截圖（含 `syncAndDraw(setWaitForPresent(true))`）都壓在 UI thread，
Pixel Tablet 上佔 84 ms 中的 35 ms。現在只有「錄 display list」在 Main。
這對慢機一定有幫助，而且不是機型 hack —— 已進 commit。

## 為什麼先不做

1. **成因未知**，現在做任何修改都是賭。前四個「看起來很合理」的假說已經全被實測推翻過一次了
2. IFP34 的 adb 當時連不上（USB 沒列舉、網路不通），拿不到那行決定性的 log
3. 主要缺陷已解：Pixel Tablet 完全修好、IFP92 明顯改善。剩下的是單一機型的殘留
4. 沒有產品端的壓力訊號 —— PM 尚未提出 IFP34 的表現不可接受

## 翻案條件（任一成立就回來處理）

1. **PM／產品端明確指出 IFP34 的換窗表現不可接受**（Jay 2026-09-16 原話：
   「未來如果 PM 真的說要改善再來改善」）
2. 有人在 IFP34 上跑出那行 `回報不可用` 的結果 —— **不管有沒有輸出都值得回來**，
   因為它把兩個互斥可能收斂成一個，修法就確定了
3. IFP34 出貨量或在裝機型中的占比提高到讓單一機型缺陷變成普遍問題
4. 換窗機制因為其他需求要重做（那時順便把這個一起解）
