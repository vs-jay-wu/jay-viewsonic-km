# 對外文件

「對外」＝**讀者不是你自己**。PR 描述、Jira 留言、跨團隊規格、給別人（或別人的 agent）
開工用的 prompt 都算。

這些文件最常見的失敗不是寫太少，而是**把自己的思考過程當成交付內容**。

---

## 1. 先確定讀者是誰，第二人稱只能指讀者本身

同一件事對不同讀者要說的話不一樣：

| 讀者 | 這件事該寫成 |
|---|---|
| 對方團隊的**人**（Jira 留言、會議文件） | 「告知」或「需要你們決定」 |
| **自己**的知識庫 | 決策紀錄：選了什麼、為什麼、當時否決了什麼 |
| 對方的**實作 agent**（handoff prompt） | 「照這樣做」／「這件事不在規格內，要問人」 |

⚠️ 同步多份文件時最容易把措辭一起搬過去。實際犯過：給 agent 的 prompt 裡寫
「這件事**不需要你們回覆**」、「希望**一起定下來**」——對 agent 完全沒有意義。

**檢查方式**：把文件裡每一個「你／你們」都指認一次，確認指的是這份文件的讀者。
若指的是第三方（對方團隊、PM、其他 agent），改成第三人稱陳述。

**給 agent 的文件另外要注意**：任何「這是產品決定」「這要看需求」的句子，
對 agent 都是空的。要改寫成它能執行的指令 ——
「**不在本規格範圍內；若沒有既有規範，請向負責的 RD 確認，不要自行決定**」。

## 2. 已決 / 待決嚴格分開，而且待決要盡可能少

把**已經決定**的事寫成「需要對方確認」有兩個壞處：

1. 讓對方以為還有得談，於是重新討論一件已經付出實作成本的事
2. **稀釋掉真正需要他們決定的那一條** —— 實際犯過：唯一真正該問的
   「契約版本演進策略」差點被埋在一堆假問題裡

所以分成兩塊，標題就寫清楚：

- **需要一起確認的** —— 只放雙方共有、且**對讀者也還沒定案**的（見下）
- **行為限制（告知）** —— 我們的既成決定 ＋ 它對對方造成的限制。**不需要對方回覆**

（沒有第三塊。「對方範圍內的事」不需要在文件裡提——見上一節「修法是刪除」。）

### ⚠️「待決」要以**讀者的視角**判斷，不是作者的視角

這是最容易錯的一層：**對作者還沒定案的事，對讀者可能早已定案**
——因為他們拿到的是既成的成品。

實際犯過：把「契約的版本演進策略還沒跟對方 PM 對齊」寫進給對方 RD 的 agent prompt。
那對我確實是待辦（還要開會），但對那個 agent 完全不是——他們實作的對象是
**已經 merge 的 v1**，我給什麼就是什麼。寫進去只會讓它以為契約還會變，
甚至為不存在的彈性做設計。

**檢查方式**：對每一條「待決」問一次——
> 「這件事沒定案，會改變**讀者這次要寫的程式碼**嗎？」

不會，就不要寫。若擔心未來相容性，寫**現在就該遵守的規則**
（例如「不認識的 key 一律忽略」），而不是「這件事還在討論」。

---

## 3. 只寫結論與判準，不寫決策過程

評估階段列出所有選項（含後來否決的）是對的；**交付文件裡留著被否決的選項，
等於邀請對方重做一次已完成的決定，甚至選錯。**

同一段文字在「決定要不要做」的場合有價值，在「照著做」的場合就是雜訊。
這跟「註解描述現狀、不描述 diff」是同一個原理，只是換到跨團隊的尺度。

### 三個具體反模式

**① 不要提供假的權衡。** 「錯的資料 vs 沒有資料」不是取捨——錯的資料的價值是**負的**
（下游持有一個不存在的 key，以它為條件的操作全部落空且無聲）。
把它寫成二選一會誘導對方選錯。正確做法是**移除那個選項**，只陳述決定與理由。

**② 不要警告不可能發生的事。** 寫「不要從 X 拿 Y」之前先問：**對讀者而言 Y 存在嗎？**
實際犯過：把設計階段「要不要曝光某欄位」的分析搬進交付文件的「不要做的事」，
但那個欄位從來沒有被曝光——反而暗示了它存在。

**③ 不要替對方設計他們範圍內的東西。** 對方拿資料做什麼、UI 怎麼呈現是他們的事。
我們的責任是讓狀態**可被判斷**並說清楚，不是提供方案。

### 發現越界時，修法是「刪除」，不是「加免責聲明」

上面三個反模式我都犯過，而且第一反應都是**加字**：

| 反模式 | 錯誤的修法（加字） | 正確的修法（減字） |
|---|---|---|
| 提供假的權衡 | 補一句說明哪個比較好 | **移除那個選項** |
| 警告不可能發生的事 | 解釋為什麼不可能 | **刪掉那條警告** |
| 替對方設計 | 聲明「這不在本規格範圍內／我沒有立場建議」 | **什麼都不說** |

⚠️ 「這不在本規格範圍內」「我們沒有立場建議」這類句子**本身就是越界的痕跡**
——真正守住範圍的文件不會提到範圍。看到自己在寫這種句子時，
要刪的是它前後那整段，不是把它留下來當免責。

同理，若整份文件根本沒有要求對方做某件事（例如 prompt 的任務只有「讀取、分類、回報」，
完全沒提 UI），那就**不需要**特別聲明那件事不在範圍內——那是在回答沒人問的問題。

## 4. 自足：指標只能指向對方開得了的地方

- ❌ 個人知識庫路徑、本機才有的檔案
- ❌ 會被 discard 的本機 WIP（「參考那支 XxxReader.kt」——那個檔明天就不在了）
- ✅ Jira key、PR 連結、對方 repo 內的檔案

若某個設計是實機驗證後才收斂出來的、而承載它的檔案不會留下，
**把結論寫進規格本文**，而不是指向一個會消失的檔。

---

## 5. 把踩過的坑寫進去 —— 那通常是最有價值的一段

契約規格對方看得懂；**「照直覺做會踩到什麼」對方看不出來**。
這一段最省對方時間，也最能避免他們重複你的除錯過程。

寫的時候一併寫**症狀**，不要只寫規則：

> ❌ 節流要狀態感知
> ✅ 純時間節流會讓「資料被清掉後」卡在初始化中不動（實測踩過）；讀到有效值就重置計時器

## 6. 機械性但會咬人的細節

### ⚠️ Jira：`jira_add_comment` 的**回傳值本身是有損的**，不要拿它判斷格式

送出後 MCP 回的那個 `body` 是 ADF→純文字的轉換結果，會把粗體、code span、
清單、標題全部攤平，看起來像「Jira 把我的格式吃光了」。**實際儲存的內容是好的。**

實際犯過（VSFT-10092）：看到回傳值裡 `` `*mvb*` `` 變成 `**mvb**`、
`` `[Quiz Tool][Android]` `` 少一個中括號，就對使用者宣告「ADF 轉換把格式吃掉了」。
用 `jira_get_issue(issue_key, include="comments")` 讀回來一看，backtick、粗體、
兩個中括號全都在 —— 從頭到尾沒壞過。

**規則**：

1. 送出後**不要**看 `jira_add_comment` 的回傳值就下結論。
2. 要確認就用 `jira_get_issue(..., include="comments")` 讀回來 —— 它回的是
   忠實的 markdown。
3. 只有讀回來**真的**壞了才修。**絕對不要**因為 echo 看起來怪就重貼一則
   —— 那會在對方的票上洗版，而且原本那則是好的。

### Jira 真正會吃掉的：含兩個底線的識別字

markdown→ADF 會把 `FOO_BAR_BAZ` 變成 `FOO*BAR*BAZ`，反引號、`\_` 轉義、
fenced code block 三種都救不了；單底線（`foo_bar`）沒問題。

這一條是**讀回來確認過**的真實案例，跟上面那個假警報不同。契約常數送出後
用上面第 2 點複查一次，救不了就改成「確切值見 PR 描述」並確認 PR 那邊是完整的。

#### ⚠️ 但 2026-09-21 有一次反例（同樣是讀回來確認）

VB-2335 的留言裡有九個**四個底線**的檔名（`00_before_broken_question_image.png` 等），
全部包在反引號裡。`jira_add_comment` 的 **echo 把它們吐成 `00*before*broken*question*image.png`**
—— 但 `jira_get_issue(..., include="comments")` **讀回來逐字完好**，底線一個沒少。

所以「反引號救不了」這句**至少不是全域成立**。兩次都是讀回來確認，差別可能在
識別字型態（全大寫常數 vs 帶 `.png` 副檔名的檔名）或工具版本，**沒有查清楚**。

**在查清楚之前的做法（兩種情況都安全）**：照上面第 2 點**一律讀回來**，
以讀回來的結果為準 —— 完好就不要動（不要因為 echo 難看就重貼，那是洗版），
真的壞了才改寫法。**不要**預先假設一定會壞而去繞路。

> 📌 待確認：這兩次觀察為什麼不一致。查清楚之後把這兩小節收斂成一條，不要讓兩種說法並存。

### 另外兩個會被吃掉的（2026-09-11 讀回來確認）

VB-1945 的留言送出後用第 2 點複查，發現：

| 寫的 | 實際儲存 |
|---|---|
| `**做法**` | `\*\*做法\*\*` —— 星號被轉義，**粗體沒生效**，會顯示成字面的 `**做法**` |
| `dex +5.2 MB` | `dex 5.2 MB` —— **前導 `+` 被吃掉** |

證據等級：**讀回來看到**（`jira_get_issue(..., include="comments")` 的逐字輸出）。
我沒有到瀏覽器確認最終渲染，所以不排除是讀回來這一層的再轉義。

**做法**：粗體被轉義只是難看，不影響語意，**不值得為它重貼一則**（洗版的代價更大）。
但 `+` 這種**改變數值語意**的字元要注意 —— 想表達增量就寫「增加 5.2 MB」或
「5.2 MB（增量）」，不要依賴 `+`。同一則裡的反引號 code span、連結、換行都正常。

⚠️ 上一節「實際儲存的內容是好的」那句仍然成立於**它舉的那個案例**（反引號與中括號），
不要因為這一段就反過來不信任 markdown、或去寫轉換器（見下一節）。差別在於：
該檢查的方式沒變，只是這次檢查**真的**查到東西。

### ⚠️ GitHub 沒有附件上傳 API —— 圖只能靠人手動拖

要在 PR 描述或留言裡**內嵌圖片**，唯一的產生方式是**網頁 UI 拖放**（產出
`github.com/user-attachments/assets/…`）。`gh` 沒有上傳附件的指令，那個 endpoint 也不公開。

繞不過去的幾條路，先別浪費時間試：

| 想法 | 為什麼不行 |
|---|---|
| 推一個 branch 放圖，引用 `raw.githubusercontent` | **私有 repo 不行** —— GitHub 用 camo proxy 代理外部圖片，camo 無法帶認證，別人看到破圖 |
| 把圖 commit 進 PR 的 branch | 汙染 diff，而且 reviewer 通常明確說「不用 push」 |
| gist | 二進位檔支援很差 |

**所以流程要這樣安排**：需要貼圖時，**先把圖存到一個 Jay 方便拖放的目錄**
（`~/Downloads/<TICKET>-evidence/`，檔名按順序前綴好可以一次全選），
回報時直接給路徑，不要只說「圖在我本機」。

**Jira 則有 API，可以自己傳**（`jira_update_issue` 的 `attachments`，見 [[jira-vb]]）。
所以退路是：**圖傳 Jira、PR 上放連結** —— 但要講清楚這**不等於**滿足
「證據留在 PR 上」的要求（reviewer 2026-09-21 明確說「不能只在你本機或票的附件」）。
傳完票上要再補一則留言把每個檔對應到哪個步驟，不要丟一堆檔名。

### Jira 的 `@` mention：用 `[~accountid:…]`

`jira_add_comment` 吃 markdown，但 `@名字` 不會變成真的 mention（對方收不到通知）。
可用的寫法是 Jira wiki 的 accountId 形式：

```
[~accountid:712020:e2a970a3-39bf-4999-be20-3d31349b7946] 你的內容…
```

**驗證方式**：讀回來會顯示成 `User:712020:e2a970a3-…`（不是字面的 `[~accountid:…]`），
那才代表存成了 mention 節點。accountId 從 `jira_get_issue` 的
`author.account_id` / `assignee.account_id` 取，或用 `jira_search_user`。
證據等級：**實測**（2026-09-21，VB-2335 comment `133968`，讀回來確認）。

### 不要為此寫 markdown→ADF 轉換器

`jira_add_comment` 本來就吃 markdown 且儲存正確。多一層轉換是解一個不存在的問題，
只會多一個會壞的東西。缺的是驗證方式，不是轉換器。

**量測數字要用對方的基準。** 貼自己開發機的數字（例如「約 4 秒」）會讓對方照那個
體感訂 timeout，而他們的日常機器可能慢好幾倍。要嘛標明機器等級，要嘛直接給
**最慢**的那個數字。
